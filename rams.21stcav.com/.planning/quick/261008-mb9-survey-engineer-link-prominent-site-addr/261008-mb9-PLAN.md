<objective>
On the site survey engineer link (`GET survey/{token}` → `SurveyController::show` → `resources/views/surveys/show.blade.php`), make the site install address genuinely prominent and surface the site contact's name and phone (as a tappable `tel:` link) on the SITE tab — the first tab, per D-01 of the earlier tab-scaffold work.

Reading note for whoever picks this up next: the user's own words were *"on the engineer link please make site install address more obviouis and add site contract, site phone"* — read here as site **CONTACT**, not "contract". The contract/quote reference (e.g. `21CQ31114-08-OPS`) already renders in the masthead via `$survey->project_name`/related fields, so "contract" as a literal ask would be redundant; "contact" is the only reading that adds anything new, and it matches the identical request made earlier for the worksheet link. If that reading turns out wrong, the fields this plan touches (`site_contact_name`, `site_contact_phone`) are easy to repurpose, but nothing here was invented to fit a misreading.

Why the address needs fixing, measured not assumed: it renders exactly once today, at `show.blade.php:246`, as `<p class="text-xs text-white/80 mt-0.5 truncate">{{ $survey->site_address }}</p>` — small, teal-band text, and `truncate` clips a long address outright (the reported case was "4th Floor, 65 Chandos Place, WC2N 4HG" getting cut). An engineer standing outside a building needs to confirm the address at arm's length without it being cut off.

Site contact name/phone are NOT new fields — `site_contact_name` (string 150) and `site_contact_phone` (string 50) already exist on `site_surveys` (migration `2026_04_11_200000_add_visit_and_pm_fields_to_site_surveys.php:12-13`), and the masthead ALREADY computes and conditionally renders a "Site contact: {name} · {tel link}" line today (show.blade.php ~249-279), sourced from the project's latest package (`ship_contact`/`ship_phone`) with a fallback to these two columns, including UK tel: normalisation. That existing line stays as-is — this plan does not touch it beyond what the masthead-truncation fix requires. What's missing is the SAME information, prominent, on the SITE tab, which today only shows client name / survey date / surveyor name / completion count — no address, no contact.

Purpose: an engineer arriving on-site must be able to confirm the address and reach the site contact without hunting, and without a NULL field (the common case on most existing surveys) rendering a broken-looking page.
Output: masthead address no longer truncates; a new Site Address + Site Contact card is the first thing shown on the SITE tab; both locations handle the null case cleanly; a new test proves every one of the above, including the escaping and null-safety.

⚠ **TWO DECISIONS ADDED 2026-10-08, after planning raised them. Both are mine, not the planner's.**

**(a) The masthead "Site contact" line ALSO loses `truncate`.** Planning left this open, noting the brief emphasised the address. Drop it there too. A phone number clipped mid-digits is worse than useless — an engineer reads it, dials it, and gets a wrong number — and the line already sits directly beneath the address, so leaving one clipped and one not would look like a bug.

**(b) ⚠ THE BLANK CASE IS THE WHOLE REASON THIS WAS REPORTED, AND IT MUST BE VISIBLE.**
The site-contact line is **not new** — quick task `260602-mlt` shipped it at `show.blade.php:249-279`, with UK `0→+44` normalisation, reading `extracted_data['ship_contact'/'ship_phone']` and falling back to `site_surveys.site_contact_name/site_contact_phone`. It ends with `@if($siteContactName !== '' || $siteContactPhone !== '')` — **so it renders NOTHING when both are empty.**

The user's screenshot of `21CQ31114-08-OPS` shows no contact line at all. That means the data is blank, **not** that the feature is missing. They read the silence as "this was never added".

So the SITE tab card must **render a visible placeholder when the fields are empty**, never collapse to nothing: an engineer on site must be able to tell *"the office has not filled this in"* apart from *"the page is broken"*, and the office must be able to see the gap. **This is the same failure pattern as the Planned AV works prose block and the AV Works Summary editor — built, working, unpopulated, and silent about it.** Silence is what made all three look broken.

Keep the masthead's existing `@if` behaviour as it is (an empty line in the teal band adds nothing); the **SITE tab card** is where the placeholder belongs.
