# Quick Task 260925-d65: Site survey .docx output escaping (D-46.2-06-05) Summary

`SiteSurveyDocxService` was the only one of five PhpWord writers that never called
`Settings::setOutputEscapingEnabled(true)`. PhpWord's default is `false` and the setting is a
process-global static, so a request that built **only** a site survey escaped nothing — and
`GET site-surveys.docx` is exactly such a request.

## The defect

`app/Services/SiteSurveyDocxService.php` omitted the call its four siblings all make:

| Writer | Call site |
|---|---|
| `DocxBuilderService` | `:128` |
| `DocxBuilderServiceV2` | `:102` |
| `OmManualDocxService` | `:63` |
| `WorksheetDocxService` | `:44` |
| `SiteSurveyDocxService` | **absent** |

Reachable because 46.2-02 gave the service its first caller, 46.2-05 put hand-typed free text on the
cockpit form, and 46.2-06 proved the document opens.

## What unescaped output actually does — measured, not assumed

PhpWord does **not** throw, and the `.docx` is a perfectly readable ZIP. It simply writes the text
verbatim into the run:

```xml
<w:t xml:space="preserve">Ampersand & angle <brackets> "quoted"</w:t>
```

A bare `&` and a stray `<brackets>` element. `word/document.xml` is therefore **not well-formed
XML** — `DOMDocument::loadXML()` reports `xmlParseEntityRef: no name`, a cascade of
`Opening and ending tag mismatch` through `w:t` → `w:r` → `w:p` → `w:tc` → `w:tr` → `w:tbl` →
`body` → `document`, and finally `Premature end of data in tag body`. The generator succeeds
silently; the failure only surfaces when Word opens the file. That is why the second test asserts
well-formedness rather than stopping at the escaped string.

## The vacuity trap, and proof the defence bites

`Settings::$outputEscapingEnabled` is a process-global static and PHPUnit shares one process. Any
earlier test that builds a RAMS / O&M / worksheet document leaves the static `true`, so this test
would pass **vacuously** — measuring a sibling's call, not this one. The test sets it to `false`
itself to reproduce a cold request.

Three runs, all with the SAME test, prove the defence is load-bearing rather than decorative:

| Fix | Defence | Result |
|---|---|---|
| reverted | `false` (as committed) | **2 failed** — the defect is detected |
| reverted | forced `true` (simulating a sibling having run first) | **2 passed** — vacuous, detects nothing |
| applied | `false` (as committed) | **2 passed** — genuinely green |

The middle row is the one that matters: without that single line the test is green against the
unfixed code.

## Test hygiene

`SiteSurveyDocxService` writes to `storage_path('app/site-surveys')` directly, bypassing
`DocumentArtifactStorage`, so `Storage::fake()` does not contain it. The test `finally`-unlinks the
file it generates and asserts the directory's `.docx` count is identical before and after — the
assertion lives in the `finally` block so it holds even when the escaping assertions fail.

## Noticed and left alone

1. **Four of the five cockpit free-text fields never reach the .docx at all.** The brief expected
   `general_notes`, `site_access_notes`, `parking_restraints`, `delivery_routes` and
   `comms_room_access_notes` to be in the document. Grepping the service finds only
   `general_notes` (lines 57 and 131). `site_access_notes`, `parking_restraints`,
   `delivery_routes` and `comms_room_access_notes` are on the model's `$fillable` and on the
   46.2-05 form, but `SiteSurveyDocxService` renders none of them — so a PM types them and they
   silently do not appear in the Word output. This is a content gap, not an escaping defect, and is
   out of scope here. It is also why the test's second vector is a room-level field
   (`access_notes`, via `buildRoomBlock`) rather than one of the other four: those four could not
   demonstrate escaping because they are never written. **Worth its own defect.**
2. **`resources/templates/` does not exist**, so `DocumentTemplateService::exists('site-survey')`
   is always false and the templated branch of `build()` (lines 50-66) is dead on this checkout.
   The programmatic `buildCover` path is the only one exercised — including by these tests. Noted
   because the templated branch passes `general_notes` through a raw string-replace into the
   document XML, which output escaping does **not** cover; if a template is ever added, that branch
   needs its own look. Left untouched.

3. **`DocumentFormatInventoryTest` leaks two `.docx` files per run** into
   `storage/app/site-surveys/`. Its two site-survey cases generate documents and never unlink them,
   so the directory accumulates an 8220-byte / 7944-byte pair on every suite run — visible as dated
   pairs from 2026-09-24 09:22, 19:02, 19:35, 20:02 and 2026-09-25 09:06, ten files in total, none
   of them tracked. **Not mine** (this task's test unlinks in a `finally` and asserts count parity),
   and not in scope, but it is why the directory is not empty. Left as found.
