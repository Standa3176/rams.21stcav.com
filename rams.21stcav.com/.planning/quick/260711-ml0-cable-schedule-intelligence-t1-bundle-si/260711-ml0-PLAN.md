<objective>
Three linked cable-schedule intelligence improvements shipped as one plan, one
atomic commit per task. This is Tier-1 of the cable-schedule intelligence
programme — additive, deterministic, no AI. Port-picker FK infrastructure
(`source_device_id` / `source_port_id` etc.) is Tier-2 and stays untouched.

**T1-A — Signal type + colour-coded XLSX**
Persist a `signal_type` on every generated row and surface it as a new
tinted column in the XLSX between "Cable Type" and "Cores". The `signal_type`
is inferred from the same equipment-name matches that already pick
`cable_type` — one pass, no re-classification.

**T1-B — Prefer Device model when the project has one**
When the project has ≥1 `Device` row, generate from the Device collection
instead of walking the quote extraction. Devices know their room, rack
position, and signal role — that's higher-fidelity than a quote line.
Zero-device projects (every project today, until Device seeding is wired
in) keep the existing quote-line path byte-for-byte.

**T1-C — Word-boundary matching**
The current `matchesAny()` uses `str_contains`, which is why "Microsoft"
matches "mic", "Lamp" matches "amp", and "Cisco" matches "csc" (the
HDBaseT extender token). Swap in a `\b`-anchored `preg_match` and lock
the fix in with a 4-case unit test.

Purpose: measurably fewer false positives in cable-type classification,
richer per-row context, and the visual language that engineering has been
asking for on the exported schedule.

Output: 1 additive migration, 1 model fillable bump, 2 service upgrades,
1 XLSX column, 1 new unit test file, 1 regression-test comment.

Non-goals (deferred — see final section):
- T1-D quoted-cable-product signal type (parse "Cat6a", "HDMI 2.1", etc.)
- T1-E distance heuristics (length_m inference from room→rack lookup)
- T2-A auto-populate `source_device_id` / `source_port_id` FKs
- T2-B signal-path DAG rendering
</objective>

Step 1 — Rewrite `matchesAny()`.
Replace the current body:

    private function matchesAny(string $haystack, array $keywords): bool
    {
        foreach ($keywords as $kw) {
            if ($kw !== '' && str_contains($haystack, $kw)) return true;
        }
        return false;
    }

with:

    private function matchesAny(string $haystack, array $keywords): bool
    {
        foreach ($keywords as $kw) {
            if ($kw === '') continue;
            // Word-boundary match kills false positives — "amp" in "lamp",
            // "mic" in "Microsoft", "csc" in "Cisco". \b handles alpha/
            // digit boundaries. Multi-word keywords like "patch panel"
            // still match because \b is between-token, not per-char.
            // The `i` flag is defensive — all current call sites lowercase
            // the haystack first, but a future consumer might not.
            if (preg_match('/\b' . preg_quote($kw, '/') . '\b/i', $haystack) === 1) {
                return true;
            }
        }
        return false;
    }

Step 2 — Verify no consumer regressions by inspection.
`matchesAny` is called from `classifyItems` (LABOUR/CONSUMABLE/MOUNT lists),
`inferCableRun` (14 branches), `isCableProduct`, `isEquipmentWithMount`.
All keyword lists contain standalone tokens (`'hdmi'`, `'camera'`,
`'projector'`, `'crestron'`) or multi-word tokens (`'patch panel'`, `'audio
processor'`, `'room kit'`) — both work under `\b`. No keyword contains
internal punctuation that `preg_quote` doesn't already escape. No inline
change to any keyword list is required.

Watch-out: `\b` treats hyphens as word boundaries in PCRE. `'q-sys'` will
match against `"biamp q-sys core"` — `\bq-sys\b` succeeds because there's a
boundary before `q`, `q-sys` is treated as three tokens (`q`, `-`, `sys`),
and `\b` sits before `q` and after `sys`. Same for `'cisco switch'`
(space-separated) — `\bcisco switch\b` works. `'4k'` matches inside `"lg
55oled 4k"` — `\b4k\b` succeeds because digit→space is a word boundary.
None of the current keyword lists need touch-ups.
