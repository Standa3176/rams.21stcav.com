### Worksheet snapshot timestamp — the decision

The `worksheets` table has NO `generated_at` column (migration `2026_04_11_000001_create_worksheets_table.php` lines 18–47 confirms — only `timestamps()` + `softDeletes()` + status/error/generated_data/filename/etc).

However, `WorksheetGeneratorService::build()` (line 230) embeds `'generated_at' => now()->toIso8601String()` **inside** the `generated_data` JSON. `BuildWorksheetJob::handle()` (line 97) then persists `generated_data` via `$worksheet->update([...])` which also bumps `updated_at`.

**Two candidate signals:**
1. `$worksheet->generated_data['generated_at']` — ISO8601 string, set ONCE at generation, immutable across status flips (draft → final), accurately represents the snapshot moment.
2. `$worksheet->updated_at` — mutates on every status change, sign-off completion, email send, etc — would false-positive whenever a sign-off lands AFTER a package edit even though the snapshot didn't change.

**Use signal 1.** The `generated_data['generated_at']` ISO8601 string is the honest snapshot timestamp. `updated_at` is the wrong proxy because the worksheet's row gets touched for many non-snapshot reasons (signoff stored in a separate table BUT email-sent columns flip on the worksheet row itself — `completion_email_sent_at` / `failed_email_sent_at` are both fillable).

**Comparison:** `Carbon::parse($worksheet->generated_data['generated_at']) < $worksheet->project->latestPackage->updated_at`.

### ProjectPackage updated_at

`ProjectPackage` is a stock Eloquent model with default `timestamps()`. Every time the project page edit form saves a description, `extracted_data`, `equipment_list`, etc., the row's `updated_at` advances. `Project::latestPackage()` is `hasOne(ProjectPackage::class)->latestOfMany()` — the most recent revision.

### Status guard for isStale

`Worksheet::STATUS_PENDING` / `STATUS_GENERATING` / `STATUS_FAILED` worksheets have no meaningful snapshot to compare against:
- `pending` / `generating` — generated_data is null
- `failed` — generated_data may be null OR set from a prior successful run; either way "stale" is the wrong UX (offer Regenerate via the existing failed-state button, not via a stale badge)

isStale() short-circuits to false for any status that isn't `draft` or `final`.
