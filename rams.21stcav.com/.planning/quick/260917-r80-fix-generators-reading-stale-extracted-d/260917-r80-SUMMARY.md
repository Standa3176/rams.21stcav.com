# Quick Task 260917-r80: Fix generators reading stale extracted-data key Summary

**One-line fix (`equipment` now read before `equipment_list` in `ProjectDataService::resolveUncached()`) so engineer edits to equipment category on a package-review form actually propagate to regenerated install programmes and worksheets — proven end-to-end with a real-`ProjectDataService` regression test.**

- **Completed:** 2026-09-17

## Accomplishments
- Fixed `_raw_equipment` in `ProjectDataService::resolveUncached()` to read `extracted_data['equipment']` before `extracted_data['equipment_list']`, matching the sibling method `resolveEquipment()`'s already-correct priority.
- Replaced the stale, factually-wrong comment above the read site (previously claimed `equipment_list` "has the broadest coverage with area fields intact") with the real invariant: both keys are written identically at import, but `ProjectPackageReviewController::update()`/`approve()` only ever refresh `extracted_data['equipment']`, so `equipment_list` silently goes stale after any edit.
- Added 3 unit tests to `ProjectDataServiceTest.php`: production-shaped divergence fixture (edited `equipment` wins), `reviewed_data`-still-wins regression guard, and a no-op guard for fresh-import packages where both keys are identical.
- Added an end-to-end regression test to `InstallTaskGeneratorServiceTest.php` that exercises the real `ProjectDataService` (not a Mockery double) through `InstallTaskGeneratorService::generate()`, proving generated `InstallTask.equipment_category` reflects the edited copy, not the stale one.
- Verified the fix actually bites: temporarily reverted the one-line change, confirmed both new test suites went RED (3 tasks/`hardware` instead of 2 tasks/`customer_supplied`), then restored the fix and confirmed GREEN again.
