<objective>
Build the office-side review surface for completed engineer surveys.

Three user pains, one bundled task:
1. **Office notes** — per-room and survey-level free-text fields for the office to clean up / annotate engineer-submitted data.
2. **Variations** — flat capture of scope changes found on-site (extra hardware, cable changes, access issues, client-provided changes) for sales/quote conversations. NO workflow.
3. **Client PDF** — Tier 1 client-facing report (matches Mini O&M visual language) that surfaces per-room photos, the office's polished notes, and a variations summary.

Purpose: today the office has nowhere to layer their context onto an engineer's raw survey data, and clients receive the engineer-internal summary PDF (technical jargon, all checklist artifacts) by default. This task closes both gaps without breaking the existing engineer pipeline or RAMS flow.

Output: 1 migration, 1 new model, 1 new controller, 1 new Blade, 1 new TYPE_SURVEY storage constant, 1 new service method, 5 new routes, 4 modified Blades. Single wave, 6 atomic tasks, ~30% context budget.
</objective>

<decision_rationale>
Why these locked decisions over the alternatives — captured here so the executor doesn't second-guess them mid-flow:

**Why flat variations, not a workflow state machine?**
v1 is a record-keeping surface for the sales team's quote-revision conversation. A `proposed → quoted → approved → invoiced` state machine with notifications and event dispatch would require:
- Workflow events + listeners
- Email templates per transition
- Approval gates / role checks
- Audit trail beyond the model timestamps
None of which the user has asked for. The user's verbatim ask is "the info can be used in rams and order additions/changes" — that's an export-to-CSV problem, not a workflow problem. Single status enum (proposed/quoted/approved/rejected) with no enforced order means the office can flip the dropdown freely as the sales conversation evolves. If a real workflow becomes necessary later, this row + status enum is the foundation.

**Why per-room AND survey-level office notes?**
- Per-room only → office notes for site-wide concerns (parking won approval after delivery time agreed, comms-room access window confirmed in writing) end up duplicated across rooms or buried in the wrong room.
- Survey-level only → per-room context (the "client wants the camera moved 30cm left after the engineer's photo" type note) ends up in one giant survey-level block that loses room attribution.
- The Mini O&M (260506-qa9) uses the same shape (per-room blocks + survey-level cover) and worked well — same visual hierarchy reused here for consistency.

**Why TYPE_SURVEY new constant, not TYPE_OM with filename prefix?**
DocumentArtifactStorage's contract is "one type → one disk subdirectory → readers know exactly where to look". Reusing TYPE_OM with `client-survey-` prefix mixes survey artifacts into `documents/om-manuals/`, which:
- Breaks the principle that listings of `documents/om-manuals/` should only contain O&M manuals
- Makes future cleanup commands (e.g. archive surveys older than X) brittle (regex on filename instead of directory listing)
- Is exactly the trap H-07 was designed to prevent (CLAUDE.md: "a typo lands the file in the wrong tree and readers won't find it")
Adding TYPE_SURVEY is a 5-line change and gives surveys their own clean disk root. Same precedent as TYPE_DRAWING (Phase 17) and TYPE_SNAGGING (Phase 16) — both added with no LEGACY_ROOTS entry because the artifact didn't exist pre-H-07.

**Why D-15 auth (auth()->check) not ProjectPolicy?**
Per memory `260506-qa9` and surrounding QA, the production sharing model is "any authenticated user in the office can act on any project". ProjectPolicy enforces stricter owner-OR-admin rules used elsewhere (e.g. project deletion) and would block legitimate office staff from managing variations on a colleague's project. The recent fix `bd31cfc` (260506-qa9) explicitly switched a Mini O&M check from ProjectPolicy to auth()->check for this exact reason. Same pattern here.

**Why DO NOT touch RAMS?**
The user explicitly listed survey-to-RAMS auto-pull as gap (b) in the prior discussion and deferred it. Wiring office notes / variations into RAMS regen is a non-trivial RAMS-pipeline change (RamsDataBuilderService context expansion + Blade layout decisions + risk-classifier hook decisions) that deserves its own quick task with its own design discussion. Storing the data on the survey first lets us iterate on the consumer side later without re-touching the producer.
</decision_rationale>

```php
<?php

namespace App\Http\Controllers;

use App\Models\SiteSurvey;
use App\Models\SurveyVariation;
use Illuminate\Http\RedirectResponse;
use Illuminate\Http\Request;

/**
 * Office-side CRUD surface for SurveyVariation rows. Pure flat capture —
 * no workflow, no events, no notifications (D-LOCK-1).
 *
 * Auth: D-15 pattern via abort_unless(auth()->check(), 403). NOT ProjectPolicy
 * (the production sharing model lets any authenticated office user act on any
 * project — see memory `feedback_*` and quick task 260506-qa9).
 */
class SurveyVariationController extends Controller
{
    public function store(Request $request, SiteSurvey $siteSurvey): RedirectResponse
    {
        abort_unless(auth()->check(), 403);

        $data = $this->validate($request, $siteSurvey);

        SurveyVariation::create(array_merge($data, ['site_survey_id' => $siteSurvey->id]));

        return back()->with('success', 'Variation added.');
    }

    public function update(Request $request, SiteSurvey $siteSurvey, SurveyVariation $variation): RedirectResponse
    {
        abort_unless(auth()->check(), 403);
        abort_unless($variation->site_survey_id === $siteSurvey->id, 403);

        $variation->update($this->validate($request, $siteSurvey));

        return back()->with('success', 'Variation updated.');
    }

    public function destroy(SiteSurvey $siteSurvey, SurveyVariation $variation): RedirectResponse
    {
        abort_unless(auth()->check(), 403);
        abort_unless($variation->site_survey_id === $siteSurvey->id, 403);

        $variation->delete();

        return back()->with('success', 'Variation removed.');
    }

    /**
     * Validation rules shared by store + update. The photo_id allow-list is
     * scoped to the survey's own photos so a forged photo_id from another
     * survey is rejected.
     */
    private function validate(Request $request, SiteSurvey $siteSurvey): array
    {
        $allowedPhotoIds = $siteSurvey
            ->rooms()
            ->with('photos:id,site_survey_room_id')
            ->get()
            ->flatMap(fn ($r) => $r->photos->pluck('id'))
            ->all();

        return $request->validate([
            'room_name'   => ['nullable', 'string', 'max:150'],
            'type'        => ['required', 'in:extra_hardware,extra_labour,cable_change,client_provided_change,access_issue,other'],
            'description' => ['required', 'string', 'max:3000'],
            'qty'         => ['nullable', 'integer', 'min:1', 'max:9999'],
            'photo_id'    => ['nullable', 'integer', 'in:' . (empty($allowedPhotoIds) ? '0' : implode(',', $allowedPhotoIds))],
            'status'      => ['nullable', 'in:proposed,quoted,approved,rejected'],
            'notes'       => ['nullable', 'string', 'max:2000'],
        ]);
    }
}
```

```php
public function buildClientReport(SiteSurvey $survey): string
```

```php
/**
 * GET /site-surveys/{siteSurvey}/client-report

/**
 * GET /site-surveys/{siteSurvey}/variations.csv
 *
 * Streams a CSV of the survey's variations for sales-team quote-revision
 * conversations. Quick task 260508-v7g.
 */
public function variationsCsv(SiteSurvey $siteSurvey): \Symfony\Component\HttpFoundation\StreamedResponse
{
    $this->authorizeSurvey($siteSurvey);

    $siteSurvey->load('variations.photo');
    $filename = 'variations-survey-' . $siteSurvey->id . '-' . now()->format('Ymd') . '.csv';

    return response()->streamDownload(function () use ($siteSurvey) {
        $out = fopen('php://output', 'w');
        // BOM so Excel renders UTF-8 cleanly.
        fwrite($out, "\xEF\xBB\xBF");
        fputcsv($out, ['Room', 'Type', 'Description', 'Qty', 'Status', 'Photo Filename', 'Notes', 'Created', 'Last Updated']);
        foreach ($siteSurvey->variations as $variation) {
            fputcsv($out, [
                $variation->room_name ?? '',
                str_replace('_', ' ', $variation->type),
                $variation->description,
                $variation->qty,
                $variation->status,
                $variation->photo?->original_name ?? '',
                $variation->notes ?? '',
                $variation->created_at?->format('Y-m-d H:i') ?? '',
                $variation->updated_at?->format('Y-m-d H:i') ?? '',
            ]);
        }
        fclose($out);
    }, $filename, [
        'Content-Type' => 'text/csv; charset=UTF-8',
    ]);
}
```
