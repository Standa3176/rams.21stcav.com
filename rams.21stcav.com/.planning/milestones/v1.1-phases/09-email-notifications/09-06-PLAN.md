## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Postmark Server API Token → production `.env` | Token grants send permission for the entire account; mishandling = mail fraud risk |
| DNS zone `21stcav.com` → public DNS resolvers | Wrong record breaks deliverability or (worse) lets attackers spoof from `@21stcav.com` |
| BCC env var (`ops@21stcav.com`) → audit inbox | Misrouted BCC sends operational mail to the wrong inbox |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-04 | I (Information disclosure) | `POSTMARK_API_KEY` in production `.env` | mitigate | Token lives only in production `.env` (git-ignored); checklist explicitly warns "never commit secrets to `.env.example`"; `config:cache` resets after rotation; rollback path = swap to `MAIL_MAILER=log`. |
| T-09-01 | S (Spoofing) | DNS records SPF/DKIM/DMARC | mitigate | Checklist mandates all three records before "live" tick; DMARC starts at `p=none` for 14-day observation, then `p=quarantine`; `check-auth@verifier.port25.com` round-trip verifies all three pass. |
| T-09-03 | I (Information disclosure) | `RAMS_NOTIFICATION_BCC=ops@21stcav.com` in production | accept | BCC inbox is internally controlled; BccTest in plan 09-05 already verified BCC presence/absence per config. RFC 5322 mail providers (Postmark) strip BCC from outgoing headers per spec — recipients do not see the BCC list. |
| T-09-04 | I (Information disclosure) | Postmark Activity log | accept | Activity log retains email metadata for 45 days (Postmark default); operationally accessible only via authenticated dashboard; no patient/financial PII in any system mail. |
