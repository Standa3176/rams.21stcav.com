<objective>
Give `Visit` the lifecycle it needs — sent, returned, sent back, accepted — with the smallest honest
schema: a column for every act a human performed, and a derivation for everything the engineer's own
record already knows.

Purpose: every other plan in this phase reads or writes one of these. Getting it wrong here is the
only way this phase can quietly break Phase 45's `1 visit · reconstructed` at-rest disclosure, or
create a second place where "the engineer returned this" is recorded — the exact failure D-01 spends
a paragraph warning about.
Output: a migration, the model's state machine, a factory that can produce a visit in any state, and
a unit test that proves the transitions.
</objective>

      (timestamps); `accepted_by_user_id`, `created_by_user_id` (foreignId to `users`,
      `nullOnDelete()`); `send_back_reason` (text); `rooms_in_scope` (json).
    - **There is deliberately NO `returned_at` and NO `scope_locked_at` column.** A return is
      already recorded, by the engineer, on their own record — `SiteSurvey.submitted_at` or the
      latest `WorksheetSignoff`. A second copy on `visits` would go stale the moment a worksheet is
      re-signed after remedials, and then the cockpit and the engineer link would disagree about
      whether the work came back with no way to tell which is true. This is the same reasoning
      `Visit::isSuperseded()`'s docblock already makes, applied to the same shape of fact. Both are
      DERIVED in Task 2.
    - Every column is nullable because a migration that back-filled a value would be asserting
      something about the 24 backfilled visits already on live that nobody measured.
    - Deleting a staff login must never delete delivery history — hence `nullOnDelete()` on both FKs.
    - After migrating, a row inserted before this migration still reads `status = 'completed'`,
      `is_backfilled = 1` and NULL in every new column.
  </behavior>

    of `2026_09_19_150100_add_install_record_id_to_install_programmes.php`. `Schema::table('visits', ...)`

    do NOT change the `status` default; a PM-created visit sets its own status explicitly.

<task type="auto" tdd="true">
  <name>Task 2: The state machine — stored acts, derived truth</name>
  <files>app/Models/Visit.php, database/factories/VisitFactory.php, tests/Unit/Models/VisitLifecycleTest.php</files>
  <behavior>
    - `STATUSES` is UNCHANGED: `[planned, completed]`. The stored column keeps meaning what Phase 45
      made it mean, and no backfilled row is rewritten. The one new stored value is that a visit
      whose link has been issued is written as `planned` with `sent_at` set — `sent` is a derived
      state, not a stored one.
    - A NEW derived vocabulary: `STATE_PLANNED`, `STATE_SENT`, `STATE_RETURNED`, `STATE_SENT_BACK`,
      `STATE_ACCEPTED`, `STATE_CLOSED`, enumerated in `STATES`.
    - `returnedAt(): ?Carbon` — DERIVED through the existing `source()`: a survey's `submitted_at`,
      or the created_at of a worksheet's `latestSignoff()`. Null when there is no source, when the
      source was force-deleted, or when nothing has come back. Never reads a column on `visits`.
    - `state(): string` resolves in this order and the order is the decision:
      accepted_at set → `STATE_ACCEPTED`;
      `wasSentBack()` → `STATE_SENT_BACK`;
      `returnedAt()` not null → `STATE_RETURNED`;
      `sent_at` set → `STATE_SENT`;
      stored status `completed` → `STATE_CLOSED` (this is every Phase 45 backfilled visit);
      otherwise `STATE_PLANNED`.
    - `isClosed(): bool` — accepted_at set, OR stored status `completed`. This is the method the
      cockpit's progress ring must use: a visit a PM accepted is finished, and so is a backfilled
      one that was already complete when it was reconstructed.
    - `isAwaitingReturn(): bool` — `sent_at` set and `returnedAt()` null.
    - `isLocked(): bool` — `returnedAt()` is not null. **Scope locks ON RETURN, not on acceptance**:
      ROADMAP criterion 3 says "stays editable after sending; scope locks once a return arrives".
    - `wasSentBack(): bool` — `sent_back_at` set AND later than `returnedAt()`. Comparative, not a
      bare flag: a visit sent back and then returned again is no longer awaiting rework, and a
      boolean would have had to be un-set by hand to say so.
    - `acceptedBy(): BelongsTo` and `createdBy(): BelongsTo` to `User`.
    - `rooms_in_scope` casts to `array`; `sent_at` / `accepted_at` / `sent_back_at` cast to
      `datetime`. `$fillable` gains the seven new columns and nothing token-like — there is no token
      on this model and none is to be introduced here.
    - A backfilled visit from `VisitFactory::backfilledFromWorksheet()` still reads
      `isBackfilled() === true`, `status === 'completed'`, `isClosed() === true`, and
      `state() === STATE_CLOSED`. A backfilled worksheet visit WITH a signoff reads
      `isLocked() === true` — which is correct and worth a test: the work came back, years ago.
    - Factory states: `sent()`, `returned()`, `sentBack()`, `accepted()` — `returned()` must produce
      the return on the SOURCE record (a submitted survey / a signed worksheet), not on the visit,
      or the factory would be modelling a shape the schema does not have.
  </behavior>
  <action>
