engineer link back, produced by the generator that already exists. Modules that hold a document but
no visit get one control: generate it.

of the read-only fence. Both halves belong in the same commit sequence — a button that appears
without the fence entry being deleted on purpose is exactly the drift the fence exists to catch.

less than it did and says per entry why.

The existing generators, all inside the `auth` block in routes/web.php:

  worksheets.generate-from-project     POST  worksheets/generate-from-project/{project}

`WorksheetController::generateFromProject()` does exactly this, and nothing else:
  Worksheet::create([... 'status' => Worksheet::STATUS_GENERATING])
  $this->deliverablesService->autoFlipIfNotRequired($project, ProjectDeliverable::KEY_WORKSHEET, auth()->user())
  $this->workerMonitor->ensureRunning()
  BuildWorksheetJob::dispatch($worksheet->id)
  return back()->with('success', 'Worksheet generation queued.')

`SiteSurveyController::createFromProject()` returns the create FORM (with a supersede confirmation
block) when a live survey already exists — `whereNull('superseded_at')` and status in
draft/completed — and otherwise calls `$this->service->createFromProject($project, $user)` then
`autoFlipIfNotRequired(..., KEY_SITE_SURVEY, ...)`.

Both `SiteSurvey` and `Worksheet` generate their `access_token` in `boot::creating` by DIRECT
PROPERTY ASSIGNMENT, bypassing `$fillable`. `access_token` and `access_token_expires_at` are
deliberately absent from `$fillable` (security re-audit S-02/S-03, documented inline). That pattern
is the ONLY sanctioned way a token comes into existence. Never mass-assign one, never generate one
outside a model's own boot hook, never put one in a form.

The cockpit's read controller (`ProjectCockpitController`) has a docblock saying it exposes exactly
one action and that "the next phase that needs a write owns its own controller." Honour it: this
plan adds a SECOND controller and leaves the read one alone.

Module keys come from `CockpitModulePresenter::moduleMap()` — site_survey, rams, worksheet, om,
cable_schedule, install_programme, drawings, snagging, programming.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> `POST /projects/{project}/cockpit/*` | The cockpit's first write surface. Staff-auth, session CSRF |

| PM form input -> `visits` row | Dates, room names and resource ids are all user-supplied |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-46-04-01 | Spoofing | cross-site POST to the create route | mitigate | Registered inside the `web` + `auth` group so session CSRF applies; `test_every_form_in_the_region_carries_a_csrf_token()` proves the form carries the token rather than assuming the middleware is wired |
| T-46-04-02 | Elevation of Privilege | creating a visit on another project | mitigate | `{project}` is route-model-bound and every write is scoped to it; `module` and `visit_type` are `Rule::in` the issuer's own const maps and address no id |

Tokens come only from `SiteSurvey::boot` / `Worksheet::boot` direct property assignment; `$fillable` omissions S-02/S-03 are preserved. A test asserts no token appears in any rendered form field |
