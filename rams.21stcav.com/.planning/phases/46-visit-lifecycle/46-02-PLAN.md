<objective>
The minimal snag record D-03 asks for: enough to capture what a PM saw on a return, shaped so that
Phase 47 EXTENDS it rather than replacing it.

Purpose: D-02 makes "raise a snag" one of the four PM actions, and D-03 fences everything that
follows into Phase 47. A record designed only for what Phase 46 needs would force Phase 47 to
migrate it; a record designed for Phase 47's full lifecycle would be Phase 46 building Phase 47.
This plan takes the narrow middle: the columns a raised snag genuinely has, and not one column more.
Output: `snags` table, `Snag` model, factory, unit test.
</objective>

<task type="auto" tdd="true">
  <name>Task 1: The snags table and model</name>
  <files>database/migrations/2026_09_20_130000_create_snags_table.php, app/Models/Snag.php</files>
  <behavior>
    - Columns, and only these: `id`; `project_id` (FK, cascade on delete — a snag has no meaning
      without its project); `visit_id` (FK to `visits`, **nullOnDelete**, nullable); `title`
      (string 200, NOT NULL); `detail` (text, nullable); `room_name` (string 200, nullable);
      `raised_by_user_id` (FK to `users`, nullOnDelete, nullable); `status` (string 24, default
      `open`); `timestamps`. Index on `(project_id, status)` and on `visit_id`.
    - `visit_id` is NULLABLE ON PURPOSE even though Phase 46 always sets it: Phase 47 will let a
      snag be raised that is not tied to a single visit, and a NOT NULL column would have to be
      altered to allow it. This is the one place the schema anticipates Phase 47, and it does so by
      being LESS strict, never by adding a column nobody writes.
    - `Snag::STATUS_OPEN = 'open'` and `STATUSES = ['open']` — exactly one entry. Phase 47 owns the
      three outcomes and adds them here. A Phase 46 snag has no other state it can honestly be in.
    - No `parts`, no `outcome`, no `parent_snag_id`, no `resolved_at`, no `assigned_to`. Each of
      those is Phase 47 (D-03). Adding one here would be building the snag lifecycle behind a
      column name.
    - `visit()`, `project()` and `raisedBy()` relations; `$fillable` covers every column except
      `id` and the timestamps.
    - A snag whose visit's SOURCE record was force-deleted still resolves its visit and its project
      — the same D-04 property the visit itself has.
  </behavior>
  <action>
    Write the migration and the model. Docblock the model with D-03 quoted verbatim ("raising a snag
    here creates a minimal snag record linked to the visit it came from... Phase 46 must not build
    the snag lifecycle — it provides the entry point Phase 47 builds out") and an explicit
    **PHASE 47 EXTENSION POINTS** list naming: the three outcomes on `status`, a parts relation, and
    a `parent_snag_id` for linked follow-ups. Naming them as future work at the definition site is
    what makes this a foundation rather than a stub, and it is the difference between Phase 47
    extending this table and Phase 47 replacing it.

    Do NOT add a route, a controller, a policy or a service for snags in this plan. The only writer
    in Phase 46 is the PM action built in Plan 46-05.

    Do NOT run `artisan migrate:fresh --env=testing` (see 45-BASELINE.md — it would wipe
    `database/database.sqlite`).
  </action>
