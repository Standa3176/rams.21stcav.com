is not managing one.

<!-- Read these before deciding where a note goes. -->

`SiteSurvey` ALREADY HAS an `office_review_notes` column (quick task 260508-v7g, "Office review
surface"). **Do not write the office note there.** Three reasons, and they are the decision:
it is a single overwritable field, so the second note destroys the first; it carries no author and
no timestamp, so "who said that, and when" is unanswerable; and it lives ON the engineer's record,
which is the shape D-02 forbids — "the engineer's record stays intact; the office view sits
alongside it". A worksheet has no equivalent field at all, so reusing the survey's would also mean
install visits could not be annotated.

`CockpitPanelPresenter::notes(Project, string $moduleKey)` already builds the Notes tab from the
module's own note field plus logged `note_added` entries. This plan ADDS office notes to that list;
it does not replace what is there.

`Snag` (Plan 46-02): project_id, visit_id (nullable, nullOnDelete), title, detail, room_name,
raised_by_user_id, status (only `open`). `SnagTest` has a six-column scope fence asserting no
Phase 47 column exists — `outcome`, `parts`, `parent_snag_id`, `resolved_at`, `assigned_to`, `cost`.

Fence state after 46-04: `<form`, `<input`, `<button`, `<textarea` lifted inside the cockpit region;
`<select` and `<script` banned; nine handler attributes banned; `Add note` and `Create visit` lifted
from DEFERRED_AFFORDANCES; `Add a snag` and `Book a visit` STILL BANNED as Phase 47 wording, which
is why this plan's control reads **`Raise a snag`** and nothing else.
