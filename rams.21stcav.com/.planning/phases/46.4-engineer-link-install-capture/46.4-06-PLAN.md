<objective>
Teach the offline queue a **third kind** so a kit row survives a plant room with no signal (D-06,
*"make queue"*) — **additively**, without touching the schema every pending photo depends on — and
**rule, at the code, on what modify and mark do offline.**

Purpose: this is the single most dangerous change in the phase. `drain()` today **unconditionally**
does `fd.append('photo', row.blob, …)` and routes on a **two-value `kind` ternary**. A kit row has
no blob, so as things stand it would hit that append's catch and be marked **"Local blob unreadable"
FOREVER** — an engineer's work, lost silently, on the one surface used by someone standing in a
plant room.

Output: a `kit` kind that branches BEFORE the blob append, a third URL arm, local edit/discard of a
still-queued row, a queue panel that names all of it, and guards that pin the schema.

**REVISED 2026-09-26.** Was plan 05. Now also carries the D-08 offline ruling below.
</objective>

<offline_ruling>
## The ruling on modify and mark offline — decided here, stated at the code

**A row that is already on the SERVER cannot be modified or marked without a connection.
A row still sitting in the QUEUE can be corrected or discarded on the device, because that is not a
server operation at all.**

Why, in full, and this reasoning goes in a comment above the queue's kit handling so nobody
re-litigates it from scratch:

1. **A queued ADD has no server id.** A queued "modify row 41" that arrives before the add that
   creates row 41 is a second, order-dependent protocol layered on a store whose schema is frozen at
   version 1 — client-side temporary ids, a drain-time rewrite, and a merge rule for the case where
   the add succeeded and the modify then 422'd. That is exactly the class of change that strands
   work, and stranding work is the failure this whole plan exists to prevent.
2. **This page already has this idiom and engineers have met it.** Sign-off refuses offline by
   explicit design — `alert('Signing off needs an internet connection…')`. Room-complete and
   survey-reviewed are plain POST+redirect with no offline path at all. Only photos queue today.
   Requiring a connection to CHANGE something is consistent; it is not a new tax.
3. **Correcting a queued row needs no server.** The row has not left the phone. Editing or
   discarding it is an IndexedDB write, and discarding it is **not** a "mark for deletion with a
   reason" — nothing reached the office, so there is nothing to explain. Say that in the UI.
4. **The engineer is always told which case they are in.** Plan 05 renders `Correct` and
   `Mark for deletion` visibly disabled with the words `Needs a connection` when offline. A queued
   row's own controls read `Edit` and `Discard` and work. ⚠ **An affordance that appears to work
   offline and silently loses the change is the one unacceptable outcome** — neither half of this
   ruling permits one.

**The cost, stated honestly:** an engineer who typed the wrong quantity offline and has already
regained signal long enough for the row to drain must wait for signal to correct it. That is a real
limitation. It is worth surfacing at the checkpoint, and if the user rejects it, the answer is a
queued-modify protocol as its own phase — not a bolt-on here.
</offline_ruling>

**The schema — DO NOT CHANGE ANY OF IT:**
  DB_NAME 'engineer-worksheet' · **DB_VERSION 1** · STORE 'pending_uploads'
  `createObjectStore(STORE, { keyPath: 'id', autoIncrement: true })`
  `store.createIndex('capturedAt', 'capturedAt', { unique: false })`
⚠ `onupgradeneeded` only ever **creates** the store — it has no migration branch. A keyPath or index
change **strands every photo already queued on every engineer's phone**. The queue's own record is
the engineer's only copy. Treat this schema as immutable.

**`OfflineQueue.enqueue(row)`** — `row = {token, kind, room, blob, mime, fields}`; stores
`{token, kind: row.kind || 'completed', room, blob, mime, fields: row.fields || {},
attemptCount: 0, lastError: null, capturedAt: Date.now()}`. `fields` is a **free-form bag**;
nothing in the store's shape needs to change for a kit row.

**`OfflineQueue.drain(opts)`** — the two places that must change, in order:

  1. THE BLOB APPEND (this is the bug):
        const fd = new FormData();
        try {
            fd.append('photo', row.blob, (row.kind === 'label' ? 'label.jpg' : 'photo.jpg'));
        } catch (e) { … row.lastError = 'Local blob unreadable'; … }
  2. THE URL:
        const path = row.kind === 'label' ? '/label-photo' : '/photos';

  `fd.append('room_name', row.room || '')` and the fields spread sit between them and are **already
  correct for a kit row**.

**Internals that already exist and must be reused, not duplicated:**
  `tx(mode, fn)`, `_getAllRaw()`, `_updateRow(row)`, `_sleep(ms)`, `OfflineQueue.remove(id)`,
  `OfflineQueue.list()` (projects `{id, token, kind, room, mime, fields, attemptCount, lastError,
  capturedAt}` — note it does NOT project the blob, so the panel already works for a blobless row),
  `OfflineQueue._notifyChange()`, `OfflineQueue.subscribe(handler)`.

**The panel UI** (a separate IIFE): `_esc(s)`, `_relTime(ts)`,
`_icon(kind) { return kind === 'label' ? '📷' : '🖼'; }`, `_statusFor(row)`, `renderList(items)` —
which prints `row.kind === 'label' ? 'Box serial label' : 'Completed-work photo'` as every row's
subtitle. **Both assume every row is a photo.** Each row already renders `↻ Retry` and `✕ Remove`.

Auto-drain: `_autoDrain(reason)` fires on the `online` event and a 60s tick, guarded by `_draining`.
Drain sleeps 200ms between rows (5/sec) — comfortably under the 30/min per-token
`worksheet-kit-write` limiter from plan 05.

**From plan 04:** `WorksheetCaptureLock::MESSAGE` is the sentence a signed worksheet returns with
422. Plan 04's SUMMARY carries its exact text. **The panel must display it verbatim.**
**From plan 05:** the exact 422 text for marked / reconciled / nothing-changed / blank-reason.
