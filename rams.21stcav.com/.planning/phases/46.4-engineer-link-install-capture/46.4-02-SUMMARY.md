# Phase 46.4 Plan 02: Two Photo Trays, a Label, and a Lightbox That Works Summary

Every room on the engineer link now has a **Start** tray and a **Completion** tray, each with its
own count, thumbnails, label field and capture button; a label typed before capture reaches
`WorksheetPhoto.caption` online **and** through the offline queue with **zero schema change**; and
tapping a thumbnail opens a photo for the first time since the call sites were written in 260508.

## What shipped

### 1. The server half (Task 1)

`uploadPhoto` validates `bucket` with `Rule::in(WorksheetPhoto::BUCKETS)` — the **model's own
constant**, never a literal list, so the vocabulary cannot drift between the two files.

**`sometimes`, not `nullable`, and the distinction is load-bearing.** An **absent** bucket is a
compatibility case that must keep working: a pre-46.4 client posts none, and neither does a photo
that has been sitting in a browser's IndexedDB since before this deploy and drains days later. Those
land in `completion` — the same statement 46.4-01's backfill made about every legacy row. A bucket
that is **present but empty** is a client that meant to say something and said nothing, and is
rejected 422. `nullable` would have conflated the two, because the global
`ConvertEmptyStringsToNull` middleware turns `bucket=` into `null` before the validator sees it.

`sort_order` is now scoped on **room AND bucket**, so the two trays number independently.
`bucket` joins `caption` in the JSON response. `deletePhoto` was not given a bucket parameter, and
**`markRoomComplete` was not touched** — its "engineers on flaky networks must not be locked out"
docblock is a decision, not an oversight.

### 2. The trays, the label, and the lightbox (Task 2)

`$roomPhotos` is partitioned **once**, in the existing `@php` block, by `groupBy(bucket)` — no second
query on a page an engineer opens on site signal. Two trays render Start-then-Completion, each
`data-photo-tray data-bucket="…"` with its own `data-photo-count` span.

⚠️ **`📷 Photos of completed work` is unchanged, verbatim.** 46.4-01's migration justified stamping
every legacy photo `completion` by quoting that exact wording; renaming it would retroactively make
a written ruling look arbitrary. The comment above the tray array says so and names the migration.

**D-04 costs one input and four lines of JS.** `uploadWorksheetPhoto` gained a 4th `bucket` argument
and reads the label from the `[data-photo-caption]` input inside its own `[data-photo-tray]`
ancestor (`window.__wsPhotoCaptionInput`, shared by the original and the offline wrapper). Online:
`fd.append('bucket', …)` plus `caption` when non-empty. Offline: the same two values in
`fields: { bucket, caption }`. **`fields` is a free-form bag that is already spread into the drain
FormData key by key**, so `DB_VERSION`, `keyPath`, `createObjectStore` and the `capturedAt` index are
all untouched — which matters because `onupgradeneeded` on this page only ever CREATES, so a version
bump would strand every photo queued on a bad-signal site. **`kind` stays `'completed'`**: a photo is
still a photo and the bucket is data, not a kind. The label input is cleared after a successful
capture so the next photo does not inherit it.

Captions render **escaped** under their thumbnail (`{{ }}`, no second raw echo) — engineer free text
on a page the **client signs**.

**The lightbox is ~70 lines of vanilla `<dialog>`**, appended once on first call, inline-styled like
everything else on this page: image, caption line (set via `textContent`, never `innerHTML`),
prev/next shown only when `length > 1`, arrow keys, backdrop-tap close, Esc via the dialog's own
behaviour, and a `window.open` fallback where `showModal` is missing. It takes
`([{url, caption}], startIndex)` — **the existing signature — so neither call site changed.** It is
deliberately **not** `components/photo-lightbox.blade.php`: that component is Alpine-based, Alpine is
never loaded here, and it styles itself with classes this page does not carry on a stylesheet that is
byte-pinned. Including it would have swapped one dead feature for another.

**Plan 04's hook, and nothing more:** `data-capture-control` is on every capture control — both label
fields, both capture buttons, both hidden file inputs, and each photo delete button (D-07 locks
deletes by name). **No lock was built here.** The trays ship unlocked for exactly one wave; 46.4-04
owns the lock and enforces it server-side, because a hidden button was never a permission on a
token-only page.

### 3. Guards that bite (Task 3)

Thirteen tests, every count derived from `self::ROOMS` / the pinned occurrence tally and never a bare
literal. Tray membership is asserted **by DOMXPath subtree** — a page-level `assertSee` passes when
both photos land in the same tray, which is the exact defect the partition could ship. The escaped
caption assertion checks the escaped form is **present** before checking the raw form is absent.

**Bite proof:** replacing the Start tray's bucket with a dud turned this file
**`Tests: 5 failed, 8 passed`** — the tray-count guard, the title guard, the subtree guard, the
per-tray count guard and the lock-hook guard all went red together.

## Deviations from Plan

**1. [Rule 1 — bug in the plan's own spec] `nullable` could not deliver the plan's stated behaviour.**
The plan said `'bucket' => ['nullable', …]` AND that `bucket=` must be rejected 422. Those are in
tension under Laravel 11's default `ConvertEmptyStringsToNull`, which rewrites the empty string to
`null` before validation — `nullable` would have accepted it and defaulted it to `completion`.
`sometimes` delivers both halves of the plan's intent. Recorded in the validation comment and pinned
by `test_an_upload_with_no_bucket_key_at_all_still_succeeds…` plus the four-case rejection provider.

**2. [Rule 2 — missing critical] Comment wording had to avoid the literals the guard counts.**
The first draft of the lightbox comment contained the words `x-show` and the component's tag, which
took the pinned Alpine occurrence counts from 1/0 to 3/1 — a guard failing on a **comment**. The
comment now names neither, and says why in-line so the next reader does not reintroduce them.

**3. [Rule 2] The `⚠ No photos captured yet` warning is now keyed to the COMPLETION tray's own count**,
not the whole-room count it read before. The plan put the warning on the completion tray only, and a
warning inside a tray that counts its own photos must speak about that tray or it is a lie. The
consequence is deliberate and documented: a room holding **only** a start photo shows the warning
while `Mark Room Complete` is enabled — because the gate is whole-room, unchanged, and **visual only**.

## Known gaps, carried rather than solved

- **The trays are capturable after sign-off for exactly one wave.** `test_this_plan_ships_no_lock_of_its_own`
  asserts that state on purpose so 46.4-04 flipping it is a visible, intentional change rather than
  a silent one.
- **`uploadPhoto` still has NO room-name inclusion-list guard**, unlike `markSurveyReviewed` and
  `markRoomComplete`. It accepts any `string|max:200` room name and has since long before this phase,
  so a leaked token can create a photo row keyed to a room that does not exist. **Pre-existing, not
  introduced here, and not fixed here** — adding the guard is a behaviour change to an endpoint two
  other plans are writing against this week. Worth a checkpoint question at 46.4-07.
- **No thumbnail reordering and no move-between-buckets.** A photo captured into the wrong tray must
  be deleted and retaken.
