# Phase 46.4 Plan 04: The Sign-Off Lock Summary

Once a client signs, the engineer link captures nothing more — and **the server is what refuses**,
on all five capture endpoints that ship today, before validation, with a no-side-effect assertion on
every refusal and a passing mirror case on every unsigned worksheet. The page still renders the
record; only the ability to change it goes.

## The five locked endpoints

| Method | Route | Refusal test | No-side-effect assertion |
|---|---|---|---|
| `uploadPhoto` | `POST worksheet/{token}/photos` | `test_upload_photo_is_refused_after_signoff_and_writes_nothing` | row count AND `Storage::allFiles()` count both unchanged |
| `deletePhoto` | `DELETE worksheet/{token}/photos/{photo}` | `test_delete_photo_is_refused_after_signoff_and_deletes_nothing` | row survives AND the file survives |
| `uploadLabelPhoto` | `POST worksheet/{token}/label-photo` | `test_upload_label_photo_is_refused_after_signoff_and_creates_no_device` | `devices` count unchanged, `device_label_photos` still 0 |
| `confirmLabelPhoto` | `POST worksheet/{token}/label-photos/{photo}/confirm` | `test_confirm_label_photo_is_refused_after_signoff_and_confirms_nothing` | still unconfirmed AND `device.serial_number` still null |
| `deleteLabelPhoto` | `DELETE worksheet/{token}/label-photos/{photo}` | `test_delete_label_photo_is_refused_after_signoff_and_deletes_nothing` | row survives AND the file survives |

Each has a **mirror** (`…_still_succeeds_on_an_unsigned_worksheet`), because a lock that refuses
everything always is an outage, not a lock. Plus
`test_a_worksheet_signed_twice_is_still_locked` — `isSigned()` is existence, not equality.

Every guard sits on the method's **first line after `resolveWorksheet()`, before validation**
(T-46.4-04-05: a locked caller learns nothing about the payload). Two placements are load-bearing
beyond that:

- `deletePhoto` unlinks the **file before the row**, so a guard any later could leave an orphan.
- `uploadLabelPhoto` does a `Device::firstOrCreate` before it stores anything, so a guard placed
  after validation would still **mint an asset-register row** for a signed worksheet. The device
  count is the assertion that catches that.

| Every GET — `show`, `servePhoto`, `serveSurveyPhoto`, `downloadReferenceFile` | Reading is not capturing. A signed worksheet is a **record** its signer must be able to open | `test_the_page_still_renders_and_photos_still_serve_after_signoff` |

The reason lives in the test file as prose, so a future reader sees a decision rather than an
oversight — and **flipping the status-confirmation ruling is a two-line change** (invert one test,
move two names out of the reflection allow-list).

## The reflection check, and its bite proof

`test_every_unlisted_public_controller_method_calls_the_capture_lock` reflects over every public
method **declared on** `PublicWorksheetController`, subtracts a seven-entry allow-list where each
entry carries its own one-line reason, and asserts the rest contain
`WorksheetCaptureLock::isLocked`. It also asserts every allow-listed name still exists, so the
list cannot outlive the methods it excuses.

**Bite proof:** deleting the `confirmLabelPhoto` guard turned the file
`Tests: 2 failed, 15 passed` and the reflection failure named the method:

> These public PublicWorksheetController methods write without the D-07 capture lock and are not on
> the reasoned allow-list: **confirmLabelPhoto**.

**This is what forces plan 46.4-05's three kit endpoints into the guard** without anyone having to
remember this file exists.

## 422, not 423 Locked

423 is arguably more correct and is deliberately **not** used. `public-show.blade.php`'s hand-rolled
fetch handlers treat every non-2xx identically and surface the response text; introducing a status
code no handler on that page has ever seen is a change with no benefit. 422 is already this
controller's refusal idiom (the forged-room-name guard) and matches SCC's
`PublicPmvController::addCheck` precedent. Body is `{"message": …}` so plan 06 has one key to read.

## The exact MESSAGE — plan 46.4-06 displays this VERBATIM

```
This worksheet has been signed off — it can no longer be changed.
```

**It is a sentence, not the word "Locked", on purpose.** A worksheet can be signed while an engineer
still has rows queued in IndexedDB on their phone. Those rows drain into a locked endpoint and take
this 422 — **correct** (the client signed a record; late arrivals must not alter it) — **but the
engineer must be TOLD, in words, not left with a row stuck on "failed".**
`test_a_drained_queue_row_gets_the_human_sentence_plan_06_must_display` posts a photo shaped exactly
as `drain()` builds it (multipart, field `photo`, `fields` bag spread as top-level keys, **no bucket
key** — a row queued before this deploy has none) and asserts the body carries the string, so plan 06
has something real to display. The requirement is written into that test's docblock, addressed to
plan 06 by name.

## The view: read-only, not gone

`$captureLocked = WorksheetCaptureLock::isLocked($worksheet)` is computed **once** in the existing
top `@php` block — **not** `isSigned()` at ten sites, and **not** re-derived from `$latestSignoff`
(the controller passes that in for display and the two must not drift). Server and page now share
one predicate through one class.

Not rendered when locked: both trays' label field, capture button and hidden file input; every
per-photo `✕`; the `📷 Box Serial Label` control; the label `Edit / Confirm` button (it POSTs to
`confirmLabelPhoto`). The "⚠ No photos captured yet — capture at least one before requesting
sign-off" warning also goes, because it is advice that only makes sense while capture is possible.

Still rendered: **the trays themselves, every thumbnail, every caption, every label reading and the
kit list.** A named comment on the tray control block tells plan 46.4-05 to wire its kit drawer to
this same variable rather than inventing a second flag.

One banner, server-rendered `@if`, no Alpine, no JS toggling:

> ✓ Signed on **{d M Y}** — this worksheet is a completed record and can no longer be changed.
> Photos, labels and kit lists stay visible to read.

## Deviations from Plan

**1. [Rule 1 — the view carried the same lie as the docblock.]** The plan named the controller
docblock. It did not name `signed-banner__keep`, which said, on a page the **client** reads:
*"This worksheet remains accessible — engineers may continue to update notes and photos."* That is
now false on the server. Leaving it would have been worse than the docblock — a client reading it
would believe the record they signed can still be edited. Corrected in place, not deleted, with the
history in a comment: *"This worksheet remains accessible to read — it is now a completed record and
can no longer be changed."*

**2. [Rule 3 — avoided a self-inflicted guard failure.]** The first draft of my banner comment
contained the words "no x-show" — which would have taken plan 02's pinned Alpine occurrence count
from 1 to 2 and failed a guard **on a comment**, the exact trap plan 02's summary records paying for
once already. The comment now names no directive and says why in-line.

**3. [Scope, stated not silently taken]** The plan's task 2 said the sign-off form must not be gated.
It already was, by pre-existing code — see "Things noticed" below. I routed that pre-existing
`@if($latestSignoff)` wrapper through `$captureLocked` (identical state, one predicate) and did not
narrow it. Un-gating a client-facing signature form was not asked for and is not mine to take.

## Things noticed and deliberately left alone

- **⚠️ THE SIGN-OFF FORM IS ALREADY UNREACHABLE ON A SIGNED PAGE, AND IT IS NOT THIS PLAN'S DOING.**
  `260504-iy4 L3` wraps the *entire* page body — the room drawers **and the Client Sign-Off card** —
  in a single `<fieldset disabled>` whenever a sign-off exists (opens ~:705, closes ~:1560). A
  disabled `fieldset` cascades, so the JS that enables `#signoff-submit` after a signature is drawn
  cannot re-enable it. **The server accepts re-signing — this plan asserts that — but the page has
  not offered it since 260504.** So the "snag-list audit trail" is currently reachable only by a
  direct POST. I routed the wrapper through `$captureLocked` (same state, one predicate) and changed
  nothing else: narrowing it re-opens a client-facing signature form on signed worksheets, which is a
  behaviour change nobody asked for and which cuts against D-07's own spirit. **Worth a checkpoint
  question at 46.4-07 alongside the room-complete question.**
- **A send-back does not unlock a signed worksheet.** `VisitReworkState::isReopened()` already
  accepts a `Worksheet`, and `SiteSurvey::isLockedForEngineer()` uses exactly that to reopen a
  submitted survey after an office send-back. Worksheets have **no** such reopening gate today, so
  `isLocked()` is plain `isSigned()` as the plan specifies. If the office sends back a **signed**
  worksheet, the engineer cannot capture the fix. Pre-existing shape, not introduced here, and a
  genuine question for the user — but `isLocked() === isSigned()` is what D-07 and the plan say, and
  widening it to `isSigned() && ! isReopened()` is an authorization change that must be decided, not
  inferred.
- **`deleteLabelPhoto` has no UI trigger anywhere in `public-show.blade.php`.** The endpoint is
  routed, throttled and now locked; nothing on the page calls it. Guarded and tested regardless —
  a reachable route is a surface whether or not a button points at it.
- **`uploadPhoto` still has no room-name inclusion-list guard**, unlike `markRoomComplete` /
  `markSurveyReviewed`. Pre-existing, carried forward from plan 02's summary, still a 46.4-07
  checkpoint question.
- **Two read-only banners now appear on a signed page** — the new one at the top of the capture
  region and the pre-existing 🔒 `alert-info` above the sign-off card ("Photo uploads, label
  captures, and review actions are now disabled"). That pre-existing sentence is **now true**, having
  described a client-side-only state before. Redundant but accurate; deleting existing client-facing
  copy was not in scope.
- The sign-off form's five dead Alpine directives, ~110 untracked PNG screenshots, a stray `nul`.
  All ruled out of phase 46.4 by name; `git clean` is prohibited.
