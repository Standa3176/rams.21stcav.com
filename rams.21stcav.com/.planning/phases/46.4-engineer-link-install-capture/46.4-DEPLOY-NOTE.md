## 1. THIS PHASE ADDS MIGRATIONS. RUN THEM FIRST. THIS IS THE ONE THAT WILL BITE YOU.

Two, both new in this phase:

| # | File | What it does |
|---|---|---|
| 1 | `database/migrations/2026_09_26_100000_add_bucket_to_worksheet_photos_table.php` | Adds `worksheet_photos.bucket` + an index, and **backfills every pre-existing row to `completion`** with an explicit `UPDATE` (not a column default) |
| 2 | `database/migrations/2026_09_26_100100_create_worksheet_additional_kit_table.php` | Creates `worksheet_additional_kit` — the per-room extra-kit rows |

```
php artisan migrate --force
```

> **Run this BEFORE anyone opens an engineer link.** `public-show.blade.php` now
> reads `bucket` on every photo and queries `worksheet_additional_kit` on every
> room. Deploying the Blade without the migrations is a **500 on the one surface
> that is used standing on site**, not a page that merely looks unchanged.

**Order matters: migrate, then serve the new Blade.** If your deploy ships code
and migrations in one step, that step must not be interruptible between the two.

**Rolling back is safe, and was read rather than assumed.** Both `down()` methods
are guarded: migration 1 checks `Schema::hasColumn` and walks `Schema::getIndexes`
before dropping either, and migration 2 is a plain `dropIfExists`. Rolling back
**destroys the kit rows** — there is no archive — so take a DB backup first if any
engineer has already used the link.

## 5. ⚠️ TELL THE OFFICE BEFORE SOMEONE PHONES: A SIGNED WORKSHEET CAN NO LONGER BE CHANGED

This is the behaviour change of the phase, and it is deliberate (decision D-07 —
the user's words: *"client cannot chage anything as they are signing to confirm
work is complete."*).

After this deploy, **once a client has signed, the engineer link goes read-only.**
Gone: photo upload, photo delete, photo labels, label-photo upload/confirm/delete,
and adding, correcting or marking a kit row. **Eight endpoints, enforced on the
server** — not merely by hiding buttons, because the token is the only credential
on that page and a hidden button is not a permission.

Anyone in the habit of adding a photo after the client signed **will find the
buttons gone.** The page says why, in one sentence:

> ✓ Signed on *{date}* — this worksheet is a completed record and can no longer be
> changed. Photos, labels and kit lists stay visible to read.

Three things deliberately still work after sign-off, so nobody reports them as
broken:

- **Reading.** The page, the photos and the kit list all still render. A signed
  worksheet is a record.
- **Signing again.** Append-only; the snag-list re-sign workflow is untouched.
- **Mark room complete / mark survey reviewed.** These are engineer status
  confirmations, not the captured record. *This is a ruling, and it is question 6
  at the plan's checkpoint — it may yet be reversed.*

## 6. Engineers with the link already open, and photos already queued

- **The IndexedDB queue schema did NOT change.** `DB_VERSION` is still `1`, the
  store, the `keyPath` and the `capturedAt` index are all unchanged. Nothing
  already queued on a phone is stranded by this deploy.
- **A photo queued BEFORE this deploy has no `bucket` field, and that is fine.**
  The upload endpoint validates `bucket` with `sometimes` — an absent bucket
  defaults to `completion`, exactly the statement migration 1's backfill makes
  about every legacy row. Those photos drain and land normally.
- ⚠️ **But a row queued before a client signs will now be REFUSED on drain**, with
  HTTP 422 and this sentence: *"This worksheet has been signed off — it can no
  longer be changed."* The queue panel displays that server message verbatim, so
  the engineer reads the reason rather than seeing a row stuck on "failed". That
  refusal is correct — a client signed a record and late arrivals must not alter
  it — but it is the question someone will ask, so it is written down here.
- **There is no recovery path for such a row from the device.** If it matters, the
  office adds it, or the worksheet is handled off-system.

## 8. This repo's own deploy traps that still apply

- **Deploy as `stcav`, NOT as `root`.** Running the deploy as root leaves
  root-owned files in the tree and the next `stcav` deploy fails on them.
- There are **two remotes** on this repo. Push to the one you meant.
- `RAMS_UNIFIED_COMPOSER` picks the live PDF template — unrelated to this phase,
  but it is the env flag behind past "code-only stages break the site" incidents.

## 9. How to tell the deploy worked, in ninety seconds

1. Open an engineer link for a worksheet with rooms. Each room should show **two
   photo trays** — `📸 Before you start` and `📷 Photos of completed work` — and an
   **`+ Add additional kit`** button. If the page 500s, the migrations did not run
   → §1.
2. Open a worksheet that had photos **before** this deploy. Every one of them
   should sit in the **Completion** tray. If any is in Start, the backfill did not
   run.
3. Add a kit row. Open the office worksheet page — it should appear in an
   **Additional Kit** table with a named engineer, a qty and a description.
4. Open `Projects › (a project) › Asset List`. It should list devices carrying a
   captured serial / MAC / asset tag.
5. Open an **already-signed** worksheet's link. The grey banner should be there and
   there should be **no capture buttons at all**.
