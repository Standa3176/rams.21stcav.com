# Phase 46.4 Plan 06: The Offline Queue's Third Kind Summary

An engineer standing in a plant room with no signal can now add additional kit. The row is saved on
the device with **no blob at all**, and it uploads by itself when signal returns — alongside any
queued photos, into a different endpoint, without either disturbing the other.

The change is **purely additive**. **DB_VERSION is still 1, the keyPath is still `id`, the
`capturedAt` index is untouched, and the queued record gained no field.** `onupgradeneeded` only ever
creates the store — it has no migration branch — so any of those would have stranded every photo
already sitting on every engineer's phone. That is the failure this plan existed to avoid, and all
four are now pinned by assertions rather than by care.

## The guard, verbatim — read the ordering without opening the file

```js
                            // without an edit here.
                            const isBinary = row.kind !== 'kit';
                            if (isBinary) {
                                try {
                                    fd.append('photo', row.blob, (row.kind === 'label' ? 'label.jpg' : 'photo.jpg'));
```

and the third arm:

```js
                            // A TABLE, not a nested ternary — the next kind gets
                            // its own line and nothing else moves.
                            const path = row.kind === 'label' ? '/label-photo'
                                       : row.kind === 'kit'   ? '/additional-kit'
                                       :                        '/photos';
```

`fd.append('room_name', …)` and the `fields` spread sit between them and were already correct for a
kit row — they were not touched.

## The assertion that encodes the whole plan, and its bite proof

The ordering is compared by **source position**, never by eye:

```php
$guardAt  = strpos($drain, "const isBinary = row.kind !== 'kit';");
$appendAt = strpos($drain, "fd.append('photo'");

// NON-VACUITY FIRST: both must exist, or `false < 123` would "pass".
$this->assertIsInt($guardAt, 'The isBinary guard is gone from drain(). A blobless kit row now hits the blob append.');
$this->assertIsInt($appendAt, 'The blob append is gone from drain() — this guard is measuring nothing.');

$this->assertLessThan(
    $appendAt,
    $guardAt,
    "The isBinary guard is no longer ABOVE fd.append('photo'). A blobless kit row will now be "
    . "stamped unreadable forever. This ordering is the entire point of plan 46.4-06.",
);
```

plus a second assertion that the append is genuinely *inside* the guard, not merely after it:

```php
$this->assertMatchesRegularExpression(
    "/const isBinary = row\.kind !== 'kit';\s*\n\s*if \(isBinary\) \{/",
    $drain,
    'The isBinary guard no longer opens a block — the append may be running unconditionally.',
);
```

**I watched it FAIL before it passed.** The bite restored the pre-plan bug — the append made
unconditional and the guard left sitting below it:

## What queues, and what does not — and what the engineer SEES

| Action | Offline behaviour | What is on screen |
|---|---|---|
| **ADD a kit row** | **Queues.** Blobless `kind: 'kit'` row in IndexedDB, drains to `/additional-kit` | The row appears immediately with a `Queued on this device — uploads by itself when you are online` chip, plus the existing `📥 Saved offline — will upload when you're online` toast |
| **CORRECT a row already on the SERVER** | **Refused.** Not queued | The control reads **`Needs a connection`**, `aria-disabled="true"`, dimmed, and explains itself on tap (wave 4's finding: a natively `disabled` button fires no click) |
| **MARK a server row for deletion** | **Refused.** Not queued | Same as above |
| **EDIT a row still IN THE QUEUE** | **Works.** `OfflineQueue.update(id, patch)` — an IndexedDB write, no server involved | Control reads **`Edit`**; the drawer reopens pre-filled, heading `Correct this queued item`, button `Save on this device` |
| **DISCARD a row still IN THE QUEUE** | **Works.** The existing `remove(id)` | Control reads **`Discard`**; confirm says *"It is still on this device and has NOT reached the office, so there is nothing to explain — it simply will not be sent."* No reason is asked for, and it is **not** a D-08 mark-for-deletion |

**No affordance appears to work offline and silently loses the change.** The one remaining way that
could have happened — editing a queued row that drained while the drawer was open — is closed twice:
`update()` returns **false** for a row that is gone or in `_uploadingIds`, and the drawer then shows
*"That item has already uploaded — reload the page to correct it."*

### Rule 2 addition: a drained row loses its device-local controls

Not in the plan, added because the plan's own rule demanded it. A queued row that drains would have
kept a live-looking `Edit` button whose `update()` would quietly return false. `refreshQueuedRows()`
subscribes to `offline-queue-change`, drops the controls and swaps the chip to
`Uploaded — reload the page to correct this item`. The real row, with `Correct` / `Mark for
deletion`, arrives on the next render from the database, exactly as the plan specified.

## The four reasons are pasted AT THE CODE

A 40-line block comment at the head of the drawer's kit handling carries the ruling itself — not a
pointer to this file, because this file will not be open when somebody next wonders. It opens
`46.4-06 — WHAT QUEUES OFFLINE, AND WHAT DOES NOT` and carries all four headings verbatim:
**A QUEUED ADD HAS NO SERVER ID** · **THIS PAGE ALREADY HAS THIS IDIOM AND ENGINEERS HAVE MET IT** ·
**CORRECTING A QUEUED ROW NEEDS NO SERVER** · **THE ENGINEER IS ALWAYS TOLD WHICH CASE THEY ARE IN**,
ending with the cost stated rather than hidden. Four of those strings are asserted present by
`test_the_offline_ruling_is_written_at_the_code`.

**The cost, restated for the checkpoint:** an engineer who typed the wrong quantity offline and has
since regained signal long enough for the row to drain must wait for signal to correct it. If the
user rejects that, the answer is a queued-modify protocol as its own phase — not a bolt-on here.

## The queue panel renders a kit row correctly

`_icon` is now an object literal keyed by kind with a default — `🧰` kit, `📷` label, `🖼` otherwise —
because that is where a fourth kind goes, not on the end of another ternary. The subtitle reads
`Additional kit · <qty> × <part description>` instead of `Completed-work photo`.

**Truncation happens BEFORE escaping** — `_esc(_trunc(f.part_description, 60))`, never the reverse,
because truncating already-escaped markup can cut an `&amp;` in half and render the fragment raw
(T-46.4-06-05). The test asserts `_esc(_trunc(` is present **and** `_trunc(_esc(` is absent.

`_statusFor`, `_relTime` and the chip count were left alone — the count is kind-agnostic and should
stay that way, because the engineer wants to know how many things are waiting, not how many of each.

## The server's own words now reach the engineer

`drain()`'s non-ok branch reads the JSON body and prefers its `message` over `resp.statusText`. That
is what carries `WorksheetCaptureLock::MESSAGE` — *"This worksheet has been signed off — it can no
longer be changed."* — to an engineer whose row drains into a worksheet the client has since signed,
and it equally surfaces plan 05's marked / reconciled / nothing-changed sentences.

**The change is confined to the message.** The counters, the `attemptCount >= 3` threshold and
`_updateRow` are untouched, and that is asserted rather than promised:

```php
$this->assertSame(3, substr_count($drain, 'if (row.attemptCount >= 3) hitMaxRetry++;'));
$this->assertSame(3, substr_count($drain, 'row.attemptCount = (row.attemptCount || 0) + 1;'));
```

## ⚠️ WHAT IS **NOT** PROVEN HERE

**Nothing in this plan exercises IndexedDB.** Two rows actually sitting in a real browser's store —
one photo, one kit row — and **both** draining when signal returns is a **browser** fact, and this
repo has **no browser-driving harness**. `puppeteer` is a dependency, but it is reached only through
Browsershot inside `PdfRenderService`, which renders HTML to PDF; it does not drive a live
application.

**The real coexistence proof is step 3 of plan 46.4-07's blocking human checkpoint** — airplane mode,
one photo and one kit row queued, signal restored, both arrive. The guards in this plan exist to make
that walk's code-level preconditions non-negotiable between now and then. The same paragraph is at
the top of `OfflineQueueKitKindGuardTest`, because a guard test that quietly implies more than it
checks is worse than no test.

**Puppeteer verdict:** not attempted beyond inspection. A browser-driven test would need a live HTTP
server (IndexedDB, CSRF and the session-bearing token URL all require an origin), which is the plan's
explicit stop condition. **Nothing was installed** (T-46.4-06-SC).

## The empty-string `labour_resource_id` finding — MEASURED, and it works

`fd.append(k, fields[k])` stringifies, so a kit row queued with nobody selected sends
`labour_resource_id=''`. **That is accepted and stores `null`**, confirmed against the real endpoint:

```php
$response = $this->drainKitRow($worksheet, self::ROOMS[0], [
    'labour_resource_id' => '',
    'qty'                => '2',
    'part_description'   => 'Cable ties, black',
]);

$response->assertStatus(201);
// NULL, not 0 — a zero would be a real id that nobody holds.
$this->assertNull($row->labour_resource_id);
```

The global `ConvertEmptyStringsToNull` middleware turns it into `null` before `nullable|integer` sees
it. **No drawer change was needed** — the key is sent unconditionally, as the plan's first option had
it.

## Both drain payload shapes, against the SAME worksheet

`test_both_drain_payload_shapes_are_accepted_against_the_same_worksheet` posts the kit shape
(multipart, `room_name` + the three fields, **no `photo` part**) and the photo shape (a `photo` part
plus `room_name`, `bucket`, `caption`) at one worksheet in one test, then asserts one kit row and one
photo landed with the right bucket and caption. Neither endpoint's validation is disturbed by the
other's shape. That is the **server** half of coexistence; the client half is the checkpoint.

## Deviations from Plan

**1. [Rule 3 — blocking] `OfflineQueue.list()` did NOT project `fields`; it does now.**
The plan's `<interfaces>` block stated `list()` projects `{id, token, kind, room, mime, fields, …}`.
Measured, it projected only `id, kind, room, capturedAt, attemptCount, lastError`. Task 2(a) requires
the panel to build a kit subtitle "from `row.fields`, which `list()` already projects" — it could not.
One line added: `fields: r.fields || {},`. **This is a PROJECTION change, not a record-shape change**
— the blob is still stripped, the store is untouched, and a comment at the line says so. The plan's
"do not touch `list`" was about the store, and this respects that.

**2. [Rule 1] The photo endpoint returns 200, not 201.**
The plan's task 3 behaviour spec predicted `/photos` would answer 201. `uploadPhoto` has always
returned a bare `response()->json()` — **200**. The test asserts 200 with a comment saying it was
measured, not assumed. First run caught it: `Failed asserting that 200 is identical to 201`.

**3. [Rule 1 — my own comment broke a guard] The guard comment was rephrased.**
My first draft of the `isBinary` comment quoted `'Local blob unreadable'` literally, which took the
file's occurrence count to **2** and would have failed
`test_the_photo_failure_path_was_not_collaterally_edited`. Rephrased to "the unreadable-blob error
below"; the literal is back to exactly **1**. Caught by counting before committing, and the task 1
commit was amended.

**4. [Rule 2 — the plan's own rule demanded it] `refreshQueuedRows()` was added.**
Described above. Without it a drained row keeps a dead `Edit` button, which is precisely the
"appears to work and silently loses the change" outcome the plan forbids.

## Task 2(d) — the deliberate NON-change, recorded

A row whose failure is terminal by nature (the worksheet has been signed) will keep retrying on the
60s tick and keep 422ing. **No new terminal state and no new column was added.** The existing
`attemptCount >= 3` / `hitMaxRetry` path already surfaces it, and the engineer now reads the lock's
sentence in the panel and can hit `✕ Remove`. The alternative — a `dead` flag — **would be a schema
field on a store frozen at version 1**, which is the one thing this plan refuses to do.
