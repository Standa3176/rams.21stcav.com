## Idempotency — explicit proof (case 4, `test_running_backfill_twice_does_not_duplicate_rows_or_audits`)

Seeded: 1 project with 1 `RamsDocument`.

| Run | `project_deliverables` rows (this project) | `project_deliverable_audits` rows (this project's deliverables) |
|---|---|---|
| After 1st `up()` call | 9 | 9 |
| After 2nd `up()` call (same seeded state, no new documents) | 9 | 9 |

`rams` stays `required` after the second run (asserted explicitly) — the second run's `insertOrIgnore()` calls all return `0` (row already exists), so neither the deliverable row nor its audit row is touched or duplicated.

## Does not clobber existing rows — explicit proof

Case 4 doubles as this proof: the `rams` row written by the first run (`state = 'required'`) is asserted unchanged after the second run. No test in this plan calls `->update()` on `project_deliverables` at all — the migration's only two DB-write calls (`insertOrIgnore` on `project_deliverables`, plain `insert` on `project_deliverable_audits` gated behind the insert actually happening) are structurally incapable of overwriting a pre-existing row; `insertOrIgnore()` is a no-op against an existing unique-key match at the SQL level on both SQLite and MariaDB, not just in this codebase's usage of it.

## Programming — what it backfills to, and why

Unconditionally `not_yet_decided` for every project, every time. Confirmed live this session: there is no `Programming` model, no `programming`-shaped table, and no relation on `Project` for it anywhere in this codebase (D-05 — Programming is a tracked flag only, no generator, explicitly out of scope for this whole phase). D-17's rule is "has evidence → required, no evidence → not_yet_decided" applied per-deliverable; Programming has no evidence source to check, so `not_yet_decided` is the only value the rule can produce for it. This is not the "default the whole back-catalogue uniformly" behaviour D-17 explicitly rejects — the other 8 keys are genuinely evidence-driven per-project; only this one key is constant, and it is constant because there is nothing to check, not because a fallback rule was applied lazily.

## Engine-specific risk (SQLite vs MySQL/MariaDB)

None identified. Every DB call in the migration is one of: `->count()`, `->pluck()`, `->value()`, `->get()`, `->insertOrIgnore()`, `->insert()` — all through Laravel's query builder against plain equality/`whereIn` predicates on already-indexed foreign-key columns. No `whereRaw`, no `DB::raw`, no `JSON_EXTRACT`/`->>'`, no raw aggregation. `insertOrIgnore()` itself is engine-portable at the Laravel grammar level (`INSERT OR IGNORE INTO` on SQLite, `INSERT IGNORE INTO` on MySQL/MariaDB) — this is a well-established Laravel builder method, not a hand-rolled raw statement, so there is nothing here that could silently diverge in production the way a raw JSON function would (per this plan's stated worst-case-outcome constraint).

One structural point worth flagging rather than treating as risk: the migration loads all `projects.id` values into memory via a single `->get()->each()` (not chunked). The plan's threat model (`T-260822-11`) explicitly accepts this — read-only counts against indexed columns, single insert per row, no user input — and states the production row-count/scale question is deliberately left unvalidated in favour of idempotency as the mitigation. Not changed here; flagging per the report requirements, not treating it as a bug to auto-fix, since the plan explicitly specified this exact loop shape.
