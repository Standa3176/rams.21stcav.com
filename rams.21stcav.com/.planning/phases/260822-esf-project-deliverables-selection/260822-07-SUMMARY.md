# Phase 260822-esf Plan 7: Deliverables Edit Form (D-10) + Completion Warn-Then-Confirm (D-14) Summary

**Registered `projects.deliverables.update` at the exact path/name Plan 04's already-shipped "Add anyway" form depends on, built the Project Data tab's first-ever write form (9 deliverables, audited via `ProjectDeliverablesService::setState()`), and added a warn-then-confirm branch to `transition()` so completing a project with outstanding required deliverables lists exactly what's missing and asks for confirmation instead of silently blocking or silently proceeding — including fixing a previously-dead `session('warning')` CSS class that would have made that warning invisible.**

## Performance

## Accomplishments

- **The blocking contract is satisfied exactly.** `php artisan route:list --name=projects.deliverables.update` shows `POST projects/{project}/deliverables › ProjectController@updateDeliverables` — the identical path/name Plan 04's muted-tab "Add anyway" form (commit `9812c48`) already hardcodes.
- `ProjectController::updateDeliverables()` validates `deliverables[key]=state` via Laravel's `array:key1,key2,...` rule (rejects any key outside `ProjectDeliverable::ALL_KEYS` with a 422) + `Rule::in()` on the 3-state enum, then writes every changed key through `ProjectDeliverablesService::setState()` — the sole audited (D-03) write path. It also accepts Plan 04's flat `deliverable_key` + `state` payload, normalizing it into the same array shape before validating, so both callers share one code path (see Deviations — this was a real functional gap, not just a route-registration formality).
- The Project Data tab's `show.blade.php` panel gets its first-ever write form: 9 radio groups (Required / Not required / Not yet decided), one per `ProjectDeliverable::ALL_KEYS`, pre-checked to `$project->deliverableState($key)`, plus a shared optional reason textarea.
- `ProjectController::transition()` gains a D-14 warn-then-confirm branch for `to_status=completed`: `outstandingRequiredDeliverables()` lists every `ALL_KEYS` entry that is `Required` with zero backing documents (`programming` deliberately excluded — no document type exists for it, D-05). First submit without `confirm_incomplete=1` redirects back with a `warning` flash instead of changing status; the same Advance button's hidden `confirm_incomplete` input then flips to `1` automatically (driven by `session('warning')`), so the next click proceeds exactly as `transition()` always did.
- Fixed a real gap found while verifying D-14 end-to-end: `layouts/app.blade.php` had an `alert-banner--warning` CSS class with no matching `@if(session('warning'))` block anywhere in the codebase — the D-14 warning would have been flashed and silently discarded. Added the block, mirroring the existing success/error banner shape.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `updateDeliverables()` normalizes Plan 04's flat `deliverable_key`+`state` payload**
- **Found during:** Task 1, before writing tests
- **Issue:** The plan specified validating `deliverables[key]=state` via `array:ALL_KEYS`. Plan 04's already-shipped "Add anyway" form (`show.blade.php`, commit `9812c48`) posts a flat `deliverable_key` + `state` pair to this exact route. Against the plan's validation rule as literally specified, that flat payload has no `deliverables` key at all and would 422 — the "Add anyway" button would silently stop working (redirect back with unrendered validation errors) even though the route itself resolves cleanly. The plan's own "Report back" instructions explicitly required proving this form "now reaches a live route," which read together with D-02's "no hard block anywhere" rationale means it must actually work, not just avoid a 404/500.
- **Fix:** `updateDeliverables()` checks for `deliverable_key` without `deliverables` and merges it into the same array shape before validating, so one validation/write path serves both callers.
- **Files modified:** `app/Http/Controllers/ProjectController.php`
- **Verification:** `ProjectDeliverablesUpdateTest::test_plan_04_add_anyway_flat_payload_reaches_the_live_route_and_flips_the_flag` — posts the exact flat shape to the exact hardcoded URL and asserts the flag flips.
- **Committed in:** `b655639` (Task 1 commit)

**2. [Rule 1 - Bug] `outstandingRequiredDeliverables()` eager-loads `deliverables` itself**
- **Found during:** Task 2, before writing tests
- **Issue:** `Project::deliverableState()` returns `null` for every key unless the `deliverables` relation is already eager-loaded (its own `relationLoaded()` guard, by design). `show()` eager-loads it, but the route-model-bound `$project` passed into `transition()` never goes through `show()` — it comes straight from Laravel's route-model binding. Without a fix, D-14's whole outstanding-check would silently never find anything Required (every `deliverableState()` call returns `null`, which never equals `STATE_REQUIRED`), making the warn branch permanently dead code that would have looked correct in review but never fired in production.
- **Fix:** `outstandingRequiredDeliverables()` calls `$project->loadMissing('deliverables')` as its first line.
- **Files modified:** `app/Http/Controllers/ProjectController.php`
- **Verification:** `ProjectCompletionTest::test_completing_with_outstanding_required_deliverable_warns_and_does_not_advance` — would fail (no warning flashed) without this fix. Confirmed by temporarily reverting the `loadMissing()` line during implementation and observing the test fail before re-adding it.
- **Committed in:** `c74797a` (Task 2 commit)

**3. [Rule 2 - Missing critical functionality] Added the missing `session('warning')` banner block**
- **Found during:** Task 2, while verifying the D-14 UX end-to-end
- **Issue:** `layouts/app.blade.php` defines `.alert-banner--warning` CSS but has no `@if(session('warning'))` block anywhere in the codebase to render it — confirmed by grep (only match was the `confirm_incomplete` hidden input I had just added). Without this, `transition()`'s D-14 warning would be flashed to the session and never displayed: the user would see the page reload with no visible explanation, and the hidden `confirm_incomplete` field would silently flip to `1` for their next click — meaning they'd complete the project with missing deliverables without ever having been shown what was outstanding. This directly contradicts D-14's stated requirement ("lists what is outstanding and asks for confirmation").
- **Fix:** Added a `session('warning')` banner block mirroring the existing success/error banner shape, using the pre-existing (previously unused) `.alert-banner--warning` CSS class.
- **Files modified:** `resources/views/layouts/app.blade.php`
- **Verification:** Blade compile check passes; `ProjectCompletionTest::test_completing_with_outstanding_required_deliverable_warns_and_does_not_advance` asserts `session('warning')` contains the outstanding label text (`assertStringContainsString('RAMS', session('warning'))`), proving the message content is correct even though the HTTP-test layer doesn't render Blade — this is a controller-side proof, and the banner-rendering fix was verified separately via the Blade compile check plus manual code review of the exact same `@if` shape used by the two adjacent, already-working banners.
- **Committed in:** `c74797a` (Task 2 commit)

**4. [Rule 1 - Bug] Narrowed Plan 04's `test_programming_never_appears_on_the_page`**
- **Found during:** the full `Project|Health|Transition|Deliverable` targeted-suite run after Task 2
- **Issue:** Plan 04 (commit `9812c48`) shipped a test asserting the literal string `"Programming"` never appears anywhere on the project show page (`assertDontSee('Programming')`), documenting D-05 ("flag only, no tab, no generator"). This plan's Task 1 — required by both D-04 ("nine selectable deliverables" explicitly lists Programming) and this plan's own brief ("all 9 deliverable states must be settable") — legitimately renders the word "Programming" as a form-row label in the new deliverables edit form. The two requirements were never actually in conflict (D-05 means "no tab," not "the word must never appear anywhere"), but the test's literal scope was.
- **Fix:** Renamed to `test_programming_never_appears_as_a_tab` and narrowed the assertion to the exact tab-label markup the render loop emits (`ws-tab__label">Programming`), which is what D-05 actually guarantees — no tab-strip entry, no count pill, no click target.
- **Files modified:** `tests/Feature/Projects/ProjectTabStripTest.php`
- **Verification:** Full targeted suite (`Project|Health|Transition|Deliverable`) went from 1 genuine failure + the 1 known-intentional failure back to just the 1 known-intentional failure after this fix.
- **Committed in:** `a1361ed` (own atomic commit, separate from Task 1/2 — a same-session regression found by running the full suite, not part of either task's own scope)
