# Phase 260822-esf Plan 8: Quote-Import Deliverables Interstitial (D-15/D-16) Summary

**A genuinely new page — `quote-import.deliverables-step` — sits between review and confirm: `review.blade.php`'s form now posts there instead of straight to confirm, the interstitial pre-fills RAMS/Worksheet/Survey to Not required when the quote has no `services`-category line (D-15), and `QuoteImportService::confirm()` writes the submitted checklist through `ProjectDeliverablesService::setInitialStates()` strictly before Plan 02's Hook 1 reads deliverable state to decide its D-11 auto-advance target.**

## Accomplishments

- **The interstitial is a real, distinct page — not a fieldset, not a modal.** `php artisan route:list --name=quote-import` shows `POST quote-import/{package}/deliverables-step` sitting between `quote-import.review` (GET) and `quote-import.confirm` (POST), routed to a dedicated `QuoteImportController::deliverablesStep()` action rendering a dedicated `quote-import/deliverables.blade.php` view.
- `review.blade.php`'s confirm form now posts to the interstitial (button relabelled "Continue"); the interstitial's own form is what finally posts to `quote-import.confirm` (button carries the original "Confirm & Open Project" label, since it is now the true final step). The 7 review fields (`name`, `ref`, `client_name`, `site_address`, `works_description`, `project_id`, `new_project`) are re-validated by `deliverablesStep()` and carried forward as hidden inputs — no session storage needed for a single-shot wizard step.
- D-15 defaults computed server-side in `deliverablesStep()`: `$hasServiceLine` checks `equipment_list` for any row with `category === 'services'` (confirmed live at `EquipmentCategoryClassifier.php:210-266` — this bucket collapses install/labour/commissioning/RAMS/site-survey SKU tokens into ONE category, no finer granularity exists). When false, Site Survey/RAMS/Worksheet default to `not_required`; when true, they default to `not_yet_decided` — never `required`, since the classifier signal supports no positive "definitely required" read. Every other deliverable (O&M, Cable Schedule, Install Programme, Drawings, Snagging, Programming) always defaults to `not_yet_decided`.
- `QuoteImportController::confirm()`'s validation array gains `deliverables` (`array:` + `Rule::in()` 3-state enum, mirroring Plan 07's `updateDeliverables()` shape exactly) and passes it through the single existing `$this->service->confirm(...)` call site at line ~172 as a new named argument.
- `QuoteImportService::confirm()` gains a 4th `array $deliverables = []` parameter and constructor-injects `ProjectDeliverablesService` (matching the class's existing all-constructor-injection style rather than the plan's `app()` fallback — no direct `new QuoteImportService(...)` call site exists anywhere in the codebase, confirmed by grep, so the added dependency resolves safely everywhere). The write happens via `setInitialStates()` immediately after the package-update transaction and immediately BEFORE Plan 02's Hook 1 block, followed by `$confirmed->project->unsetRelation('deliverables')` — required because Hook 1's `loadMissing('deliverables')` is a no-op if the relation is already cached from earlier in the same request.

## D-15's `services` signal — held up, but it is coarse and that is the whole point

Confirmed live (not assumed) at `app/Services/Imports/EquipmentCategoryClassifier.php:210-266`: install/labour/commissioning/RAMS/site-survey SKU tokens all collapse into ONE `services` category. This supports exactly the distinction D-15 names — "RAMS, Worksheet and Survey default off together when there is no services line" — and nothing finer. There is no signal in this data that could distinguish "needs RAMS but not a survey" or vice versa; the implementation does not invent one. When a services line IS present, the three keys default to `not_yet_decided`, never `required` — the classifier's presence signal only tells you work is happening, not which of the three specific deliverables it implies, so defaulting to `required` would be inventing a positive claim the data doesn't support. This is exactly what the plan's `<interfaces>` section specified and what `DeliverableImportDefaultsTest::test_services_line_present_defaults_survey_rams_worksheet_to_not_yet_decided` pins.

## Decisions Made

- **Every deliverables write from this flow is audited as `ACTION_IMPORT_DEFAULT`**, regardless of whether the submitted value matches the computed default or was changed by the user on the interstitial page. The plan explicitly offered this as "Claude's call which is simpler to implement correctly" — distinguishing "accepted the default" from "changed away from the default" per-key would require diffing the submitted payload against the just-computed `$defaults` array inside `confirm()` (which doesn't currently receive `$defaults`, only the final submitted states), adding a second parameter and a per-key branch for marginal audit-trail value. `ACTION_IMPORT_DEFAULT` correctly and honestly describes "this state was set as part of the import-confirm flow" either way; the `before_snapshot`/`after_snapshot` on every audit row (from `ProjectDeliverablesService::setState()`, Plan 01) still shows exactly what value was written.
- `deliverablesStep()` is POST-only (no separate GET view + redirect pair). It validates the same 7 fields `confirm()` validates and renders the interstitial directly in the same request/response cycle. This avoids needing session storage for fields that already round-trip cleanly as hidden inputs on the rendered form, matching the plan's own `<interfaces>` guidance ("avoids a second round-trip and avoids needing session storage").
- Constructor-injected `ProjectDeliverablesService` into `QuoteImportService` rather than using the plan's offered `app()` helper fallback. The class already uses 100% constructor-promoted readonly properties for its 3 existing dependencies; matching that style was straightforward once confirmed (by grep) that no call site anywhere in the codebase or test suite directly instantiates `QuoteImportService` with `new` — every resolution goes through the container, so the added constructor parameter is safe.
