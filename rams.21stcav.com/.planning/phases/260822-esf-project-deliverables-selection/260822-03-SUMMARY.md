## Explicit Proof in Both Directions

**Direction 1 — not-required produces no red/amber:**
- `test_green_when_rams_not_required_and_engineering_with_no_rams` — engineering status, zero RAMS documents, RAMS marked `not_required` → green, not the "No approved RAMS in engineering" red.
- `test_green_when_survey_not_required_and_overdue` — survey_pending, 20 days overdue, zero submissions, Site Survey marked `not_required` → asserted NOT red, NOT the "Survey overdue" reason. (It IS amber via the separate, untouched "Stage duration > 7 days" rule — see Decisions above for why that is correct and out of scope for D-12.)

**Direction 2 — a genuinely-required missing deliverable still produces red (proved by breaking the guard and watching tests fail, then restoring):**

1. Temporarily replaced `isExplicitlyNotRequired()`'s body with `return true;` (i.e. every deliverable treated as not-required, unconditionally).
2. Re-ran `--filter=ProjectHealthServiceTest`: **2 tests failed** — `test_red_when_engineering_no_approved_rams` (expected `red`, got `green`) and `test_red_when_survey_overdue_no_submission` (expected `red`, got `amber`). This proves the existing RED tests genuinely depend on the guard evaluating false for required deliverables — not just documenting intent.
3. Restored the exact original implementation (`return $project->deliverableState($key) === ProjectDeliverable::STATE_NOT_REQUIRED;`).
4. `git diff --stat app/Services/ProjectHealthService.php` showed **zero diff** from the committed state — confirmed byte-for-byte restoration.
5. Re-ran `--filter=ProjectHealthServiceTest`: 15/15 passing again.

**The guard fails closed.** A deliverable with no row, or a row in `required`/`not_yet_decided` state, is never treated as not-required — only an explicit `not_required` row suppresses the RED rule.

## Grace Period

**7 days**, stored as `ProjectHealthService::DELIVERABLE_DECISION_GRACE_DAYS` (`app/Services/ProjectHealthService.php:130`) — a named class constant, not an inline magic number. Anchored to this file's own pre-existing "Stage duration > 7 days" amber threshold (`:72`), the only precedent value in the codebase for "how long before an unattended thing becomes worth flagging" (per CONTEXT.md D-13's explicit instruction that no other value has any basis in the source material). Kept as a separate constant from the pre-existing rule's inline `7` rather than sharing one, so the two thresholds can diverge independently in future without coupling them.
