## 1. RUN `npm run build`. THIS IS THE ONE THAT WILL BITE YOU.

`resources/css/cockpit.css` is a **Vite entry** (`vite.config.js:32`).

**This phase's layout is entirely in that file.** The inline drawer's position, the one-column and
then two-column `.cav-layout` grid, the new `.cav-activity` panel and its 1024px collapse are all
CSS. The Blade changes on their own are markup with nothing to style it.

> **Deploying without `npm run build` ships the new markup against the old stylesheet — the rows
> will not collapse, the drawer will not sit beneath its row, and the page will look BROKEN rather
> than merely unchanged.**

That is the difference that matters. A missing build here does not produce "the old page"; it
produces a page nobody has ever seen, and the first person to open it will reasonably conclude the
phase shipped badly.

```
npm run build
```

Do it **before** anyone is asked to look at the page — including before checkpoint step 2 of
`46.3-04-PLAN.md`.

## 2. `php artisan view:clear` — the safe habit, not a hard requirement this time

Blade components were **ADDED** this phase (`x-cockpit.activity-panel`), not deleted, and a compiled
view cache that predates an addition simply recompiles. So the usual delete-a-component trap does
not apply here.

Clear it anyway. It costs nothing and this phase edits `cockpit.blade.php`, `panel.blade.php` and
`module-row.blade.php`.

```
php artisan view:clear
```

## 4. Nothing else

- **No migration.** No table was created, altered or dropped. No column was added.
- **No queue restart needed.** No job class changed; no job payload shape changed.
- **No config change.** `config/cockpit.php` is untouched; `COCKPIT_ENABLED` still gates the page.
- **No dependency change.** No `npm install`, no `composer require`. `npm run build` is a BUILD of
  sources already in the repo — it installs nothing. If a deploy ever demands an install for this
  phase, something is wrong: stop and check.
- **No new route.** The drawer, the collapse and the way back are all query-string state on the
  existing `projects.cockpit` route.

## 5. This repo's own deploy traps that still apply

- **Deploy as `stcav`, NOT as `root`.** Running the deploy as root leaves root-owned files in the
  tree and the next `stcav` deploy fails on them.
- There are **two remotes** on this repo. Push to the one you meant.
- `RAMS_UNIFIED_COMPOSER` picks the live PDF template — unrelated to this phase, but it is the
  env flag that has caused "code-only stages break the site" before.

## 6. How to tell the deploy worked, in ten seconds

Open the cockpit for a real project:

1. Four module rows, and a **Recent activity panel on the right**. If Recent activity is stacked
   underneath at desktop width, the stylesheet is stale → step 1.
2. Click a row. The other three rows should **disappear** and the drawer should appear **directly
   underneath** the row you clicked. If all four rows are still there, the stylesheet is stale AND
   the Blade did not deploy — check both.
3. `Back to all modules` above the tab strip. If you cannot see it, the stylesheet is stale.
