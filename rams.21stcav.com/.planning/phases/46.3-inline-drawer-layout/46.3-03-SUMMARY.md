# Phase 46.3 Plan 03: Recent activity becomes its own panel — Summary

Recent activity left the module panel and became **its own right-hand panel, outside any module**,
filling the column the inline drawer vacated in wave 2. It renders on every page including the
bare one — the render it could never have had before, because it lived inside a panel that does
not exist until `?module=`. The feed was **moved, not rebuilt**: same collection, same presenter
method, same `x-cockpit.activity-row`, same empty sentence. The second `.cav-layout` track and the
`@media (max-width: 1024px)` block were restored **in the same commit**, as wave 2's retirement
instructed, and the sketch now records the D-09 and D-14 narrowings with both original wordings
intact.

## Task 1 — the move

**Proven RED before implementation** (`gate-46.ps1 -Filter CockpitPanelTest`, before any markup
changed): `Tests: 5 failed, 21 passed (445 assertions)` — all five new tests, with the clearest
red being the module panel still carrying the card:

```
  Not to contain: Recent activity
  at tests\Feature\Cockpit\CockpitPanelTest.php:503
```

The five tests, and why each is shaped as it is:

1. **`test_the_bare_cockpit_renders_exactly_one_recent_activity_panel()`** — the render the feed
   could never have. Project-level data that only appears once you have opened something is not
   project-level.
2. **`test_every_module_and_tab_renders_exactly_one_recent_activity_panel()`** — **counted**, not
   merely found. The failure a relocated assertion must catch is a page that renders the feed
   TWICE: once at page level, once from a panel that was never emptied.
3. **`test_the_activity_panel_is_identical_across_every_module_every_tab_and_the_bare_page()`** —
   **DL-03's second half, asserted for the first time.** "It shows the same entries whichever
   module is open" has been true since Phase 45 but was never assertable: until D-03 the feed had
   no position from which it COULD differ. It compares the **serialised subtree for equality**, not
   a count of entries, because a count passes on two different feeds of the same length. Its loop
   bound is `count(moduleMap()) * count(THREE_TABS)`, derived and asserted, never a literal. It
   also asserts the expected subtree contains both entries first, so the comparisons cannot be
   trivially true on an empty string.
4. **`test_no_module_panel_carries_the_recent_activity_feed()`** — the other half. It asserts the
   module panel IS present on each of the twelve renders before asserting it is clean, so a broken
   extraction cannot pass as a successful move.
5. **`test_the_activity_panel_renders_its_hint_when_the_project_has_no_activity()`** — an absent
   panel would read as a page fault, the same reasoning the not-required module row uses.

**The markup.** `resources/views/components/cockpit/activity-panel.blade.php` takes one prop and
renders the block verbatim — **including the docblock comment about why the feed is project-wide,
which travelled with it and is MORE relevant here, not less**: that comment always said the log has
no module column, and D-03 is the markup finally agreeing with it.

In `cockpit.blade.php` it renders as a **sibling of `.cav-modules` inside `.cav-layout`**,
unconditionally, outside the module `@foreach`. In `panel.blade.php` the card, the `activity` prop
and `$activity = $activity ?? collect();` are gone, each replaced by a comment naming where the
feed went and which decision moved it — the treatment the quick-actions block and the Returned tab
got. `:activity="$activity"` came off the invocation in the same commit: a prop wired to nothing is
the wiring-that-can-never-fire this file's own comments warn about.

**`$activity` was CONFIRMED unconditional rather than assumed.** The plan asked for the check.
`ProjectCockpitController:172` reads `$activity = $this->panelPresenter->activity($project);` — not
gated on `$moduleKey` the way `files()` and `notes()` are on the two lines above it, because
`activity()` never took a module. **No controller change was required and none was made.**

**The entry count is the presenter's.** `activity()` already caps at six. Blade adds no second
opinion, on the plan's own instruction — two caps for one number is how they drift.

**Class naming.** `.cav-activity` / `.cav-activity__head`, its own, **not** `.cav-panel__card` /
`.cav-panel__card-head`. It looks like one of the drawer's cards today and deliberately does not
share their selectors — the same refusal `.cav-pnote` made over `.cav-note`. Two unrelated things
on one class is how a later edit aimed at the drawer retones the activity feed. `cav-acts` and
`x-cockpit.activity-row` stay as they are; those are the feed's own and moved with it.

### CSS — three edits, and CockpitVisualTest after every one

The plan's instruction, and this wave's single most likely silent failure: a new grid track changes
the module column's width and containing context, and the stretched-link pairing fails with nothing
else going red.

| # | Edit | `CockpitVisualTest` |
|---|---|---|
| 1 | `.cav-layout` back to two tracks, `minmax(0, 1fr) 320px` | **11 passed (114 assertions)**, 9.57s |
| 2 | `.cav-activity` / `__head` added | **11 passed (114 assertions)**, 8.00s |
| 3 | the 1024px media block restored | **11 passed (114 assertions)**, 7.29s |

Green every time, including `test_the_whole_module_row_is_the_click_target_without_javascript()`.
**No anchor was given a `position` and `.cav-module`'s `position: relative` was not touched.** The
containing-block scan reads only rules whose selector ends in `.cav-module` or `.cav-module__open`;
`.cav-activity` is a **sibling of `.cav-modules`**, never an ancestor of a row, so it cannot reach
the overlay by construction rather than by luck.

**320px, not the old side panel's 360px** — the feed is six single-line entries and an avatar,
narrower than a tabbed panel needed, and the module list is the page's purpose so the reading
column keeps the extra 40px.

**Sticky: YES, and it is NOT the call 46.3-02 reversed.** That plan retired the DRAWER's
`position: sticky` because a sticky drawer detaches from the row it belongs to. This panel belongs
to no row: it is the project's own column, it is context for whatever is being read beside it, and
a drawer carrying a long document form is exactly the case where the feed would otherwise scroll
away. It occupies its own grid track, so it overlaps nothing, and it drops to `static` under
1024px with the column itself.

### THE MEDIA BLOCK, RESTORED IN THE SAME COMMIT

Wave 2 retired `@media (max-width: 1024px)` **by name**, quoted its two declarations and left the
instruction that this plan restore it **in the same commit as its second track, never after it**.
`c7082ea9` carries both. The regression that instruction prevents is silent: a two-column layout
that never collapses passes every test in this repo and is met by a human on a laptop.

**Only ONE of the two quoted declarations came back, deliberately.**
`.cav-layout { grid-template-columns: minmax(0, 1fr) }` is restored and doing real work again.
`.cav-panel { position: static }` is **not** — it became the base value when the drawer went inline
and it still is, so restating it would be a declaration that changes nothing, which is the very
reason wave 2 removed the block rather than narrowing it. What sits there instead is the new
panel's own un-sticking, `.cav-activity { position: static }`, which does change something.

**The activity column stacks BELOW the module list** at narrow widths — the rows are the page's
purpose and the feed is context. Source order gives that for free, so no `order` was introduced;
the rule says so, so the absence reads as a decision. **No fourth breakpoint was invented**: the
count is back to the three that existed before wave 2 — 1024 / 860 / 680.

**No hex reached a Blade file**, every new class is `cav-`-prefixed, every value is an existing
`--cav-*` token, and no Tailwind utility was used in the subtree.

⚠️ **A NEW CR-9 WRINKLE, AND IT IS THE DANGEROUS KIND.** When the harness moved a stalled run to
the background and the `php` processes were then killed, the harness reported the background task
as **"completed (exit code 0)"**. That exit code is the kill, not a green suite. **A stalled run
that is killed can present as a PASS.** The standing rule "never quote a backgrounded run as a gate
result" already covered it; this is the mechanism by which breaking it would have produced a
confidently false green. Recorded in the ledger.

Also confirmed: **all three stalls here had neither known trigger** — plain redirect, one
invocation per command, no pipe. That is further evidence for CR-9's own recorded finding that "it
is the pipe" is **falsified as a complete account**.
