# Phase 46.3 — Count ledger

Every count this phase moves, every assertion it retires, and every consequence it accepts rather
than papers over. Same shape and same house rule as `46.2-COUNT-LEDGER.md`: **a count moves BY NAME
with a reason and stays EXACT — never relaxed to `assertGreaterThanOrEqual`; an assertion is
RETIRED BY NAME with the decision cited — never deleted to make a red test pass.**

Opened by Plan 46.3-01 (wave 1). Plans 46.3-02, -03 and -04 append to it.

## Consequences recorded, not papered over

### CR-1 — D-04 was REVISED. The earlier reading is withdrawn, and the rejected option is named.

The user's words were **"strip 0 visits"**, said while looking at an empty project where the row
read `0 visits` — pure noise, and they were right about that.

Planning then found what a full strip would cost. The same slot renders `1 visit · reconstructed`
and `2 visits · 1 superseded`. `CockpitModulePresenter::visitPhrase()`'s own docblock calls it
**the page's at-rest disclosure slot**: with the panel closed it is the *only* place a backfilled or
superseded visit is disclosed without opening anything. Phase 45's **D-02** put it there precisely so
a PM would not read an **inferred** visit as a recorded fact — and there are **24 backfilled visits
on live**. A full strip would have deleted that warning along with the zero-noise.

Three options were put to the user:

1. **hide-at-zero** — suppress the phrase only when the count is zero;
2. **strip the visit phrase and show a document count instead** — move `site_survey` and `worksheet`
   from `COUNT_VISITS` to `COUNT_DOCUMENTS`;
3. **strip the visit phrase and show nothing**.

**The user chose option 1, hide-at-zero, on 2026-09-26.**

> **Option 2 — "strip and show a document count instead" — was CONSIDERED AND REJECTED.** Do not
> propose it again. It would have taken the disclosure slot away by a different route, and it would
> have required editing `MODULE_MAP`'s count modes and relations, which this phase treats as
> do-not-touch. `site_survey` and `worksheet` **stay on `COUNT_VISITS`**.

An earlier draft of Plan 46.3-01 proposed option 2. That draft is **withdrawn**, and the withdrawal
is written at the top of the plan's `<objective>` as well as here, because a plan and a ledger
disagreeing is worse than either being wrong alone.

### CR-2 — OPEN QUESTION: `0 documents` still renders on RAMS and O&M, deliberately.

The zero rule is scoped to the **visit phrase**, and only to it. `0 documents` still renders on the
RAMS and O&M rows.

That is not an oversight and it is not a half-finished job. The ruling names the visit phrase, and a
planner does not widen a user's decision on their behalf — especially not by deleting copy. It is
also not obviously the same case: `0 documents` on a document-creation tool arguably *is* the row's
state, whereas `0 visits` on a row whose visits are a by-product was noise.

**This is unresolved and must be ASKED, not decided here.** Plan 46.3-04's human checkpoint carries
the question: *does `0 documents` read as noise too, or as the row honestly reporting that nothing
has been generated yet?* Until the user answers, `0 documents` stands.

### CR-3 — The stretched-link assertion was widened BEFORE any layout moved, on purpose.

`.cav-module` is `position: relative`; `.cav-module__open::after` is `inset: 0`. Giving the anchor a
`position` of its own, or removing the row's, collapses the whole-row click target onto the 28px
chevron **with nothing else failing** — no test red, no error, no visual difference at rest. Quick
task `260920-rwc` established the trap; `cockpit.css` warns about it in three separate comment
blocks (`:393`, `:482`, `:1471`, `:1676`) precisely because prose was the only guard.

Waves 2 and 3 restructure this row. So wave 1 lands first and leaves them an assertion that already
bites, and the biting was **proved** rather than assumed: `position: absolute` was injected into the
`.cav-module__open` rule, the test went red, and the file was reverted byte-identical (sha256
compared before and after). An assertion that is green on arrival and green after the change tells
you nothing.

### CR-4 — Two assertions outside the plan's `files_modified` had to move (A-5, and the fence test).

`CockpitDocCreationEndToEndTest:279` asserted the old closed-state copy and is not in the plan's
file list. It was retargeted in the same commit as the relabel rather than left to fail, because the
house rule is that the commit which invalidates an assertion is the commit that moves it — and
because a red left for a later wave is a red someone else will be tempted to delete.

### CR-5 — A BLADE TRAP, PAID FOR AND WRITTEN DOWN: `@php` inside a Blade COMMENT still compiles.

The first version of the relabel carried an explanatory Blade comment reading *"see the `@php`
block"*. Blade compiled the directive **inside the comment**, emitted an unterminated `<?php`, and
every cockpit render 500'd with `ParseError: syntax error, unexpected token "endforeach"` pointing
at a compiled view 175 lines away from the edit. Thirteen tests went red at once and none of them
named the cause.

Blade comments are NOT inert. Do not write `@`-directive names in `{{-- --}}` prose in this repo.
The comment now says "the props block above" and says why.
