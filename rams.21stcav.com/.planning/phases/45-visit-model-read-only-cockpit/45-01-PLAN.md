Two gates, both of which must exist before any code in this phase is written.

1. Mint VIS-01..VIS-10 into `.planning/REQUIREMENTS.md` so every other plan's `requirements:`
   frontmatter points at something real.
2. **MEASURE** the InstallProgramme behaviour-preservation baseline by executing the test subset,
   and record the real numbers. `45-RESEARCH.md` counted 161 test methods **statically** and
   flagged this as assumption A1 — it was never run. A gate asserted against an unverified number
   is not a gate. Plans 45-04 and 45-08 re-assert against what this plan measures.

**This plan is the SOLE wave-1 plan, deliberately serialised.** Every other plan in the phase
depends on it. The reason is Task 2's own precondition: the baseline must be measured on a clean
tree before any Phase 45 code exists. If 45-02 (which lands the `visits` migration) or 45-03 (which
runs `npm install` + `npm run build`) ran concurrently, the measurement would be taken against an
unknown tree — every test in the subset uses `RefreshDatabase`, so a half-applied migration
corrupts the number, and that corrupted number is then re-asserted as a gate by 45-04 and 45-08.
The entire safety rail of the phase would rest on a figure measured against a moving target.
Serialising costs almost nothing: two document tasks and one test run.

Purpose: this is the phase's safety rail. D-06's constraint ("if the split cannot be made
behaviour-preserving, stop and raise it") is only enforceable against a measured number.
Output: a `Group VIS` block in REQUIREMENTS.md, and `45-BASELINE.md` holding the executed result.
</objective>
