# Plan 45-15 — Visual polish to match sketch 004

## Why this plan exists

The user compared the built page against their design and said it is *"a lot less colourful and tier 1 than my example."* They are right, and the cause is a specification error rather than an execution one.

Plan 45-09 derived the cockpit token set from the app's own palette and banned hex literals in Blade. That guaranteed accessibility and stopped the cockpit retoning the rest of the app — both still non-negotiable. But the app's palette has **one** accent, and sketch 004 uses **eight distinct module hues**. The colour the design depends on was never in the token set, so it could not be built.

This plan adds what was missing. It changes no behaviour, no data and no route.

## What the design actually shows

Read `.planning/sketches/004-delivery-cockpit/delivery-cockpit.png` before starting. The gap is:

1. **Per-module tinted icon tiles** — a soft-tinted rounded square behind each module's glyph, a different hue per module:
   Site survey blue · First fix and install mint/green · Programme and commissioning purple ·
   RAMS blue · Drawings green · O&M manual indigo · Cable schedule amber · Programming navy (dark
   tile, light glyph) · Snagging — choose a hue distinct from the other eight.
2. **The active module row** carries a left accent bar, a faint tinted background, and a filled dark button; inactive rows have outlined buttons.
3. **KPI cards** each carry their own tinted icon tile — green check, blue calendar, blue document — with a small grey label above a bold value, and a progress bar on the documents card.
4. **Stage chips** are tinted pills (blue, amber), not grey.
5. **A donut progress ring** in the panel, blue arc on a light track, percentage centred.
6. **Coloured avatars** in the activity feed — initials on a filled circle, a different hue per person.
7. **Softer surfaces** — white cards on a faint blue-grey canvas, ~10px radius, a very light border and a barely-there shadow.

## Constraints that do not move

- **Every hue is a token declared on `.cav-brand`.** No hex literal in any Blade file — there is a test. Nothing is added to `layouts/app.blade.php`'s `:root`.
- **The three protected files stay byte-identical to `4abd2b24`.** `FlagOffBehaviourUnchangedTest` asserts by sha256; a mismatch is a STOP, never a hash to refresh.
- **The read-only fence stays intact.** "Open drawer" is an `<a>` styled as a button and must remain one — the fence bans `<button`. Do not add Quick actions, an Actions dropdown or a "…" menu; those are Phase 46/48.
- **Contrast floors.** Glyphs on tinted tiles are non-text marks: 3:1. All chip text, labels and values are text: 4.5:1. Reproduce the ledger for every new pairing in the token file's docblock, as 45-09 did. **Opacity may never be applied to an element containing small text** — `#767676` at 0.7 blends to 3.03:1 and fails.
- **State is never carried by colour alone.** A module's hue is decoration and identity, never status. Status stays in the chip, which carries a glyph shape and its state in words. A greyscale render must still be readable.
- **No JavaScript, no Alpine.** The donut ring is CSS (`conic-gradient`) or inline SVG, not a chart library.

## Tasks

### Task 1 — Extend the token set with the design's hues

Add to `resources/css/cav-tokens.css`, on `.cav-brand`:

- A **tint/ink pair per module hue** (`--cav-hue-survey-bg` / `--cav-hue-survey-fg`, and so on for the nine). Tints are the pale tile background; inks are the glyph colour and must clear 3:1 on their own tint.
- **Surface tokens** the design needs: card background, canvas, hairline border, and one soft shadow.
- **Avatar hues** — at least four, cycled deterministically by user id so the same person keeps the same colour.
- Keep every existing token. Source values from the app's palette where one fits; where the design needs a hue the app does not have, pick one and record the contrast figure beside it.

Verify: `grep -c -- "--cav-" resources/css/cav-tokens.css` rises; the only selector in the file is still `.cav-brand`; the three protected files are unchanged.

### Task 2 — Apply the hues and lift the surfaces

- `CockpitModulePresenter` supplies a **hue key per module** alongside the existing data. Blade reads the key; it does not decide the colour and it does not hardcode the list.
- `icon.blade.php` renders the glyph inside its tinted tile.
- `module-row.blade.php` gains the active-row treatment (left bar, tint, filled link-button) and the outlined variant for the rest.
- `kpi-card.blade.php` gains its tinted tile, label/value hierarchy and the progress bar.
- `status-chip.blade.php` becomes a tinted pill, keeping its glyph shape and its state in words.
- `activity-row.blade.php` gains the coloured initials avatar.
- `panel.blade.php` gains the donut ring, the tinted header tile, and the underlined active tab.
- `cockpit.blade.php` and `cockpit.css` carry the card, canvas, radius and shadow treatment.

Verify: `php -l` over compiled views after `view:clear`; no hex literal in any Blade file; the full cockpit suite green.

### Task 3 — Pin it

Add `tests/Feature/Cockpit/CockpitVisualTest.php`:

- Every one of the nine modules renders a **distinct** hue class — iterate the presenter, assert nine unique values, so a later module added without a hue fails rather than silently sharing one.
- No raw hex (`#rrggbb`) appears anywhere in the rendered cockpit region.
- The status chip still carries its glyph and its state in words — the greyscale guarantee, re-asserted here because this plan touches the chip.
- "Open drawer" is an `<a>`, not a `<button>`.

Then re-run: the full cockpit suite, the 12-path D-06 baseline (`>= 159 passed AND 0 failed`, never equality against 161), and the three sha256 pins.

## Out of scope

Create visit · Add note · Upload files · the Actions dropdown · the "…" overflow menu. All writes, all Phase 46/48. The design shows them; this plan does not build them.
