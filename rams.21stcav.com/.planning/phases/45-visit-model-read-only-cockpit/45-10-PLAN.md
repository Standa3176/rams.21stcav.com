<task type="checkpoint:decision" gate="blocking">
  <decision>What does "Documents n of 9 complete" count, and does the module list show eight rows or nine?</decision>
  <context>
    D-12 specifies a KPI card reading "Documents 1 of 9 complete" with a percentage bar. D-11
    specifies EIGHT module rows. Those two numbers disagree, and the disagreement is not cosmetic.

    The only "nine" in this codebase is `ProjectDeliverable::ALL_KEYS`, documented at
    `ProjectDeliverable.php:14` as "the single canonical nine-item deliverable vocabulary". Map it
    against D-11's eight modules and exactly one key is unaccounted for: **snagging**.

    Two further facts bear on this:
      - `ProjectDeliverable`'s states are `required` / `not_required` / `not_yet_decided`. There is
        no "complete" state on it. A completeness count must therefore be derived from the nine
        section `pip` values that `CockpitSectionPresenter` already produces — `pip === 'done'` is
        the only defensible reading of "complete" in this codebase today.
      - `Visit::TYPE_SNAG` exists, and Plan 45-07 established the invariant that every visit type
        reaches exactly one drawer, so no visit is ever rendered nowhere. Dropping the snagging row
        breaks that invariant: a snag visit would exist in the database and appear on no screen.

    Whatever is chosen, the denominator must be the number of module rows actually rendered. A
    hardcoded 9 above a list of 8 is the fabricated-denominator failure this checkpoint exists to
    prevent.
  </context>
  <options>
    <option id="nine-modules">
      <name>Render nine module rows — add Snagging to D-11's eight — and keep "n of 9"</name>
      <pros>The KPI's 9 and the list agree. The 45-07 invariant holds: a snag visit has a home. The canonical nine-item vocabulary stays the single source, so the cockpit and the deliverables screen keep naming the same things.</pros>
      <cons>Deviates from D-11's stated eight, so the page has one more row than the accepted design image.</cons>
    </option>
    <option id="eight-modules">
      <name>Render D-11's eight rows exactly and change the KPI to "n of 8"</name>
      <pros>Matches the accepted design image row-for-row.</pros>
      <cons>Snag visits become unreachable from the cockpit — a record that exists and is shown nowhere. Diverges from the canonical nine-item vocabulary, so cockpit and deliverables screen disagree about what a project's deliverables are.</cons>
    </option>
    <option id="eight-plus-fold">
      <name>Render eight rows, folding snagging into "First fix and install", KPI reads "n of 8"</name>
      <pros>Matches the design's eight rows and keeps snag visits visible.</pros>
      <cons>A snag is not a first fix; the fold makes the row's count phrase ("1 visit") ambiguous about what kind of visit it counts.</cons>
    </option>
  </options>
  <resume-signal>Select: nine-modules, eight-modules, or eight-plus-fold</resume-signal>
</task>

  <files>app/Support/Cockpit/CockpitModulePresenter.php, tests/Unit/Cockpit/CockpitModulePresenterTest.php</files>
  <behavior>
    - `modules(Project): Collection` returns the rows the checkpoint settled, in D-11's order:
      Site survey · First fix and install · Programme and commissioning · RAMS · Drawings ·
      O&M manual · Cable schedule · Programming (plus Snagging in the position the checkpoint set,
      if `nine-modules` was chosen).
    - Each row is an array with keys: `key`, `title`, `description`, `icon`, `chip`, `count`,
      `section` (the `CockpitSectionPresenter` array it was built from).
    - `chip` is one of exactly three values — `not-started`, `in-progress`, `on-file` (D-10) — and
      is a pure TRANSLATION of the section's existing `pip`: `waiting` -> not-started,
      `attention` -> in-progress, `done` -> on-file. No new derivation, no second opinion. A
      section whose `not_required` is true reports chip `not-started` and a count phrase saying so,
      because that is what `CockpitSectionPresenter` already decided.
    - `count` is a phrase, pluralised, matching D-10's vocabulary: `0 visits` / `1 visit` /
      `2 visits`; `1 document`; `0 tasks`; `0 files`. The noun is fixed per module by its `kind`,
      not guessed per render: visit-kind modules count visits, document-kind modules count their
      documents, `install_programme` counts install tasks.
    - **Programming counts nothing.** There is no Programming model, no generator and no storage
      type — `ProjectDeliverable.php:14-26` says so and forbids building one. Its `count` is the
      empty string and the row renders its chip alone. It must NOT report "0 files", which would
      claim a file store exists.
    - `progress(Project, string $moduleKey): ?array` returns `['completed' => int, 'total' => int,
      'percent' => int]` for a module whose visits can be counted — completed = visits with
      `status === Visit::STATUS_COMPLETED`, total = all visits on that module. Returns **null**
      when the module has no visits at all, so the panel can omit the ring rather than draw a
      0-of-0 circle that reads as "nothing done" when the truth is "nothing planned".
    - Every `Visit::TYPES` value maps to exactly one module. Assert this as a data test over the
      constant, not over a hand-written list, so adding a seventh visit type later fails loudly.
    - Calling `modules()` and `progress()` changes no row count in `visits`, `site_surveys`,
      `worksheets`, `install_programmes` or `install_records`.
  </behavior>
