## THE RULING ON THE NO-JAVASCRIPT SIDE PANEL — decided at plan time, do not re-open

**The panel is server-rendered state driven by the query string. Plain `<a href>` links. No JS.**

    /projects/{project}/cockpit                      -> panel closed (the at-rest page)
    /projects/{project}/cockpit?module=worksheet     -> panel open, Overview tab
    /projects/{project}/cockpit?module=worksheet&tab=files
    the panel's close control is an <a href> back to the bare cockpit URL

Why the two alternatives were rejected, so nobody re-litigates this mid-build:

  - **Alpine** is loaded globally by the layout, so it is technically available. It is ruled OUT.
    `CockpitReadOnlyFenceTest::test_rows_are_static_and_nothing_is_wired_to_a_handler` asserts the
    region contains no `x-on:`, no `@click`, no `wire:` and no `aria-expanded`. An `x-data` panel
    would either trip that test or require weakening it, and weakening a fence to fit a design is
    exactly the failure the fence exists to catch. **RULING: Alpine directives count as script
    inside the cockpit region for the purposes of this phase.** Plan 45-13 adds `x-data`, `x-show`
    and `x-init` to the banned list so the ruling is enforced rather than remembered.
  - **CSS-only disclosure** cannot carry eight modules x three tabs. The checkbox-hack form needs
    `<input>`, which the fence bans outright; the `:target` form puts state in a fragment the
    server never sees, which cannot drive the Files tab's document list.

What the query-string form buys, beyond compliance: every panel state is bookmarkable and
shareable, the back button works, and it degrades to nothing when JS is off. What it costs: a full
page load per open. That is acceptable for a read-only page and is the honest trade for a phase
that ships no JS. When Phase 46 introduces writes it may progressively enhance this with Alpine —
at that point the fence is being deliberately retired, which is a decision with an owner.
