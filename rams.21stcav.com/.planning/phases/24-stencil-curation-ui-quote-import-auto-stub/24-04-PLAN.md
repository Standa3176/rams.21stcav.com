<objective>
Ship the `admin.device-stencils.preview` endpoint and the server-side XML-to-SVG rendering step it requires — settling both open questions RESEARCH.md left for the planner.

**Settled decision 1 (Research Open Question 3 — which builder does preview use):** The preview endpoint uses `AutoGenericStencilGenerator::build()` ONLY, never `DrawIoBuilderService`. Rationale, adopted from the researcher's own recommendation: the edit screen curates ONE stencil's ports in isolation — no project, no other devices, no cables. `DrawIoBuilderService::build(Project $project)` requires a `Project`; synthesising a throwaway single-device project fixture just to preview one shape is unjustified complexity for a screen whose scope never exceeds a single `<shape>`. D-02's "AutoGenericStencilGenerator for stub shapes / DrawIoBuilderService for full render" clause is read as describing which generator produced a stencil's *original* XML historically, not which one renders *this preview* — the preview always regenerates via `AutoGenericStencilGenerator`, matching exactly what Plan 24-05's Save action will also do (see Accepted Trade-off below).

**Settled decision 2 (Research Open Question 1 — preview response shape):** D-16 is locked: the endpoint returns rendered SVG. No PHP-side "mxGraph XML to SVG" renderer exists anywhere in this codebase (`DrawIoSpikeController::exportSvg` only *persists* a client-submitted SVG string from the draw.io JS embed's postMessage export — it performs zero server-side rendering). Since `AutoGenericStencilGenerator` emits a small, fully self-authored, BOUNDED stencil-XML grammar (roundrect/rect/line/text/fillcolor/strokecolor/fontcolor/fontsize/fontstyle/strokewidth/dashed/strokealpha/fill/fillstroke/stroke/connections — nothing else, per Plan 24-01's corrected grammar), this plan ships a purpose-built `StencilXmlToSvgRenderer` that walks that bounded grammar and emits equivalent `<svg>` primitives directly, in PHP, with zero new packages (RESEARCH.md's Standard Stack confirms none are needed). `<connections>` constraints are skipped in the SVG output — they carry no visual styling (Plan 24-01's task 3 note).

**Grammar note (plan-checker correction, 2026-08-13):** the real `mxgraph_xml` production renderer is genuine draw.io/mxGraph, and this file's `mxgraph_xml` is never rendered by any code in this repository except THIS preview approximation — `XtenAvLayoutEngine.php:65,174` base64-embeds it as `shape=stencil(...)` for the real draw.io engine to render. Because this project's own `AutoGenericStencilGenerator` (Plan 24-01) expresses provisional-rail dashing/opacity via the REAL mxGraph stencil state-element grammar — `<dashed dashed="1"/>` / `<dashed dashed="0"/>` and `<strokealpha alpha="0.6"/>` / `<strokealpha alpha="1"/>`, set once and applied to a batch of bare `<line x1 y1 x2 y2/>` elements before a single `<stroke/>` commits them —

⚠ **Grammar ground truth is the vendored engine, NOT the seed pack.** Verified directly in `public/vendor/drawio/mxgraph/src/shape/mxStencil.js`: line 895 reads `canvas.setDashed(node.getAttribute('dashed') == '1')` — the attribute is named `dashed`, not `value`; lines 948-951 read `canvas.setAlpha(node.getAttribute('alpha'))` and the class docblock (lines 90-91) defines alpha as **1.0 fully opaque to 0.0 fully transparent** — a 0-1 fraction, never a 0-100 percentage. `mxSvgCanvas2D.js:1137` writes `stroke-opacity` as `s.alpha * s.strokeAlpha` with no conversion, so a percentage value would serialise as `stroke-opacity="60"` and be clamped to fully opaque. **No file in `resources/data/device-stencils-seed/` contains `dashed` or `strokealpha` at all** — the seed pack cannot validate these two elements, which is exactly why two earlier attempts at this grammar were wrong. Do not re-derive from it. THIS renderer's parser must track that SAME state as it walks the tree, never look for a `dashed="1"` attribute directly on a `<line>` element (no such attribute exists in real mxGraph stencil XML, and Plan 24-01 never emits one).

**Accepted trade-off (documented, not a silent gap):** Because Save (Plan 24-05) also always regenerates `mxgraph_xml` via `AutoGenericStencilGenerator` to preserve Pitfall 2's port_id-to-constraint parity, editing ports on an ALREADY engineer-curated stencil (e.g. a hand-built seed-pack entry) will replace its bespoke visual with the standard template shape — ports/constraints stay correct, only decorative styling reverts to defaults. This is accepted because: (a) it keeps the parity guarantee absolute with one XML writer; (b) hand-built visual polish is out of this phase's bounded scope (CONTEXT.md's Criterion 5 caps delivery at the top-10 fill); (c) no "regenerate curated XML while preserving hand-authored art" engine exists or is being built here.

Purpose: makes D-02's "the preview must not be able to lie" promise concrete — the SVG shown is generated from mxgraph_xml built by the exact same code path Save uses, and the preview's dashed/muted rendering matches what the REAL production draw.io engine will show for the SAME XML (this is exactly why Plan 24-01's grammar correction matters — an invented attribute would make the two engines disagree).
Output: `StencilXmlToSvgRenderer` service, `DeviceStencilController::preview()` action, `admin.device-stencils.preview` route.
