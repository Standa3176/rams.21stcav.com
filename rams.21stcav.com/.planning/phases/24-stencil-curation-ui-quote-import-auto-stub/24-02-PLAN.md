<interfaces>
Three call sites carry THREE DIFFERENT equipment-line shapes — this is the central design constraint for this plan:

1. `ExtractQuoteJob::mergeParsedQuoteData()`'s `$parserEquipment` rows (used as `$extracted['equipment_list']`): keys `quantity, qty, part_number, part_no, name, description, area, location, item_type, category` — category IS one of the 8 canonical `EquipmentCategoryClassifier::CATEGORIES` values already. No `manufacturer`/`model` keys.

2. `QuoteWerksImportService::buildExtractedData()`'s `$equipment` rows: keys `quantity, qty, part_number, part_no, name, description, area, location, category, unit_price, total_price, manufacturer, data_source, confidence` — category already canonical (via injected `EquipmentCategoryClassifier`), manufacturer present.

3. `QuoteImportService::extract()` -> `QuoteExtractorService::extractFromPath()`'s `line_items` (renamed to `equipment_list` at `QuoteImportService.php:499`): keys `sku, qty, description` ONLY — no `part_number`, no `category`, no `manufacturer`. This is the shape `ReimportQuoteJob` produces via `completePendingReimport`.

`QuoteImportStencilStubber::stubFromEquipmentLines()` MUST normalise all three via `$line['part_number'] ?? $line['sku'] ?? ''` and `$line['name'] ?? $line['description'] ?? ''`, and MUST always run `EquipmentCategoryClassifier::classify()` (which short-circuits to the caller-supplied canonical category when present, and infers from text when absent) rather than trusting any one shape's `category` key directly.
</interfaces>
