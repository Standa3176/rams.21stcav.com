<objective>
Add one-survey-per-project enforcement: SurveyService detects existing surveys and supersedes them atomically, SiteSurveyController surfaces a confirmation block to engineers, and the internal create view renders the supersede UI.

Purpose: Without this plan, engineers can create multiple parallel surveys for the same project. Plan 02's whereNull('superseded_at') filter in ProjectDataService would then silently pick whichever survey is "latest" — the enforcement here ensures only one survey is ever active per project.

Output: SurveyService with supersede logic, controller with detection+confirmation flow, Blade view with .alert-warning supersede block.
</objective>

  <threat id="T-03-06" severity="high">
    <description>An engineer could attempt to POST to store() with supersede=1 for a project they do not own, superseding another user's survey by crafting a form submission with a foreign project_id.</description>
    <mitigation>SiteSurveyController::create() and store() already use auth()->id() scoping for $projects list. The store() call delegates to SurveyService::create() which creates the new survey with $user->id as the owner. Additionally, the project_id field is validated against exists:projects,id in validateSurvey(). To fully close this: add an ownership check in store() before allowing supersede — verify that the project_id belongs to auth()->user() or that the user is an admin before proceeding with supersede. Add: abort_unless(!$data['project_id'] || \App\Models\Project::where('id', $data['project_id'])->where('user_id', auth()->id())->exists() || auth()->user()->isAdmin(), 403);</mitigation>
  </threat>
  <threat id="T-03-07" severity="medium">
    <description>The supersede confirmation is a single-click action via a form submit button — there is no additional confirmation step beyond the inline warning block already displayed. If the page is submitted programmatically (e.g., CSRF replay), an existing survey could be superseded.</description>
    <mitigation>The standard Laravel CSRF token on the form (already present via @csrf in the Blade template) prevents CSRF replay attacks. The supersede flow requires: (1) a CSRF-valid POST, (2) authenticated session, (3) ownership of the project. The inline warning block with two explicit buttons satisfies the UI-SPEC requirement for a second-click confirmation pattern without a modal.</mitigation>
  </threat>
