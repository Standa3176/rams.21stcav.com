## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| DB row -> future consumer | `labour_resources.email`/`phone` are genuine PII-adjacent staff contact fields; this plan only lays the schema, but the shape it picks (plain columns, no encryption-at-rest layer exists anywhere else in this app either) is what every later plan inherits |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-44-01 | Information Disclosure | `labour_resources.email` / `.phone` columns | accept | No new encryption-at-rest layer is introduced here — matches the rest of the schema (e.g. `users.email`); the real mitigation is access-path control, not storage encryption. Plans 44-02 (admin-only routes) and 44-04 (privacy guard test) own that control. |
| T-44-02 | Information Disclosure | Any future direct serialization of `LabourResource` (`toArray()`/`toJson()`) | mitigate | `toClientSafeArray()` is the sanctioned safe accessor this plan ships; Plan 44-04 proves it exists and returns exactly `id`+`name`, giving Phase 45/46 authors a documented safe path instead of ad-hoc field-picking. |
| T-44-03 | Tampering | `roles` json column | accept | No app code trusts `roles` for authorisation — it is a descriptive/display field only, never gates access. A malformed value at worst mis-displays a badge. |
