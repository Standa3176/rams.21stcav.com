  <name>Task 1: LabourResourceSelect component</name>
  <files>app/View/Components/LabourResourceSelect.php, resources/views/components/labour-resource-select.blade.php</files>
  <behavior>
    - Rendering `<x-labour-resource-select />` with two active resources and one INACTIVE resource
      in the database lists the two active names and never the inactive one's name — proves the
      component queries `LabourResource::active()` itself rather than accepting an
      already-filtered collection from the caller (the structural guarantee, not a convention).
    - `<x-labour-resource-select :selected="[$activeOne->id]" />` pre-selects that option
      (`selected` attribute present on that `<option>`) and no other.
    - `<x-labour-resource-select name="visit_resource_ids" />` renders `name="visit_resource_ids[]"`
      on the `<select multiple>` element (array-style name so multiple selections post correctly);
      the default name (no prop given) is `resource_ids`.
    - The rendered HTML contains each active resource's `name` but never its `email` or `phone`
      value, even when a resource is seeded WITH email/phone populated — defence-in-depth for D-04
      on a surface that is not currently client-facing but should never casually become a leak
      point either.
    - Options are ordered by name ascending.
  </behavior>
  <action>
    Create `App\View\Components\LabourResourceSelect extends \Illuminate\View\Component` with a
    constructor accepting `public array $selected = []` and `public string $name =
    'resource_ids'`. `render(): View` returns
    `view('components.labour-resource-select', ['resources' =>
    LabourResource::active()->orderBy('name')->get()])` — the query lives in the component, not in
    the Blade file, so it cannot be bypassed by a caller forgetting to filter.

    Create `resources/views/components/labour-resource-select.blade.php`: a
    `<select multiple name="{{ $name }}[]" id="...">` looping `$resources`, each
    `<option value="{{ $r->id }}" @selected(in_array($r->id, $selected))>{{ $r->name }}</option>`.
    Option label is `$r->name` ONLY — no interpolation of email/phone/roles into the visible label
    text. A `data-roles="{{ implode(',', $r->roles) }}"` attribute on the option is acceptable
    (roles are not PII) if useful for later JS grouping, but is not required — do not add JS
    behaviour this phase does not need.
  </action>
