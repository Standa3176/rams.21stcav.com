# Phase 46.8 Plan 01: Comms Room Out Of The RAMS Data Feed Summary

Removed comms-room access from the RAMS hazard/PPE data builder, the project-context attacher, the DOCX and both PDF RAMS renderers, and the worksheet's own "Site Logistics" cover-page block, per 46.8 D-02's explicit override of 46.5 D-03 — while leaving `comms_room_access_status`/`comms_room_access_notes` completely untouched on disk, exactly as 46.8 D-03 requires.

## What Was Built

**Task 1 — the data layer never attaches or re-introduces the two keys.**

- `ProjectContextBuilder::build()` no longer puts `comms_room_access_status`/`comms_room_access_notes` into `context['site_logistics']` when reading the `SiteSurvey` model. The other five keys (`parking_restraints`, `distance_from_base_miles`, `distance_from_base_notes`, `site_access_notes`, `delivery_routes`) are untouched.
- `RamsDataBuilderService::normalise()` strips the same two keys from its `site_logistics` array literal unconditionally — even if a stale caller's `$sl` input still carries them, the normalised output never does. This is defence in depth: the attacher above already never sends them, but the normaliser doesn't rely on that.

**Task 2 — the four generation-time renderers never print the row, and the two now-dead `$commsLabels` maps are deleted.**

- `DocxBuilderService::buildScopeOfWorks()` — the live RAMS DOCX section (`$hasSiteLog` OR-guard dropped from 7 terms to 5; the `comms_room_access_status`/`_notes` row-builder `if` block removed; `$commsLabels` deleted — confirmed it had no other reader in the file).
- `pdf/rams.blade.php` and `pdf/rams-v2.blade.php` — identical removal applied to each file's own `$hasSiteLog` guard, row block and `$commsLabels` map.
- `WorksheetDocxService` — both sites updated together: `loadSiteLogistics()` no longer returns the two keys (and the "all N keys empty" comment corrected from 7 to 5), and the render block's comms-room `if` + its local `$commsLabels` map are removed.

None of these files any longer contain a functional reference to `comms_room_access_status`/`comms_room_access_notes` — only explanatory comments noting the deliberate exclusion remain (verified by grep after every edit).

**New test — `tests/Feature/Rams/CommsRoomRemovedFromRamsFeedTest.php`** (7 tests, all RED-then-GREEN verified):

1. `ProjectContextBuilder::build()` never attaches either key (control: other 5 keys still populated).
2. `RamsDataBuilderService::assemble()` never re-introduces either key even when a stale caller injects them directly into the `site_logistics` sub-array before calling `normalise()`.
3. RAMS DOCX (`DocxBuilderService::build()`) omits the "Comms room access" row and the sentinel text/label while keeping every other populated row.
4. RAMS DOCX with every site-logistics field empty still omits the whole "Site Logistics & Access" heading — the guard's remaining 5 terms still correctly detect "nothing to show".
5. `pdf/rams.blade.php` rendered directly via `view()` omits the row.
6. `pdf/rams-v2.blade.php` rendered directly via `view()` (with its `dto`/`theme` dependencies) omits the row.
7. `WorksheetDocxService::build()` against a real `SiteSurvey` row omits the row from the generated worksheet DOCX, AND re-fetches the `SiteSurvey` before/after generation to prove `comms_room_access_status`/`comms_room_access_notes` are byte-identical — D-03's "column stays on disk" proven, not merely asserted.

## Deviations from Plan

None — plan executed exactly as written. One scope clarification worth recording: `RamsBuilderService::buildFromDraft()` has a third site_logistics path (`reviewed_data['site_logistics']` can override the survey-derived block — see `app/Services/RamsBuilderService.php:265-272`) feeding into `$data` before it reaches `DocxBuilderService`/the blades. This file is **not** in this plan's `files_modified` and was **not** touched. It does not need to be: the consumption-layer guard removal in `DocxBuilderService` and both blades blocks the comms-room row regardless of which upstream path populated `$data['site_logistics']` — proven directly by Task 2's tests, which inject the comms-room keys straight into `generated_data['site_logistics']` (bypassing the data-builder layer entirely) and confirm the row still never renders.

## Non-Vacuity Proof

- **RED confirmed**: the six production files were reverted to pre-plan state via `git checkout --` on exactly those six paths (no `git stash`, no `git clean`), the new test was run, and 6 of 7 tests failed with the literal `"Comms room access"` row and `SENTINEL-COMMS` text present in the rendered output. The 7th test (`test_rams_docx_with_all_site_logistics_empty_still_omits_the_whole_section`) correctly passed in both states — it is a no-regression control, not a test of the removal itself.
- **GREEN confirmed**: the saved patch was reapplied (`git apply`) and all 7 tests passed again (53 assertions).
- **Rendered output, not a variable check**: every assertion reads generated DOCX `word/document.xml` (via `ZipArchive`) or rendered Blade HTML, never a PHP array.
- **D-03 proven, not asserted**: the `SiteSurvey` row is re-fetched from the database before and after the worksheet DOCX is generated, and `comms_room_access_status`/`comms_room_access_notes` are asserted byte-identical.
