<domain>
## Phase Boundary

The survey engineer link captures what an engineer actually needs on site, and stops asking for
what they do not. **Nine changes**, requested 2026-10-09 after using the deployed link
(HEAD `b282c79d`) on a real job.

**In scope:** five changes to **Site info** (on the engineer link *and* the office create form),
four to the **room page**, and the downstream decoupling the comms-room removal forces.

**Out of scope:** the worksheet engineer link (a different page); the cockpit; the snag lifecycle

the `comms_room` column** — see D-02.

<decisions>
## Implementation Decisions

The user, verbatim, 2026-10-09:

> "ON THe engineer link > site info , remove comms room question, distance from base, route note
> from app and link . add Other notesfield to capture anyother info. on room page , remote voice
> note . on the radio button Access issues , working at height if select open box to capture notes
> on what the issues are and working height shows the working height selection which are currently
> lower on the page and site requirements. under cablke route picture and note field to capture
> notes on route. on site info , check if RAMS needed."

- **D-01:** **Site info loses three questions and gains two things.** Remove the **comms room**
  question, **distance from base**, and the **route / travel note** — from the engineer link **and**
  the office create form. Add a free-text **"Other notes"** field for anything else. And **show
  whether RAMS are required**: wire the existing `ProjectDeliverable` KEY_RAMS tick (46.5 D-05 —
  read `Project::deliverableState()`, the guarded reader), **do not rebuild it**.

- **D-02:** ⚠️ **COMMS ROOM IS REMOVED EVERYWHERE, INCLUDING THE RAMS DATA FEED. THIS OVERRIDES
  PHASE 46.5 D-03, AND THE COST WAS STATED BEFORE THE USER CHOSE IT.**

  Measured 2026-10-09: `comms_room` is read by `app/Services/RamsDataBuilderService.php`,
  `app/Services/ProjectContext/ProjectContextBuilder.php` and `app/Services/DocxBuilderService.php`,
  as well as `SurveyService`, `SurveyController`, `PublicSurveyController`, `SiteSurveyController`
  and `SiteSurvey`.

  **46.5 D-03 explicitly recorded keeping it, as a safety matter:** an installing engineer inherits
  the surveyor's comms-room access notes through the survey→install carry-forward, and it renders in
  the site-survey Word document (quick task `260926-s7k`). That phase called removing it *"a safety
  regression"*.

  That concern was put to the user with the consumers named. They chose **full removal**, including
  the RAMS feed. **Recorded here so a later reader sees a decision, not an oversight.** The practical
  consequence to expect: RAMS and the survey Word document no longer receive comms-room information,
  and an installing engineer no longer inherits those access notes.

- **D-03:** ⚠️ **REMOVE THE CAPTURE AND THE CONSUMPTION — DO NOT DROP THE COLUMN.** Existing
  `comms_room` values on past surveys **must survive on disk** (SCOPE.md D-05: nothing is deleted).
  **No migration drops or nulls it.** A destructive purge of historical data is a separate,
  irreversible decision the user has **not** made. If a plan concludes a migration is needed, **STOP
  and report** rather than writing one.

- **D-04:** **The room page loses voice note.** Confirmed with the user — *"remote voice note"* was a
  typo for *remove*, consistent with the three removals in the same sentence. It currently has 5
  references in `resources/views/surveys/show.blade.php`.

- **D-05:** **Two radio buttons reveal follow-ups when selected.**
  - **Access issues** → reveal a notes box capturing **what the issues are**.
  - **Working at height** → reveal the **working-height selection**, which currently sits lower down
    the page, **together with site requirements**.

  ⚠️ Since 46.6 each room is **one scrolling tab** with the eight former wizard steps as labelled
  sections, so *"currently lower on the page"* means further down that single room section — not a
  later wizard step. The point is to put the follow-up **next to the question that triggers it**.

- **D-06:** **Cable route gains a photo and a notes field** for notes on the route.

- **D-07:** ⚠️ **ADDED 2026-10-09, AND IT REVERSES AN EARLIER REMOVAL** — read it before acting on
  the `delivery_routes` note in the code insights below. **"Delivery Routes" is NOT removed. It is
  RENAMED to "Site delivery info" and re-purposed**, in the user's words:

  > "change delivery routes to site delivery info to capture process that we need to follow to
  > deliver hardware to site"

  So the surveyor records **the process for getting hardware onto site** — booking, access windows,
  who to call, loading bay, lift restrictions — rather than a route.

  ⚠️ **This reverses the rationale of 2026-09-27**, when the user had Delivery Routes removed from
  the office create form saying *"this is a survey not install with kit deleivery"*. They now want
  the opposite on the engineer link, and it is coherent: a survey is exactly where you learn how a
  delivery will have to work. **Do not "correct" this back.**

  ⚠️ **RELABEL IN THE UI ONLY — DO NOT RENAME THE COLUMN.** The binding stays
  `engineerFeedbackSite.delivery_routes` and the stored key stays as it is. Renaming it would be a
  migration, which D-03 forbids, and would strand every existing value. The label and the prompt
  change; the storage does not.

  **The existing placeholder is already right for the new meaning** — *"e.g. Deliveries to bay 4,
  7am-11am; contact Site Manager 0207… 1h before arrival"* (seen on the live page). It describes a
  process, not a route. **Keep it, or sharpen it; do not replace it with something about routes.**

  **Open, and worth asking rather than assuming:** whether "Site delivery info" should also return
  to the **office create form**, where it was removed in September. The user named only the engineer
  link. Default to the link alone and surface the question.

- **D-08:** ⚠️ **ANSWERED BY THE USER 2026-10-10 — THE OFFICE EDIT SCREEN LOSES COMMS ROOM TOO.**
  Planning found a **THIRD** comms-room surface that neither this context nor the research listed:
  a live **“Comms Room Access”** `<select>` at `resources/views/site-survey/edit.blade.php:165-168`,
  with its own rules in `SiteSurveyController::validateSurvey()`, on the authenticated
  `site-surveys.edit` screen reached from `projects/show.blade.php`. The planner **deliberately left
  it alone** rather than widen scope to a surface the user never named — the right call.

  **Put to the user, who chose to remove it.** Rationale, in their decision: once the engineer link,
  the office create form and the RAMS/Word output all stop using comms room, a lone dropdown that
  still saves to a column **nothing reads** is worse than no field at all — someone fills it in
  believing it matters.

  ⚠️ **D-03 still governs: remove the CAPTURE and the VALIDATION RULE, never the column.** Stored
  values on past surveys survive. Still no migration.

- **D-09:** **ANSWERED BY THE USER 2026-10-10 — “Site delivery info” stays ENGINEER-LINK ONLY.**
  It does **not** return to the office create form, where Delivery Routes was removed on 2026-09-27.
  Rationale: the surveyor is the person on site discovering how a delivery will actually have to
  work, and the create form was deliberately shortened. **Closes D-07's open question.**

### Claude's Discretion

<specifics>
## Specific Ideas

- **Judge it on a phone, one-handed, in a plant room with bad signal.** That is the only place this
  page is used, and this phase exists *because* the user took the deployed link to a real job.
- The standing criterion all milestone is **"simple to use"**; an earlier design was rejected as
  **"scary"**. Every change here either removes a question or puts an answer next to its question —
  both should make the page shorter, not longer.
- ⚠️ **Non-vacuity is the house rule and it has been broken repeatedly** — five vacuous assertions in
  46.x, a live stoppage on 2026-09-30 because a test asserted the safe half, and 46.7 shipping a
  **green suite while this very page stayed an 8-step wizard**. **Render every state claimed.** For
  the removals, assert the question is **absent from rendered output**, not merely that a variable
  changed. For D-05, render **both** radio states. For D-02, prove RAMS and the Word document still
  **generate** without comms-room input, and prove a past survey's stored value is **still on disk**.

</specifics>
