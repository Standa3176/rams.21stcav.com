# Phase 46.8: Survey Capture Refinements From Site Use - Research

**Researched:** 2026-10-10
**Domain:** Laravel/Blade/Alpine.js engineer-facing capture form + its RAMS/DOCX consumers
**Confidence:** HIGH (every claim below is grep/read-verified against the working tree; nothing
in this document is from training-data guesswork about this codebase)

## Summary

Nine capture-field changes to `resources/views/surveys/show.blade.php` (the engineer link) and,
for three of them, `app/Support/Cockpit/CockpitDocumentFormPresenter.php` (the office create
form). None requires a migration — every target column/JSON-key already exists. The real cost
is **not** schema; it is (a) the number of call sites each removed field touches, and (b) two
behaviours this research found that the CONTEXT did not have: a genuine **hazard/PPE/
access-equipment scoring dependency** on the room page's "Working Height" field, and a **pre-
existing value-vocabulary bug** in that same scoring path that this phase must not silently
"fix" while relocating the control.

**Primary recommendation:** Treat D-02 (comms-room full removal) as a mechanical, well-bounded
edit across ~9 files plus 3 test files that must be updated BY NAME, not deleted. Treat D-05 (the
two conditional reveals) as higher-stakes than it looks, because "Working Height" is not display
text — it drives `RiskTemplateResolverService::resolveFromProjectContext()`, which seeds the
survey-sourced RAMS hazard register. Do not touch the value vocabulary while moving the control.

## A. The comms-room decoupling (D-02)

### A.1 — What each consumer actually DOES with `comms_room`

All three downstream services treat `comms_room_access_status`/`comms_room_access_notes` as
**display text only** — there is no hazard, control, risk score, or template-selection logic keyed
on it anywhere in the codebase (confirmed by grepping every `hazard`/`risk_score`-bearing service
in `app/Services/Rams/` and `app/Services/*.php` for the string `comms`; the only hits are label
maps and a docx-prose sentence in `config/rams_tier1.php:441` describing cabling work generally,
unrelated to a specific survey's comms-room value).

- **`RamsDataBuilderService.php:538-546`** — `normalise()` rewrites `site_logistics` into exactly
  seven keys (comms room status/notes, parking, distance miles/notes, site access, delivery
  routes) as strict-typed scalars so the Blade renderer never sees a missing key. Pure pass-through.
- **`ProjectContext/ProjectContextBuilder.php:87-97`** — `buildFromSurvey()` attaches
  `context['site_logistics']` straight off `SiteSurvey` model columns (not from `survey_data` JSON).
  Pure pass-through.
- **`DocxBuilderService.php:676-737`** — `buildSummaryHeader()`'s "Site Logistics & Access" block.
  `$hasSiteLog` is a boolean OR across all seven fields (`:681-689`); if ALL seven are empty, the
  **entire section is omitted** — no heading, no empty table, nothing printed. Each row is only
  added `if (! empty(...))` (`:704-725`). **Verdict: it is purely printed as text.** No hazard, no
  score, no branching template choice.
- There is also a matching render in `resources/views/pdf/rams.blade.php:795-829` and
  `resources/views/pdf/rams-v2.blade.php:857-891` (the two RAMS PDF Blades) — same `$hasSiteLog`
  guard pattern, same "text only" verdict. **`rams-v2.blade.php` is not the live renderer** per
  `WorkingAtHeightResidualScoreTest`'s own docblock ("the live primary renderer"
  is `DocxBuilderService::buildRiskAssessment()`), but both exist and both must stay consistent if
  touched.

**Answer to research question A.1: comms room is printed text everywhere. Removing it changes
cosmetics (a row disappears from three documents and the engineer-link form), not RAMS safety
output.** Contrast this directly with D-05's "Working Height" field — see section B below, which
**does** feed hazard selection, and is the genuinely higher-risk item in this phase.

### A.2 — What happens when the value is absent

Already safe on every consumer, by construction, for a BLANK value (new surveys after removal):

- `RamsDataBuilderService.php:539-540` — `(string) ($sl['comms_room_access_status'] ?? '')` — casts
  to `''`, never null, never throws.
- `ProjectContextBuilder.php:90-91` — same `?? ''` pattern directly off the model attribute.
- `DocxBuilderService.php:681-689` / both RAMS PDF Blades — `$hasSiteLog` OR-guard; an all-empty
  `site_logistics` array (once comms room is permanently blank) simply omits two fewer rows than
  today; if `parking_restraints`/`site_access_notes`/`delivery_routes` are still populated, the
  section still renders, just without a "Comms room access" row. **No empty heading, no stray
  label, no exception** — this was already engineered for optional fields.
- `SurveyCarryForward.php:148-176` — `forSurvey()` only pushes a row into its output list `if
  ($value !== '')` (`:148-153`); `commsRoomAccess()` returns `''` when both status and notes are
  empty (`:168-176`), so the row silently disappears from the install hand-off. Already safe.

For a PAST survey (existing non-empty value, capture removed but column NOT dropped per D-03):
every one of the above paths still reads the live column value and will **continue to render it**
on old records, since nothing in this phase proposes touching the column or its read path in these
four files — only the *engineer-facing capture* (the form on `surveys/show.blade.php`) and, per
D-02, the *RAMS feed specifically* are to be decoupled. This is the one place D-02's "including the
RAMS feed" instruction has a real decision to make: if `RamsDataBuilderService`/
`ProjectContextBuilder` stop reading the column (the literal ask), **old surveys with real
comms-room data on disk will stop appearing in NEW RAMS/DOCX generations run after this ships**,
even though the column still holds the value. That is a direct, intended consequence of D-02 and
should be stated plainly to whoever reviews the plan, since it is easy to read D-03 ("don't lose
the data") as implying the data keeps flowing to every consumer — it does not; D-03 only protects
the column, not every reader of it.

### A.4 — Does survey→install carry-forward actually read it? (verifying/correcting 46.5 D-03's claim)

**Confirmed, not merely claimed.** `app/Support/Visits/SurveyCarryForward.php`:

- `FIELDS` (`:74-83`) lists `comms_room_access_status => 'Comms room access'` as one of nine

  parking, comms-room access and notes, delivery routes, site access notes, site risks and H&S

**Verdict: 46.5 D-03's claim is CORRECT, not stale.** An installing engineer genuinely does inherit
the surveyor's comms-room access notes today, through this exact class, rendered on the worksheet

not "the claim was wrong," it is **"the claim was right, and `SurveyCarryForward.php` plus

`tests/Unit/Visits/SurveyCarryForwardTest.php`, `tests/Feature/Worksheets/SurveyCarryForwardOnEngineerLinkTest.php`,
and `tests/Feature/Cockpit/CockpitSurveyFeedbackFieldsTest.php`.

## B. The two conditional reveals (D-05)

### B.5 — Where Access Issues / Working at Height live today, and what "lower on the page" means

Both are `<x-survey.toggle-field>` **switches** (`resources/views/components/survey/toggle-field.blade.php`)
— **not literal radio buttons**, despite the user's informal phrasing. They live in section
`#sv-step-2` ("2. Quick Capture", `show.blade.php:1140-1151`):

```blade
<x-survey.toggle-field field="access_issues"     label="Access Issues"     icon="🚧"
                       parent="rooms[currentRoomIdx]._ui" />
<x-survey.toggle-field field="working_at_height" label="Working at Height" icon="🪜"
                       parent="rooms[currentRoomIdx]._ui" />
```

Both are UI-only `_ui.*` booleans (not the canonical risk data; `working_at_height` is sent to the
server as normalization CONTEXT on step 6 save but not persisted itself — see
`buildStepPayload()` case 6 comment, `:2411-2413`: "server clears access_equipment from risks when
false, then discards the field").

**"The working height selection… currently lower on the page"** = section `#sv-step-6` ("6. Access
& H&S", `:1693-1717`), a **button-group** (not a radio either) bound to the CANONICAL
`rooms[currentRoomIdx].risks[0].working_height`:

```blade
@foreach (['under_2m' => 'Under 2m', '2_to_4m' => '2–4m', 'over_4m' => '4m+'] as $val => $display)
    <button type="button" @click="rooms[currentRoomIdx].risks[0].working_height = '{{ $val }}'" ...>
```

Sections 2 and 6 are two of the eight "flattened" labelled sections the 46.6 room page now renders
on one scrolling tab (confirmed per CONTEXT's own note) — so "lower on the page" is literally true:
section 6 sits roughly 600 lines after section 2 in the same scroll.

**"Site requirements" does not exist as a bound field anywhere on this page** (confirmed: zero
hits for `site_requirement*` across the repo). The nearest candidates, none an exact match:

- `Access Equipment Required` (`:1719-1744`) — already conditionally revealed (see B.6) and
  bound to `rooms[currentRoomIdx].risks[0].access_equipment`. Plausible: "shows... working height
  selection... and site requirements" could mean "working height AND access equipment," both of
  which are H&S/safety-equipment requirements for the site visit.
- The `#sv-step-7` "Constraints" section (`:1778-1796`: Obstructions, Noise Restrictions, Client
  Constraints, Programme Constraints) — UI-only, explicitly NOT stored in the final survey record
  per the page's own disclaimer at `:1798-1801`. A weaker candidate since it is explicitly ephemeral.
- `engineerFeedbackSite.site_access_notes` — a SITE-LEVEL field (Site Logistics card), not a
  per-room one, so it cannot be "revealed" by a per-room toggle without a cross-tab UI wiring that
  does not exist today.

**Recommendation: ask the user to point at the exact element**, rather than guessing. The CONTEXT
itself flagged this gap; this research did not resolve it because no bound field named
"requirements" exists to resolve it to.

### B.6 — Existing conditional-reveal idiom (follow this, don't invent one)

The exact pattern D-05 should copy already exists in the same room page, one level below the
"Working Height" buttons:

```blade
{{--
    Access equipment — only shown when working_at_height is true (UI-only _ui field).
    Server also enforces: clears access_equipment when working_at_height=false.
--}}
<div class="bg-white rounded-2xl p-4 shadow-sm"
     x-show="rooms[currentRoomIdx]?._ui?.working_at_height">
    <p class="text-sm font-semibold text-gray-700 mb-2.5">Access Equipment Required</p>
    ...
</div>
```
`show.blade.php:1719-1724`

This is Alpine `x-show` (not `x-if`), driven by the `_ui.working_at_height` toggle — a
cross-section binding, since the toggle itself lives in section 2 and this reveal lives in section
6. That precedent directly supports D-05's "put the follow-up next to the question" requirement:
since 46.6 flattened every section into one scroll, an `x-show` reveal CAN sit immediately after the
"Working at Height" toggle in section 2 and read the same `_ui.working_at_height` value that
section 6's reveal already reads — both can co-exist, reading the same source of truth, with no
duplication of state.

⚠ **Failure mode to design against, confirmed as already-handled once, elsewhere on this page:**
the quoted comment above ("Server also enforces: clears access_equipment when working_at_height=
false") is the server-side half of exactly the trap the CONTEXT warns about. Confirm in
`normalizeStepContribution()` / step-6 handling (`SurveyController.php`, search
`access_equipment`) that any NEW revealed field (e.g. an Access Issues notes box) gets the same
clear-on-toggle-off treatment, or a note typed while the toggle was on will survive being toggled
off and silently resubmit with the toggle's "false" state — exactly the corruption bug D-05 warns
against, and exactly the bug the existing `access_equipment` field already defends against.

### Research question — radio vs toggle discrepancy

CONTEXT describes "the radio button Access issues, working at height." **Both are switches
(`<x-survey.toggle-field>`), not `<input type=radio>`.** There are no survey-link radio-style
controls at all in the relevant markup — `<select>` is explicitly forbidden
(`CockpitReadOnlyFenceTest::FORBIDDEN_MARKUP` — though that fence applies to the office cockpit, not
this page) and this page itself uses toggle switches and button-groups, never native radios, for
every binary/enum choice examined. Not a blocker — just confirm the planner's language matches the
real markup so a task doesn't literally search for `type="radio"` and fail to find anything.

## C. The additive bits

### C.7 — Cable route (D-06): location and existing photo-capture mechanics

**The per-route notes field ALREADY EXISTS.** `show.blade.php:1372-1435` ("(c) Cable Routes," inside
section 4 "Infrastructure," new-install path) renders a repeatable list bound to
`rooms[currentRoomIdx].engineer_feedback.cable_routes` — category, length, from, to, and a
**Notes** field per row (`:1421-1426`, `x-model="row.notes"`, 500 chars, placeholder "e.g. Through
ceiling void, drop into floor box"). Server-side `normalizeCableRoutes()`
(`SurveyController.php:1143-1160`) already round-trips this exact shape.

A SEPARATE, category-level photo uploader for `cable_routes` **also already exists**, in the
Photos section (`#sv-step-3`, `:1164`): `<x-survey.photo-upload category="cable_routes" label="Cable
Routes" icon="🔌" />`. This is a GALLERY for the whole room's cable-route photos, not tied to an
individual route row.

**So D-06's literal ask ("picture and note field to capture notes on route") is already
~80% satisfied by existing code.** The only genuinely new piece is giving the "(c) Cable Routes"
infrastructure card (the per-route list) its own camera affordance, rather than relying on the
separate step-3 gallery. The planner's real decision is narrower than the CONTEXT implies: either
(a) do nothing and just point the user at the existing step-3 "Cable Routes" photo category plus
the existing per-row notes field, or (b) add a photo slot inside each cable-route row.

**Can a new photo slot be added without touching the frozen IndexedDB schema? Yes, confirmed, and
cheaply.** Read `resources/views/partials/_engineer-offline-capture.blade.php:76-93`: the IndexedDB
store `pending_uploads` is `{ keyPath: 'id', autoIncrement: true }` with one index on `capturedAt`
only (`:92-93`). `category` is **not a schema-level field or index at all** — it only ever exists
as a string inside the generic `fields` object passed to `enqueue()`
(`show.blade.php:2631,2635`: `fields: { category }`). `uploadPhoto()`
(`show.blade.php:2601-2636`) reads `category` from `input.dataset.category` — any string works, no
enum. Server-side, `PublicSurveyController.php:447` validates photo `category` as
`['nullable', 'string', 'max:50']` — **not a closed list**. **Conclusion: a brand-new category
string (e.g. `cable_route_detail`) — or reuse of the existing `cable_routes` category — requires
zero IndexedDB schema version bump and zero backend validation change.** The existing
`<x-survey.photo-upload>` component is directly reusable as-is; this is the cleanest D-06
implementation path.

### C.8 — "Other notes" (D-01): reusable storage, confirmed zero-migration

`SiteSurvey` already has a **site-level, general-purpose free-text column**: `general_notes`
(`app/Models/SiteSurvey.php:30`, in `$fillable`). It is:
- Already validated at `PublicSurveyController.php:725` and `SiteSurveyController.php:221,781`
  (`nullable|string|max:3000`).
- Already consumed and printed by `SiteSurveyDocxService.php:89,170` as a "General Notes" row.
- Already part of `SurveyCarryForward::FIELDS['general_notes'] => "Surveyor's notes"`
  (`SurveyCarryForward.php:81`) — it already rides the install hand-off.

**It is NOT currently bound on the engineer link's Site Logistics card.** The card's autosave
(`show.blade.php:2046-2053`, `siteFields` array) and the server's
`normalizeEngineerFeedbackSite()` / `writeEngineerFeedbackSiteToColumns()`
(`SurveyController.php:1114-1127,1234-1245`) both handle exactly the SEVEN engineer-feedback-site
keys (comms room ×2, parking, distance ×2, site access, delivery routes) — `general_notes` is a
sibling column on the same model, written through a DIFFERENT path (the "legacy header fields,"
per `PublicSurveyController.php:682-684`'s own comment).

**Confirmed: D-01's "Other notes" needs NO migration — `general_notes` already exists, already
flows to the DOCX and the carry-forward.** The implementation is purely additive code:
1. Add a textarea in Site Logistics bound to a new Alpine key (e.g.

### C.9 — "RAMS required" (D-01): the guarded reader, its states, and a real gap

`Project::deliverableState(string $key): ?string` (`app/Models/Project.php:488-497`) is the
"guarded reader" CONTEXT points to. Its contract:

- **Returns `null`** if the `deliverables` relation is NOT eager-loaded on the `Project` instance
  (`relationLoaded('deliverables')` check, `:490-492`) — by design, so it never fires an N+1 and is
  safely callable even from a DB-less unit test.
- Otherwise returns one of three string constants from `ProjectDeliverable`:
  `STATE_REQUIRED` ('required'), `STATE_NOT_REQUIRED` ('not_required'), or
  `STATE_NOT_YET_DECIDED` ('not_yet_decided') — the last one is the DEFAULT for a project with no
  row yet for that key (`:496`), not an error state.

**Gap found: the engineer link does NOT currently eager-load `project.deliverables`.**
`SurveyController::show()` calls `$survey->load(['rooms.photos', 'rooms.questions',
'project.referenceFiles', 'project.latestPackage'])` (`SurveyController.php:65`) — no
`project.deliverables`. Calling `$survey->project->deliverableState(ProjectDeliverable::KEY_RAMS)`
on this page TODAY would return `null` for every project, regardless of the actual tick, because
the relation was never loaded. **This is a required one-line addition to the `load()` call**
(`'project.deliverables'`), not optional — without it, "RAMS required" cannot be implemented as a
read-only display; it would always render as "unknown."

**Existing precedent for the three-state display** (editable, for contrast — this page should be
read-only): `resources/views/projects/show.blade.php:2015-2050` renders the same three states as a
labelled radio trio ("Required" / "Not required" / "Not yet decided") for every deliverable key,
office-side. For the engineer link, a simple read-only equivalent — e.g. a label plus one of three
short strings, or a coloured badge using the three existing state constants directly (never
re-deriving the vocabulary) — follows the same mapping without inventing new wording.

### D.13 — The RAMS-scoring dependency this research found (not in CONTEXT)

`RiskTemplateResolverService::resolveFromProjectContext()` (`app/Services/RiskTemplateResolverService.php:367-407`)

## Common Pitfalls

### Pitfall 1: Treating D-02 as "edit four files" when it is closer to ten
**What goes wrong:** Following only CONTEXT's named consumer list omits `SurveyCarryForward.php`
and its render site, leaving the install-engineer's worksheet link showing comms-room data that the
office RAMS/DOCX pipeline no longer receives — an inconsistency, not a safety win.
**Why it happens:** The CONTEXT's consumer list was accurate for the office-generation path but was
compiled before someone traced the carry-forward path specifically.
**How to avoid:** Use the full file list in this document's "A.3" and "Consumers the CONTEXT did not
name" tables as the task checklist, not the CONTEXT's list alone.
**Warning signs:** A test in `SurveyCarryForwardTest` or `SurveyCarryForwardOnEngineerLinkTest`
still green after the office-side removal — that means the carry-forward was never touched.

### Pitfall 2: "Distance from base" collapsing into one removal when it is two bindings
**What goes wrong:** CONTEXT states items 2 and 3 ("distance from base", "route note") collapse
into ONE removal because the "Route / Travel Notes" label binds to `distance_from_base_notes`. This
is true for THAT pairing, but there is a THIRD, separate binding in the same card:
`distance_from_base_miles`, labelled "Distance from Base (miles)," a number input
(`show.blade.php:433-440`), with its own consumer entries everywhere `distance_from_base_notes`
appears. If only `distance_from_base_notes` is removed and `distance_from_base_miles` is left in
place, D-01's intent ("distance from base" as one of three removed questions) is only half done.
**How to avoid:** Treat this as THREE bindings to remove (`comms_room_access_status`,
`comms_room_access_notes` as one pair; `distance_from_base_miles`; `distance_from_base_notes`), not
two, unless the user confirms the miles input should stay.
**Warning signs:** A numeric "Distance from Base (miles)" input still rendering after the textarea
above/below it was removed.

### Pitfall 3: Fixing the working-height vocabulary mismatch while moving its UI
**What goes wrong:** Noticing the `over_2m`/`2_to_4m`/`over_4m` mismatch while relocating the reveal
and "helpfully" renaming the button values to match the resolver — silently changing which RAMS
hazards get generated for every future survey, with no user sign-off on a safety-content change.
**Why it happens:** The defect sits right next to the markup this phase is told to move.
**How to avoid:** Move the markup and its binding verbatim; flag the mismatch to the user as a
separate, explicit finding (this document already does so).
**Warning signs:** A diff that touches the `@foreach` value list in the Working Height button-group
beyond pure relocation.

### Pitfall 4: Adding "Other notes" without wiring the step-0 autosave write path
**What goes wrong:** Binding a new textarea to `engineerFeedbackSite.general_notes` and seeding it
from `$survey->general_notes`, but forgetting that `normalizeEngineerFeedbackSite()` /
`writeEngineerFeedbackSiteToColumns()` only know about the existing seven keys — the new field would
autosave client-side (optimistically) but the server would silently drop it every time, because
`stepSave()` step 0 never writes a `general_notes` key to the model.
**How to avoid:** The four-point implementation list in C.8 above must all land together.
**Warning signs:** Typing in the new field, reloading the page, and finding it empty again.

### Pitfall 5: Reading `deliverableState()` without eager-loading `deliverables`
**What goes wrong:** Calling `$survey->project->deliverableState(ProjectDeliverable::KEY_RAMS)` from
the Blade without adding `'project.deliverables'` to `SurveyController::show()`'s `load()` call —
the method returns `null` unconditionally (by design, to avoid an N+1), so "RAMS required" renders
as permanently unknown/blank regardless of the actual project state.
**How to avoid:** Add `'project.deliverables'` to the existing `load([...])` array at
`SurveyController.php:65`.
**Warning signs:** The RAMS-required badge always showing the same (presumably "not yet decided" or
blank) value no matter which project is open.
