# Phase 46.2 Plan 05: The document form in the panel Summary

**The cockpit can generate documents again.** Between `0a02b6dc` (46.2-03) and `74edf35a` the page
had no way to produce anything at all — the per-row Generate control went with
`quick-actions.blade.php`. It is back, in the panel, rendered from `DOCUMENT_FIELD_MAP` by **one
Blade component that names no document**, and it now covers four documents instead of the three the
retired control offered.

## What a PM can now do, and in which formats

| Row | Enterable fields | Word | PDF |
|---|---|---|---|
| **Site survey** | 13 across 5 groups | ✅ `site-surveys.docx` | ✅ `site-surveys.pdf` |
| **Worksheet** | **0 — it explains why** | ✅ `worksheets.download` | **stated unavailable (DC-07)** |
| **RAMS** | 14 across 5 groups | ✅ `rams.download` | ✅ `rams.download-pdf` |
| **O&M manual** | 2 + a readiness list | ✅ `om-manuals.download` | ✅ `om-manuals.download-pdf` |

Open a module → one control reading **`Generate document`** → `?action=generate` discloses that
document's form → submit → the values are persisted where the generator already reads them and the
**existing** generate entry point is called. No new generator, no new renderer, no queued job of this
plan's own, no JavaScript.

`test_every_offered_format_points_at_a_route_that_exists()` asserts every non-null cell resolves with
`Route::has()` and that a null cell renders **no radio** — so the table above is executable, not
prose. `DocumentFormatInventoryTest` is still green at 5 passed: the missing set is still exactly
`['worksheet.pdf']`, and nothing was invented to close it.

## The Blade switches on FIELD TYPE, not on which document this is

`doc-form.blade.php` iterates `groups` and branches only on `$field['type']` against the map's seven
`TYPE_*` constants. **It contains no `'rams'`, `'om'`, `'worksheet'` or `'site_survey'` literal** —
asserted by grep, with Blade comments stripped first so the file may still explain itself in prose:

```
✓ the component names no document and switches on type instead
```

The same test asserts the file contains `TYPE_` and `@foreach`, and contains neither `<select` nor
`{!!`. Two multiplicity decisions that could easily have become per-document branches are read off
the field's own **rules** instead:

- `array` in the rules → checkboxes (`additional_engineers[]`, `programmers[]`); otherwise radios
  (`lead_engineer_name`, a string column). One rule, no branch.
- `prohibited` in the rules / `readonly => true` → rendered as a **value**, not an input.

There is deliberately **no `@else` arm** on the type switch. An eighth type added to the map without
a branch renders no control, and
`test_the_open_form_renders_exactly_the_controls_the_map_implies()` — which derives the expected
`name` set from the map and compares it to the DOM — goes red. A silent fallback input would instead
ship a field nothing reads.

## The Worksheet renders its explanation, not inputs

The map gives it four display-only values and an `intro`, and the panel prints that sentence:

> *The worksheet is built from the project package, so there is nothing to fill in here. Install
> dates, engineers and the site contact belong to the RAMS. Word only — there is no worksheet PDF
> (DC-07).*

plus, from the missing-format loop, **`PDF is not available for this document (DC-07).`** No PDF
radio is rendered, and `format=pdf` on the worksheet is **also** a server-side validation error
(`test_the_worksheet_cannot_be_asked_for_a_pdf_even_by_hand()`), because the request validates
`format` against that document's own non-null cells. Saying it in one place only would let a
hand-crafted POST ask for a document that cannot be rendered.

The user's own examples — install dates, engineers, site contact — are **RAMS** fields and were not
added here; 46.2-04's grep gate is why, and the panel says so rather than leaving the short form
looking broken.

## `<select`: NOT lifted, and this was the commit that could have lifted it

46.2-03 re-took `FORBIDDEN_MARKUP` at 2 and named the condition precisely: *"If Plan 46.2-05 finds a
field that genuinely needs a `<select`, IT LIFTS THE ENTRY BY NAME IN THE COMMIT THAT SHIPS THE
CONTROL."*

**It found none.** The widest closed option set on the page is the comms-room access radio at FOUR
options, and four radios read better than a four-item dropdown on a phone in a plant room. The three
`resource-list` fields render one control per active person, which is a checkbox or radio group by
LR-04's own logic and not a picker. So the entry stays at 2, re-taken against the hardest case the
ban has faced, and the ruling is recorded in the fence and in the component's docblock.

## Deviations from Plan

### Applied under the plan's own rules

**1. [Rule 3 — Blocking] `CockpitCreateVisitTest` and `CockpitVisitActionsTest` edited, though absent from `files_modified`**
- **Found during:** Task 3
- **Issue:** `CockpitCreateVisitTest::test_no_module_panel_renders_any_visit_control()` asserted
  `substr_count($panel, 'cav-qa') === 0` and banned the string `Generate document`; both tests
  asserted `ACTIONS === []`. The cockpit suite could not go green without them, and 46.2-03's own
  comments name this plan as the one that moves them.
- **Fix:** repointed by name with the reason, as tabled above. The class count became two route
  assertions (stronger), and the emptiness assertions became `['generate']` plus a direct
  `assertNotContains` per retired visit action.
- **Commit:** `74edf35a`

**2. [Rule 1 — Bug] The `extracted_data` merge is NON-DESTRUCTIVE, against the plan's literal wording**
- **Found during:** Task 1
- **Issue:** The plan says *"merge into `extracted_data`, pass through
  `RamsReviewDataService::normalise()`, save"*. `normalise()` returns a **fixed thirteen-key array**
  (`RamsReviewDataService.php:74-90`), so saving its output over `extracted_data` would DELETE every
  sibling key the QuoteWerks import and the review form put there — `overview`, `equipment_list`,
  `cable_list` and the rest. That is silent data loss on the PM's first generation.
- **Fix:** the two sections this form owns are normalised and merged back into the existing payload;
  everything else is left exactly as it was. `test_a_rams_submission_survives_normalisation_on_a_re_read()`
  asserts the surviving sibling BY NAME as well as the round trip, so the amputation cannot come
  back.
- **Commit:** `db6effb6`

**3. [Rule 3 — Blocking] `form_data.working_hours` is patched AFTER the delegation**
- **Issue:** the map's one exception targets `form_data`, which is a column on the **RamsDocument** —
  a row `RamsController::generateFromProject` creates. It cannot be written before the delegation
  because it does not exist.
- **Fix:** patched immediately after, scoped to `id > ` the pre-delegation maximum so a re-submission
  never edits an earlier RAMS, and touching `form_data` only — never `filename`, never `status`.
  Asserted by name.
- **Commit:** `db6effb6`

**4. [Rule 2 — Missing critical functionality] A display-only field is TEXT, not a `readonly` input**
- **Issue:** the plan's `<interfaces>` implies inputs throughout. A `readonly` input still SUBMITS
  its value, and the map gives those fields `rules => ['prohibited']` — so an ordinary submission
  would have failed validation on four to five fields the PM cannot edit and cannot clear.
- **Fix:** rendered as `<span class="cav-qa__value">`. The `prohibited` rule remains as the server's
  guard against a hand-crafted POST, asserted by
  `test_a_display_only_value_cannot_be_overwritten_by_hand()`.
- **Commit:** `74edf35a`

**5. [Rule 3 — Blocking] The site survey delegates BEFORE it persists**
- **Issue:** the plan's order is persist-then-delegate. The survey's "generate" IS the row's
  creation, so there are no columns to write until the delegation has run. Worse,
  `SurveyService::createFromProject()` **throws** when an active survey already exists.
- **Fix:** create only when there is none (`ensureSurvey()`), then write the columns either way. The
  ordering is stated in `store()` rather than hidden in a helper. Superseding is a different act with
  its own route and this panel does not offer it.
- **Commit:** `db6effb6`

**6. The plan's `tdd="true"` was honoured at PLAN level, not per task.** `CockpitDocumentFormTest`
was written first and run RED (the route did not exist, so `route()` threw), then Tasks 1 and 2 were
implemented together and the file went green. The reason is structural: the write and the form are
one feature, and a test for either alone cannot pass without the other. Two commits, not three, for
the same reason — a commit that shipped the Blade without Task 3's count moves would have been RED,
and the repo's own rule is that a count moves *in the commit that ships the control*.

### A test the plan asked for that cannot be written, and what replaced it

**`a POST without @csrf is rejected`.**
`Illuminate\Foundation\Http\Middleware\VerifyCsrfToken::handle()` short-circuits on
`$this->runningUnitTests()`, so **no feature test in this suite can observe a 419** —
`withMiddleware()` does not help, because the bypass is inside the middleware and not in the stack.
Attempting it produced a 500 from a real generation running with no `Bus::fake()`, not a 419.

Replaced by the two halves, both real and both asserted:
- the FORM carries the token — `test_the_disclosed_form_carries_a_csrf_token_on_every_document()`
  plus the fence's structural per-form DOM check, now at an exact 4 (and proven capable of failing by
  breakage 3);
- the ROUTE is inside the group that checks it —
  `test_the_write_route_sits_inside_the_group_that_checks_the_token()` asserts `web` and `auth` are
  both in `gatherMiddleware()` and that the verb set is exactly `['POST']`.

This is written up in the test's docblock rather than left as a quiet omission.

## Deferred Issues

**The real-page verification was NOT performed, and this is the one thing the plan asked for that is
not done.** The plan's `<verification>` ends *"generate each of the four from the form on a real local
project and confirm the artifact opens."* That needs a running Herd site, a queue worker, and — for
the RAMS, the worksheet and the O&M — **live AI spend**, because all three dispatch a build job that
calls the model. It was not run here.

What IS proven at the HTTP layer, against a real database, by
`CockpitDocumentFormTest`: the POST creates the `Worksheet`, the `SiteSurvey` (with all thirteen
columns the PDF reads), the `RamsDocument` (with `form_data.working_hours` patched on) and the
`OmManual` (with `_draft_mode` carried into `extracted_data`); the values survive a re-read through
`normalise()`; and every format route resolves. What is NOT proven is that the resulting `.docx`
opens. **That is the 46.2-06 checkpoint's job and it needs the user in front of the page.**

**DC-07 is still NOT DELIVERED and still needs the user's decision.** The panel now SAYS the
worksheet has no PDF, which is what D-05 required — but the three options in
`46.2-FORMAT-INVENTORY.md` (accept Word-only / author a worksheet PDF Blade as its own phase / offer
the engineer-activity report relabelled) are still unchosen.

**Two open defects carried forward, neither this plan's:**
- **`D-46-05-01`** — `/worksheet/{token}` 500s for a worksheet with no rooms. Live right now.
- **`D-46.2-04-02`** — the site-survey comms-room access vocabulary mismatch: the map offers the
  STORED set (`yes,no,outsourced,unknown`) and the form-PDF Blade compares against
  `permission/outsourced/free`, so two of its checkboxes can never tick. **This plan now lets a PM
  set that field from the cockpit, which makes the defect reachable from one more surface** — the
  stored value is correct and the RAMS/DOCX renderers map it correctly; only
  `pdf/site-survey/_header-meta.blade.php:66-69` is wrong. Out of this plan's `files_modified`; logged
  so 46.2-06 or a later plan owns it.

**One limitation of the format radio, stated plainly.** It records and validates which format the PM
asked for; it cannot hand one back, because all four generators queue their build (or hand off to a
confirm step) and there is nothing to stream at the moment of the POST. A successful submission
therefore redirects to the **Files** tab, where the document appears, with the chosen format named in
a flash. If a later phase wants "click PDF, get a PDF", that is a synchronous-generation decision and
a phase of its own.
