This file exists because of one house rule: **a count that moved and is not listed
here is drift.** A re-taken number is a decision; an untouched number is an
oversight; and the only way to tell them apart afterwards is to have written down
which was which at the time. Rows that DID NOT MOVE are therefore in the table,
because "we looked and it should stay" is a finding.

## The one gap this reconciliation found

**`DEFERRED_AFFORDANCES` is the only fence list whose length is not asserted.**

`CockpitReadOnlyFenceTest:964-966` pins `FORBIDDEN_MARKUP` at 2, `WRITE_SURFACE_TABLES`
at 13 and `BANNED_HANDLER_ATTRIBUTES` at 9. `DEFERRED_AFFORDANCES` has no equivalent
line. The list is *used* — every entry is swept over every judged region at `:485` and
`:860` — so a banned string appearing on the page is caught. What is NOT caught is an
entry **leaving** the list: deleting `'Add document' => 'Phase 48'` would make the
fence quietly narrower with every test still green, which is precisely the failure mode
the exact-count house rule exists to prevent, and the reason 46-04's lifts had to be
"by name in the commit that ships the thing".

Three phases have moved this number (18 → 21) while describing it as an exact count in
their summaries. It has never been one.

**Not fixed here.** Adding `assertCount(21, self::DEFERRED_AFFORDANCES)` is a
one-line change to a file this plan's `files_modified` does not list, and pinning a
number is exactly the kind of edit that should land in a commit that can explain it
rather than in a phase-closing plan. Raised as **D-46.2-06-04** with the line number
and the fix, so whoever next touches the fence inherits a specific instruction and not
a vague worry.
