# Phase 46.2: Doc Creation Cockpit - Context

**Gathered:** 2026-09-22
**Status:** Ready for planning

<domain>
## Phase Boundary

The cockpit becomes a document creation tool. **Four** module rows — Site survey, Worksheet, RAMS,
O&M manual. Opening one slides in the panel, which carries the fields that document needs and
produces it in **Word and PDF**.

**In scope:** reducing the cockpit to four rows; a per-document input form in the panel; generating
each document in both formats from that form; and taking the visit/review surfaces off the cockpit
**without deleting the code behind them**.

**Out of scope:** deleting the visit lifecycle, the engineer links, the review evidence, the photo
ZIP or their tests (see D-02 — they stay, they simply stop being surfaced here); sending documents
to a client (Phase 48); writing new document generators (they already exist).

</domain>

<decisions>
## Implementation Decisions

Taken with the user on 2026-09-22. Their brief, verbatim:

> "only things i now need in the type of design are SiteSurvey, Worksheet, Rams, OM Manual. This is
> now just a doc creation tool so when a user selects a tab, the side window will open and allow doc
> generation and fields to enter items used in the doc creation eg rams > install dates / engineers/
> site contact etc all items currently needed for rams creation. Same for other docs. Docs will
> create in word and pdf"

### The reduction

- **D-01:** **Four module rows only** — Site survey · Worksheet · RAMS · O&M manual. The other five
  (Programme and commissioning, Drawings, Cable schedule, Programming, Snagging) are **removed from
  the cockpit entirely** — not greyed, not empty, gone.

  ⚠️ This reverses **D-16** (nine rows, Snagging added) and narrows **D-11**. Cable schedule and
  Drawings do have real generators and were plausible members; the user's call is four. Record the
  reversal where D-16 lives so the earlier reasoning is not silently contradicted.

  Consequence for a live invariant: Phase 45's rule that **every `Visit::TYPE_*` reaches exactly one
  module row** can no longer hold — snag, commissioning and programming visits have no row. That
  rule exists in a test. It must be **retired deliberately, by name, with this decision cited** —
  not deleted to make a red test pass.

- **D-02:** **The visit work is KEPT, just not surfaced on the cockpit.** Phases 46 and 46.1 built
  the visit model, engineer links, accept/send back/office note/raise snag, the survey→install
  carry-forward, the returned-evidence review and the photo ZIP. **Do not delete the models,
  services, commands, routes or their tests.** Remove only the cockpit's *surfacing* of them.

  Specifically: the engineer links (`/survey/{token}`, `/worksheet/{token}`) keep working exactly as
  today, and **the survey→install carry-forward stays live** — it is on the engineer's link, not the
  cockpit, and it is the one piece with safety consequences (an installing engineer seeing the
  surveyor's access constraints, site risks and H&S notes).

### The panel

- **D-03:** Opening a module slides in the panel carrying **the fields that document needs** — the
  user's example: RAMS → install dates, engineers, site contact. Those fields are largely
  **discoverable from each document's existing create form and builder**, not invented:
  `resources/views/rams/create.blade.php` exists, and `RamsBuilderService` / `RamsDataBuilderService`
  already read `start_date`, `site_contact`, `client_contact_name`, `client_contact_email`.
  **Derive the field set from what each generator actually consumes.** A field the generator ignores
  is a field that teaches a PM to fill in noise.

- **D-04:** **Word AND PDF for all four.** The generators exist — `SiteSurveyDocxService`,
  `WorksheetDocxService`, `OmManualDocxService`, the RAMS `DocxBuilderServiceV2`, with
  `PdfService` / `PdfRenderService` for PDF. **Do not write new generators.** Where a format is
  missing for a document type, say so rather than inventing a second renderer.

### Three decisions taken 2026-09-24, after planning surfaced them

- **D-05:** **Worksheet ships Word only. The PDF gap is recorded, not papered over.** Verified: there
  is no `pdf/worksheet*.blade.php` anywhere, and `worksheets.engineer-report-pdf` renders the
  engineer's *activity* report with `abort_if(! hasEngineerActivity(), 404)` — a different document
  for a different purpose, which would 404 for a PM generating a worksheet up front.

  Producing a worksheet PDF means authoring a renderer, which D-04 forbids and which is a phase of
  its own: somebody has to decide what a worksheet PDF contains. **The panel must say plainly that
  PDF is unavailable for this document** rather than offering a button that fails. Recorded as
  **DC-07, NOT DELIVERED**.

  Format coverage after this phase: RAMS ✅✅ · O&M ✅✅ · Site survey ✅ (Word newly reachable) ✅ ·
  Worksheet ✅ Word only.

- **D-06:** **The read-only visit list and count phrase STAY on the Site survey and Worksheet rows.**
  Removing them would mean redesigning the module row, and sketch 004's row design explicitly
  survives this phase. The rows stop *offering* visit actions; they do not stop *reporting*.

- **D-07:** **The Worksheet row is titled "Worksheet", not "First fix and install."** The old title
  named a visit type; on a document-creation page the row is the document.

### Claude's Discretion

- Whether the form lives on the Overview tab or its own tab, and whether Files/Notes/Returned
  survive. The Returned tab has no purpose on a cockpit that does not surface visits — but D-02
  says keep the code, so removing the tab is a surfacing change, not a deletion.
- Whether generation is synchronous or queued. Some of these already dispatch jobs
  (`BuildWorksheetJob`); follow each generator's existing pattern rather than imposing one.
- Whether a document's fields persist between generations, or are entered each time.

</decisions>

## Existing Code Insights

- **The fence still stands and still matters.** `CockpitReadOnlyFenceTest` carries
  `FORBIDDEN_MARKUP` (2), `DEFERRED_AFFORDANCES` (18), `BANNED_HANDLER_ATTRIBUTES` (9),
  `WRITE_SURFACE_TABLES` (11), and both `cockpitRegion()` brackets. This phase ships **forms with
  many fields** — the most input-heavy surface the cockpit has had. `<select` is still banned and a
  document form may genuinely need one: if so, **lift it by name in the commit that ships it**, as
  46-04 and 46.1-04 did. Never delete an entry to make a change fit. `<script` and all nine handler
  attributes stay banned — there is no JavaScript on this page.
- **Counts asserted exactly** across several tests (module count, GET routes = 3, write routes = 5,
  affordances = 18). Nine → four will move several. Raise or lower them **by name with a reason**,
  keeping them exact — that is this repo's established house rule and it has caught real drift.
- **`resources/views/layouts/app.blade.php`, `resources/css/app.css`, `tailwind.config.js` must stay
  BYTE-IDENTICAL to `4abd2b24`** — sha256-asserted; a mismatch is a STOP.
- All colour is a token on `.cav-brand` (76 tokens); no hex in Blade; Tailwind colour utilities
  banned; every class `cav-`-prefixed; no `position` on the module-row anchor (the stretched-link
  trap silently kills row-click).
- **Two live defects remain open and are NOT this phase's**: `D-46-05-01` — `/worksheet/{token}`
  500s for a worksheet with no rooms (**live right now**); `D-46-06-01` — the same-second send-back
  edge.

<specifics>
## Specific Ideas

- The user has now changed direction three times on this page (sketch 002 → sketch 004 → PMV-style
  review → doc creation). **The visual design has held throughout** — it is the panel's *contents*
  that keep changing. Build the form so its field set is data, per document type, rather than four
  hand-written panels: the next change should be a row in a map, not a rewrite.
- "Simple to use" has been the user's stated criterion every time, and they once rejected a design
  as "scary". A form with twenty fields is exactly how that happens again. Group, default and
  pre-fill from the project wherever the data already exists.

</specifics>
