# Phase 46.6 Plan 01: Survey Link Tab-Bar Scaffold Summary

**Sticky bottom sv-tab-bar on the survey engineer link (Site tab first, one tab per room), replacing the `screen: 'rooms' | 'step'` picker/wizard split — the room wizard itself stays unflattened and shared, exactly as before.**

## Performance

- **Duration:** ~70 min
- **Tasks:** 3 (Task 1 test, Task 2 implementation, Task 3 regression verification — no code change)
- **Files modified:** 1 modified (`resources/views/surveys/show.blade.php`), 1 created (`tests/Feature/Surveys/SurveyLinkTabbedLayoutTest.php`)

## Accomplishments

- A sticky bottom `sv-tab-bar` renders on every state of `GET /survey/{token}`: a "Site" button first, then one button per room, each showing a ✓ when that room is complete.
- A new `data-tab="site"` panel is the FIRST panel in document order and is statically active on first load (server-rendered, not JS-dependent) — carries the summary card, the office send-back banner, the engineer reference-files drawer, the Site Logistics capture form, the readonly banner, the submit panel, and the "Download PDF Form" link (all relocated unchanged from the retired `screen: 'rooms'` picker).
- One `data-tab="room-N"` panel per room (identity card + the room's "job context" drawer — planned actions, AV works, quote kit, reference checklist, pre-install checklist — UNCHANGED content, now always visible in that room's own tab rather than behind a chevron).
- The 8-step wizard (Room Context → Sign-off) is **not duplicated** per room — it remains ONE shared block, reading `currentRoomIdx` exactly as it did before this plan. `selectRoom(idx)` now sets `activeTab = 'room-' + idx` alongside `currentRoomIdx`, so the shared wizard surfaces beneath whichever room tab is active.
- Every former `screen === 'rooms'` / `screen === 'step'` read (12 sites: header progress bar, validation ribbon, two drawer headers, four drawer branch conditions, two bottom nav bars, one debounce guard) was repointed to `activeTab`-based equivalents. The `screen` Alpine property itself is fully retired, not left dead — confirmed via `grep -n "screen"` returning only prose comments afterward.

## Decisions Made

See `key-decisions` in frontmatter. In short: shared (not duplicated) wizard to protect the existing spine-parity test; no tab-persistence work in this plan (left to Claude's discretion / a later plan, per CONTEXT.md); tab-button active styling via Tailwind `:class` binding, not a new hex literal.

## Deviations from Plan

**None requiring Rule 1-4 classification.** One judgment call worth recording explicitly because it diverges from a literal reading of the plan's Task 2 action text ("one `data-tab="room-{{ $idx }}"` panel per room, each containing — UNCHANGED FOR THIS PLAN — the existing step-wizard markup"):

- **Interpreted as "the room's tab experience includes the wizard," not "duplicate the wizard DOM once per room."** The plan's own `<interfaces>` section is explicit that `currentRoomIdx` stays load-bearing and the room wizard is "unflattened" — i.e., one implementation, not N. Literal per-room duplication of the ~1,100-line wizard block would have (a) scaled page weight linearly with room count on a page whose stated audience is "a phone, one-handed, bad signal," and (b) broken `SurveyLinkBrandingTest::test_the_section_spine_is_structure_and_never_status()`, which asserts the `sv-spine` count is IDENTICAL across all states except roomless — the fixture's "locked" state has 1 room while the other three have 2, so a per-room duplicated wizard would yield 12 spines in one state and 23 in the others. This was caught by reading the wizard's `sv-spine` usage (11 occurrences) and the test's fixture room-counts before implementing, not discovered via a failing test. Kept the wizard shared, exactly as the Interfaces section already specified; no test or constraint was weakened to accommodate this — `SurveyLinkBrandingTest` passes unmodified (8/8, 159 assertions).

## Issues Encountered

None blocking. The only risk identified during planning (sv-spine parity vs. per-room duplication, above) was resolved before writing any markup, not discovered after a red run.
