# Phase 46.6 Plan 04: Completed-Survey Report — PDF + Real .xlsx Summary

**The five-section completed-survey report (rooms summary + points raised + items agreed + client items required + additional comments) now downloads as both a PDF (third mode of the existing unified Browsershot renderer) and a real .xlsx workbook (new PhpSpreadsheet-based service), with formula-injection neutralised on every free-text cell.**

## Performance

- **Tasks:** 2 completed
- **Files modified:** 4 (`SurveyPdfService.php`, `summary.blade.php`, `SiteSurveyController.php`, `routes/web.php`)
- **Files created:** 2 (`SurveyReportXlsxService.php`, `CompletedSurveyReportTest.php`)
- **Completed:** 2026-10-01

## Accomplishments

- `SurveyPdfService::buildCompletedReport(SiteSurvey $survey): string` — a new, independent `$completed` mode of `pdf.site-survey.summary`, rendering only the five named sections in the required order, with escaping and a named "Not yet reviewed." placeholder for any section with no `SurveyReportSection` row yet.
- `SurveyReportXlsxService::build(SiteSurvey $survey): string` — the same five sections as a real `.xlsx`, following `CableScheduleXlsxService`'s PhpSpreadsheet writer pattern (same palette values, same `DocumentArtifactStorage` injection), proven re-openable via `ZipArchive` + `IOFactory`.
- Two new GET routes (`site-surveys.completed-report`, `site-surveys.completed-report.xlsx`), guarded by the same `authorizeSurvey()` as the sibling `client-report`/`variations.csv` routes, both with a friendly-redirect-on-failure catch so neither can surface a raw 500.

## Decisions Made

See frontmatter `key-decisions`. In short: no second renderer, no new dependency, a new independent `$completed` flag (not an `$internal` overload), static (non-escaped) section headings to preserve the literal apostrophe in "Client's Items Required", and an explicit formula-injection guard fixing a pre-existing gap rather than copying it forward.

## Deviations from Plan

None requiring Rule 4 (architectural) escalation. One Rule-2-adjacent addition beyond the plan's literal text: the plan's `<behavior>` for Task 1/2 did not explicitly specify controller-level error handling for generation failures, but the project's own non-negotiable rules required it ("A failure must not surface as a raw 500"). Both `completedReport()` and `completedReportXlsx()` wrap their respective `build*()` calls in `try { } catch (\Throwable $e) { return back()->with('error', ...); }`, mirroring the existing `RamsController::downloadPdf()` pattern verbatim in shape. This is additive, in-scope, and does not touch any file outside this plan's file list.

## Issues Encountered

Narrowed to assert against actual *usage* (`use Dompdf`, `new Dompdf`, `Barryvdh`, `Mpdf\Mpdf`) rather than banning the bare word.

All three were caught and fixed before the GREEN run that is reported below — the RED run quoted under "Non-vacuity proof" is the real, substantive RED (missing class/method/route), not these authoring corrections.

**How the `.xlsx` was proven real, not just non-empty:** `test_build_produces_a_real_xlsx_openable_by_ziparchive_and_io_factory` calls `ZipArchive::open($path)` and asserts it returns `true`, asserts `xl/workbook.xml` is `locateName()`-able inside the archive, then loads the file via `PhpOffice\PhpSpreadsheet\IOFactory::load()` and iterates every cell, asserting the room name ("Comms Room") and the seeded `points_raised` body text are both present as real, readable cell values — not a byte-count check.

**How the five sections were proven to render with real seeded content, in order:** `test_five_sections_render_in_order_with_seeded_content_and_escaped_script` seeds all four `SurveyReportSection` rows plus a room, renders `pdf.site-survey.summary` directly via `view(...)->render()` (the same Chromium-free pattern `SurveyPdfModesTest` already uses, so this suite has no Chromium dependency), and asserts `strpos()` ordering across all five headings (`Rooms Summary` < `Points Raised` < `Items Agreed With Client` < `Client's Items Required` < `Additional Comments`), plus each section's seeded body text, plus that a planted `<script>alert('xss')</script>` renders as the escaped `&lt;script&gt;...` rather than executable markup.

**How `client-report` was proven unaffected:** `SurveyPdfModesTest`'s existing 8 tests (internal-mode sections, client-mode sections, both-modes project details, both-modes photos, client-mode variations/office-notes, internal-mode omissions, default-flag back-compat, and the route-existence smoke test for `site-surveys.pdf`/`site-surveys.client-report`) all still pass unchanged — the entire pre-existing body of `summary.blade.php` was moved, not rewritten, into the `@else` branch of the new `@if($completed)` gate, and this suite proves none of its behaviour shifted.

**How formula injection was handled:** `SurveyReportXlsxService::guardFormulaInjection()` is a private method, independently unit-exercised via `test_formula_injection_payload_is_neutralised_before_being_written_to_a_cell` — a `SurveyReportSection.body` seeded with a leading `=cmd|'/c calc'!A0` payload is written to its cell, then the workbook is reloaded via `IOFactory::load()` and the stored cell value is asserted to NOT start with `=`, `+`, `-`, or `@` (it is prefixed with a literal `'` instead), even though the source body does. The guard is applied to every free-text cell the service writes: room name, room type (`space_type`), room work-type label, room notes digest, the project-info row, and every section body — not just the one the test happens to seed.

**What the user sees on a generation failure:** both `SiteSurveyController::completedReport()` and `completedReportXlsx()` catch `\Throwable` around the respective `build*()` call and `return back()->with('error', 'Completed report ... generation failed: ' . $e->getMessage())` — a friendly flashed-error redirect, never an unhandled exception page. This mirrors `RamsController::downloadPdf()`'s existing in-repo pattern for the same class of failure (missing puppeteer/Chromium, a template error) byte-for-byte in shape.

**Which controller and middleware group:** both new routes live on `SiteSurveyController` (not a new controller), registered inside the single pre-existing `Route::middleware('auth')->group(...)` block in `routes/web.php`, immediately beside `site-surveys.client-report`/`site-surveys.variations.csv` — same section comment block, same `authorizeSurvey()` guard. `test_completed_report_routes_are_registered_and_guarded_by_authorize_survey` asserts both route names exist and that an unauthenticated `GET` to either redirects to `login`, exactly like the sibling download routes.
