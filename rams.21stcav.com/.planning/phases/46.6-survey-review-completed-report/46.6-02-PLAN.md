<objective>
D-03 and D-08: give the office a place to write the four new report sections (points raised /
possible issues, items agreed with client, client's list of items required, additional comments)
without ever touching the engineer's own captured record — following the SAME append-only,
attributed, no-update/no-delete doctrine `VisitNote` already established for a visit's send-back
note, rather than reusing the single-valued, overwritable `site_surveys.office_review_notes` /
`site_survey_rooms.office_notes` columns.

⚠️ **Why a NEW table, not `visit_notes` itself:** `VisitReworkState::forSurvey()` returns `null` for
any survey with no `Visit` wrapping it (pre-Phase-45 surveys, or any survey created outside the
visit-issuing flow) — `visit_notes.visit_id` would then have nowhere valid to point, and this report
must work on EVERY completed survey, not only visit-wrapped ones. `visit_notes` is also a single,
undifferentiated free-text stream (one `body` per note); this plan's four sections need to be
individually addressable so 46.6-04 can place each in its own named spot in the PDF/XLSX. The new
table keeps `VisitNote`'s doctrine (append-only, attributed, FK-safe) while keying off
`site_survey_id` directly — the same choice `SurveyVariation` already made for the same reason. This
reading is `Claude's Discretion` under D-03/D-08's framing, not a literal requirement to touch the
`visit_notes` table — **confirm it at the phase checkpoint** rather than treating it as settled.

Purpose: the five-section report (46.6-04) needs somewhere to read office-authored content from
that is provably never the engineer's own text — this plan is that "somewhere."

Output: `survey_report_sections` table + model, a save endpoint, and a review panel on the existing
internal survey edit page, seeded read-only with the engineer's own relevant capture (quick_notes /
SurveyVariation rows) for context, editable in a separate field.
</objective>
