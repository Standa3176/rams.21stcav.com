# Phase 46.6 Plan 02: Survey Report Sections (office annotation surface) Summary

One-liner: a new append-only `survey_report_sections` table + save endpoint + edit-page panel let the office write four named report sections without ever touching the engineer's own captured record, and it works even on surveys with no Visit wrapping them.

## What was built

**Task 1 — Migration, model, doctrine test.**
`database/migrations/2026_10_01_000000_create_survey_report_sections_table.php` creates
`survey_report_sections` (`id`, `site_survey_id` FK cascade, `section` enum of the four
named sections, `body` text, `user_id` FK nullOnDelete, `created_at` only — no
`updated_at`). `app/Models/SurveyReportSection.php` mirrors `VisitNote`'s doctrine:
`UPDATED_AT = null`, `SECTIONS` constant, `$fillable`, `survey()`/`author()` relations,
`getActorNameAttribute()`, and a static `latestFor()` reader ordered by `id` (not
`created_at`, since rows can share a timestamp). `tests/Unit/Models/SurveyReportSectionTest.php`
covers the table shape, the "second save adds a row" append-only behaviour, `latestFor()`,
relation resolution, FK dispositions (user deletion nulls `user_id` and keeps the body;
survey deletion cascades), and the grep-based no-update/no-delete-anywhere-in-`app/` assertion
mirroring `CockpitOfficeNoteAndSnagTest`.

**Task 2 — Save endpoint and the office review panel.**
`SiteSurveyController::saveReportSection()` (guarded by the same private `authorizeSurvey()`
as `clientReport()`/`variationsCsv()`) validates `section` against `SurveyReportSection::SECTIONS`
and `body` as `required|string|max:5000`, then always `SurveyReportSection::create([...])` —
never an update — and redirects back to `site-surveys.edit`. The route
`site-surveys.report-sections.store` (POST only — no PUT/PATCH/DELETE) sits in the same
`auth`-middleware group and literal-segment ordering as the sibling `client-report`/
`variations.csv` routes. `SiteSurveyController::edit()` now also resolves
`SurveyReportSection::latestFor()` per section key and passes `$reportSections` to the view.
The edit page gained a new, visually and structurally **distinct** "Completed Report" panel
(placed after the main update form closes, before the pre-existing Variations panel — kept
out of the nested `survey-form` because each section posts to its own form) with one
independent form+textarea per section, pre-filled from the latest row, plus a read-only
escaped block of the engineer's own room notes (`site_survey_rooms.notes`) and flagged
`SurveyVariation` rows (`access_issue`/`other`) for office context.
`tests/Feature/Surveys/SurveyReportSectionReviewTest.php` covers: exactly-one attributed
row created per save; guest bounced to login identically to the sibling download routes;
empty body rejected with no row written; two saves to the same section leave both rows and
the edit page shows only the latest; the edit page renders the engineer's capture read-only
and escaped, and a report-section save never changes `site_survey_rooms.notes` or
`SurveyVariation.description` (byte-identical re-read, not inferred); and a survey with
**no** `Visit` wrapping it (confirmed via `VisitReworkState::forSurvey() === null` and zero
`visits` rows) still accepts and renders its sections.

## Append-only / non-overwrite proof

Proven by code shape (mirrors `VisitNote`): `SurveyReportSection::UPDATED_AT = null`, the
migration has no `updated_at` column, and `SurveyReportSectionTest::
test_a_report_section_has_no_update_path_and_no_delete_path_anywhere_in_app()` greps every
`.php` file under `app/` for an `update()`/`delete()`/`forceDelete()` call against a
`SurveyReportSection`-shaped variable or query chain (found: none), and checks the route
table for any `report-sections` route carrying PUT/PATCH/DELETE (found: none — only the
POST `store` route exists).

Proven by behaviour, not inferred: `test_a_second_save_to_the_same_section_adds_a_row_rather_than_updating_the_first`
re-reads the FIRST row after a second save and asserts its `body` is still
`'First draft of points raised.'` — unchanged. The feature-level non-overwrite proof,
`test_the_edit_page_renders_engineer_capture_read_only_and_a_save_never_changes_it`, creates
a `SiteSurveyRoom` with `notes` and a `SurveyVariation` with `description`, renders the edit
page (asserting both appear read-only and HTML-escaped — `Door won&#039;t lock...`), then
POSTs a brand-new report-section save, then re-reads both records fresh from the database
and asserts `$room->fresh()->notes` and `$variation->fresh()->description` are **byte-identical**
to what was seeded. Neither assertion is a "no error was thrown" check — both compare exact
string equality against the original engineer-authored text.

## No-Visit case

`VisitReworkState::forSurvey($survey)` was asserted to return `null` directly in
`test_a_survey_with_no_visit_wrapping_it_still_accepts_and_renders_report_sections`, alongside
a direct `Visit::where('source_id', $survey->id)->count() === 0` check — not inferred from
the test's lack of a `Visit::factory()` call. The same test then POSTs a report-section save,
asserts exactly one row was written, and asserts the saved body renders on a subsequent GET of
the edit page. This is the scenario the table exists for, and it passes with zero `visits` rows
present anywhere in the database.

## Route placement

The new route lives on `SiteSurveyController` (not `SurveyController`/`PublicSurveyController`,
the two controllers that serve the public survey *link*). `authorizeSurvey()`, `clientReport()`,
`variationsCsv()`, and `edit()` — the office-facing internal survey screens this plan's panel
belongs beside — all live on `SiteSurveyController`, and the route is registered in the same
`Route::resource('site-surveys', ...)`-adjacent block as `client-report`/`variations.csv`,
inside the same `Route::middleware('auth')->group()`. It has nothing to do with the public
engineer link (`survey.show`/`survey.step.save`/`survey.save`), which this plan does not touch.

## Deviations from Plan

None — plan executed exactly as written. The one judgment call not spelled out verbatim in the
plan was *where* in `edit.blade.php` to place the new panel: the plan said "after the existing
Office Review Notes section," but that section sits inside the nested `survey-form`
(`id="survey-form"`), and HTML forbids nested `<form>` elements. The panel was placed
immediately after that form closes (`</form>`) and before the pre-existing Variations panel —
later in reading order than "immediately after," but still unambiguously separated from and
following Office Review Notes, and outside the only form it could not be nested inside. This is
a Rule 3 (blocking-issue) fix, not an architectural change.
