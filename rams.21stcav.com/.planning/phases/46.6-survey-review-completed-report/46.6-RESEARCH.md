# Phase 46.6: Survey Engineer Link — SCC Layout, Review, and Report Output - Research

**Researched:** 2026-10-01
**Domain:** Blade/Alpine.js engineer-facing wizard rebuild (tabbed layout) + office review + PDF/XLS report generation
**Confidence:** HIGH (all claims below are read directly from the two repos; no Context7/web lookups were needed — this is an internal-codebase comparison task)

## Summary

SCC's PMV engineer link (`pmv/show.blade.php`) is a **flat, standalone page** with a fixed-bottom
tab bar (`.pmv-tab-bar`, `position: fixed; bottom:0`), one `data-tab` panel per section (`site`,
`room-N`, `documents`, `wrap`), autosave debounced at 1500ms to `POST /pmv/{token}/save`, and a
`localStorage`-backed offline queue (`quick-260610-offsave`) that is **completely separate** from
its photo IndexedDB queue. Tab state does **not** survive a reload (no hash/sessionStorage persist
for the active tab) — SCC always reopens on the Site tab.

The RAMS **worksheet** link (46.7) already carries this exact shape (`ws-tab-bar`/`ws-tab-panel`,
12 `data-tab` hits) and ALSO improved on SCC: active-tab survives reload via `location.hash` +
`sessionStorage` (not SCC's gap), and autosave uses `localStorage` exclusively, never touching the
binary IndexedDB queue (`engineer-worksheet`). This is the better, already-proven, in-repo
precedent and should be followed over SCC's, per 46.7 D-06's explicit framing.

**The survey link is architecturally different from both**, and this is the single most important
finding of this research: the worksheet was an **accordion of everything on one page** before 46.7
(seven `<details>`, one page, one scroll). The survey link today is a **sequential Alpine
step-wizard** — `screen: 'rooms' | 'step'`, `currentRoomIdx`, an 8-step `nextStep()/prevStep()` flow
per room, with a progress bar in the header (`show.blade.php:264-270`). Verified: **0 `data-tab`,
6 `<details>`** (all for in-room sub-sections and one site-level block), matching the CONTEXT.md
measurement exactly. Converting this to "tabs along the bottom" is a bigger shape change here than
it was for the worksheet, because the existing navigation model is a wizard, not a scroll — the
planner must decide whether the room's internal 8-step flow lives *inside* each new room tab panel
(smallest diff) or gets flattened to match the worksheet's all-fields-visible pattern (bigger diff,
closer to the user's literal "tabs" mental model from SCC).

**Primary recommendation:** Follow the worksheet's (46.7) tab/autosave/persistence mechanics, not
SCC's, since 46.7 already improved on SCC in two ways RAMS should keep (hash-based tab persistence,
localStorage-only autosave never touching IndexedDB). Reuse the `partials._engineer-offline-capture`
module as-is (survey already includes it; it is NOT the worksheet's IndexedDB database — see
Architectural note below). For output: a real client PDF (`site-surveys.client-report` →
`SurveyPdfService::buildClientReport`, Browsershot) already exists and must be surfaced from the
cockpit, not re-built; for XLS, follow the `variationsCsv` CSV precedent already in
`SiteSurveyController` (streamed CSV with UTF-8 BOM) rather than adding a new binary workbook — this
repo's only *installed* XLSX precedent (`phpoffice/phpspreadsheet`, used by
`CableScheduleXlsxService`) is heavier machinery this phase does not need to reach for.

CSS display toggle, no Alpine, no framework.

**Bar** (`:1621-1633`):
```html
<nav class="pmv-tab-bar" role="tablist" aria-label="PMV sections">
  <button type="button" class="pmv-tab-btn" data-tab-target="site" data-active="true">Site</button>

```
`$statusClass` (`:1624-1627`) is computed server-side, ONLY for already-submitted rooms:
```php

    ? ' tab--status-'.str_replace('_', '-', $room->status)
    : '';
```
Live edits mirror this client-side via `applyTrafficLights()` (JS, referenced `:2685`, `:3326`) — the
server class is the first paint, JS keeps it current without a reload.

**Bar CSS** (`:202-216`): `position: fixed; left:0; right:0; bottom:0; z-index:40; overflow-x:auto;
scroll-snap-type:x mandatory` — horizontal scroll with snap, NOT wrap. Each button:
`min-height:44px` (touch target), `scroll-snap-align:start`.

**Switching logic** (`:2440-2447`, duplicated at `:3647-3651` for the locked/read-only render path):
```js
const activateTab = (targetKey) => {
  root.setAttribute('data-active-tab', targetKey);
  root.querySelectorAll('[data-tab]').forEach((p) => {
    p.classList.toggle('is-active', p.getAttribute('data-tab') === targetKey);
  });
  tabBar.querySelectorAll('[data-tab-target]').forEach((b) => {
    b.setAttribute('data-active', b.getAttribute('data-tab-target') === targetKey ? 'true' : 'false');
  });
};
```

### Autosave — SCC (verified, with the 46.7 D-06 correction confirmed first-hand this session)

- **Endpoint:** `POST pmv/{token}/save` (`routes/web.php:71`, `PublicPmvController::save`,
  throttled `pmv-engineer-save`).
- **Debounce:** 1500ms (`:2767-2780`), single-flight guarded (`if (saveInFlight) return;`).
- **Trigger:** `document.addEventListener('input', …)` on
  `[data-field], [data-row-field], [data-room-field], [data-check-field]`, immediate on `change` for
  selects/radios.
- **Payload:** `buildPayload()` (not fully quoted here — full-document snapshot; confirmed by the
  comment at `:2360`: "Save payloads are full-document so we ONLY need to keep the latest").
- **Indicator:** `#savePill` text/CSS-class states: `Idle` → `is-saving` → `is-saved` / `is-error` /
  `is-offline` (`:117-126`).
- **Offline path — `quick-260610-offsave`, confirmed real:**
  - Banner markup `:818-821`: `id="pmvOfflineBanner"`, text
    *"Offline — your edits are saved locally and will sync when you're back online."*, a manual
    "Sync now" button.
  - `offlineQueueKey = 'pmv_offline_queue:' + token` (`:2361`), `localStorage.setItem`/`getItem`/
    `removeItem` (`:2368-2377`).
  - On fetch failure in `silentSave()` (catch block, `:2480-2496`): queues `{version:1, token,
    payload, queued_at}` to localStorage, sets pill to `is-offline`, banner text becomes *"You're
    offline. Edits saved locally."*
  - Retry: `window.addEventListener('online', drainQueue)` + `setInterval(…, 30000)` (`:2426`); a
    successful `drainQueue()` call `queueClear()`s and flips the pill to `is-saved`.
  - **This queue is entirely separate from the photo IndexedDB queue** (`quick-260626-photoqueue`,
    a *different*, binary-only mechanism covered by its own banner
    `#pmvPendingPhotosBanner`, `:826+`).

### Autosave/Tab-persistence — RAMS worksheet (46.7, the better in-repo precedent)

`resources/views/worksheets/public-show.blade.php`:
- Tab persistence: `location.hash` written via `history.replaceState` on every tab switch
  (`:3073-3074`), read back on load (`:3106`), ALSO mirrored into `sessionStorage` under a `KEY`
  (`:3116-3153`) as a fallback for browsers/contexts where the hash gets lost (e.g. a full-page

- Autosave storage: `window.localStorage.getItem/setItem('wsDraft_' + WORKSHEET_ID, …)`

  write-probe pattern (`wsDraftProbe_` set then immediately removed, `:5014-5015`) checks
  localStorage availability before relying on it (private-browsing / quota-full safety).
- Comment at `:4844` is explicit: *"AUTOSAVE USES localStorage, NEVER THE PHOTO QUEUE"* — this is
  the D-06 ruling from 46.7's own CONTEXT, now verified as actually implemented, not just decided.

**Recommendation:** when 46.6 builds survey autosave/tab-persistence, use the worksheet's hash +
sessionStorage + localStorage pattern (already proven, already in this repo, strictly better than
SCC's own implementation) rather than re-deriving SCC's simpler (and reload-losing) approach.

## Common Pitfalls

### Pitfall 1: Porting the worksheet's vanilla tab-switch JS into an Alpine page verbatim
**What goes wrong:** The worksheet's `activateTab()` imperatively toggles `.is-active` classes via
`querySelectorAll` + `classList.toggle`. The survey page's DOM is owned by Alpine's reactivity
(`x-data="surveyWizard()"`, `x-show`, `x-model` throughout). Imperative DOM mutation and Alpine's
virtual-diffing can fight each other — an Alpine re-render triggered by an unrelated `x-model`
change can silently reset a class the vanilla function set.
**Why it happens:** The two pages have different JS architectures (worksheet: zero framework;
survey: Alpine-driven) despite looking similar as static HTML.
**How to avoid:** Express tab state as an Alpine data property (e.g. `activeTab: 'site'`) and drive
panel visibility with `x-show`/`:class` bindings, the same way the rest of the page already works.
Reuse the worksheet's **CSS** (`.ws-tab-bar`/`.ws-tab-panel` classes, fixed-bottom layout, scroll-snap)
freely — CSS has no framework opinion — but treat the **JS** as reference, not copy-paste source.
**Warning signs:** A tab that "sometimes" doesn't switch, or switches then snaps back after an
unrelated field edit.

### Pitfall 2: Conflating `office_review_notes` with the Phase 46-05 review doctrine
**What goes wrong:** `SiteSurvey::office_review_notes` (`app/Models/SiteSurvey.php:35`, edited in
`resources/views/site-survey/edit.blade.php:149-152`) is a free-text field that feeds the existing
client-report PDF (`summary.blade.php:67`: `@if (! $internal && filled($survey->office_review_notes))`).
It is a **different mechanism** from the Phase 46-05 "office sent this back" doctrine
(`app/Support/Visits/VisitReworkState.php`), which deliberately writes to `visit_notes` on the
`Visit` model and is explicitly documented (`ProjectCockpitActionController.php:318`) as writing
"to `visit_notes` AND NEVER to `site_surveys.office_review_notes`". A new review feature that writes
to the wrong one either pollutes the client-facing PDF with internal review chatter, or fails to
show up where the cockpit's Returned tab (Phase 47, STATE.md D-04) already expects it.
**How to avoid:** Read `VisitReworkState::forSurvey()` and the D-02 doctrine comment at the top of
that file (quoted in full under Architecture Patterns above) before deciding where review
annotations for this phase's report should live.

### Pitfall 3: Assuming "no XLS precedent" and reaching for a new dependency
**What goes wrong:** CONTEXT.md states "XLS has no precedent in this repo — establish whether a
library is already present." Taken at face value, an implementer might `composer require` a new
package.
**Why it happens:** True in the narrow sense that *site surveys* have no XLS output yet; false in
the broader sense — `phpoffice/phpspreadsheet ^5.8` is already a dependency and already has a
working consumer (`CableScheduleXlsxService`), and `SiteSurveyController::variationsCsv` already
streams a CSV from this exact controller.
**How to avoid:** Choose CSV (zero new code shape, matches `variationsCsv`) unless the five-section
report genuinely needs multi-sheet/styled output, in which case copy `CableScheduleXlsxService`'s
writer pattern rather than inventing a new one.

### Pitfall 4: Rendering the dead `public-survey/show.blade.php` instead of `surveys/show.blade.php`
**What goes wrong:** Both files exist, both are plausible-looking "the survey engineer link," and
`PublicSurveyController::show()` exists as working PHP (it would compile and render) — but has no
route. An editor who opens `PublicSurveyController.php` and sees a `show()` method, or who greps for
"survey" and lands on the 127KB file first, could spend the whole phase editing a file nobody will
ever see rendered in production.
**How to avoid:** Anchor every change to `routes/web.php:86` (`survey.show` → `SurveyController`)
and `resources/views/surveys/show.blade.php` specifically. `SurveyLinkBrandingTest.php`'s own header
comment (lines 14-20) exists precisely to keep this straight — read it before touching either file.

### Pitfall 5: `@php` inside a Blade comment, and branding-hex literals in prose
**What goes wrong (confirmed house pattern, not survey-specific):** `{{-- @php ... --}}` still
compiles in Blade and has previously swallowed an entire nav block on this page family. Separately,
`SurveyLinkBrandingTest.php` pins exact hex strings (`BRAND` / `SUPERSEDED` consts,
lines 39-49) and asserts their presence/absence across **five rendered states** (not started, partly
done, complete, locked, roomless) — not just one, so a change that happens to work on the "not
started" state can still fail the guard on "locked" or "roomless."
**How to avoid:** Never write a `@php` block inside a `{{-- --}}` comment even to "temporarily
disable" something; never type `#178A95`, `#C9922A`, `#0B3C45`, or `#0d6e77` in a new comment or
prose string anywhere in `surveys/show.blade.php`, even descriptively.

### Pitfall 6: Schema-freezing the WRONG IndexedDB database
**What goes wrong:** CONTEXT.md's code-context section warns about `engineer-worksheet`
(keyPath `id`, index `capturedAt`) being frozen and holding real unsent work. That warning is
accurate but **is about the worksheet's own inline IndexedDB, not anything the survey link uses.**
The survey link's actual IndexedDB dependency is the shared partial's `engineer-capture` database
(also v1, also `pending_uploads`, also `onupgradeneeded`-only-creates) — a *different* database that
happens to share the same shape by design (the partial's own header comment says it was "ported
from the Worksheet's proven offline machinery … and GENERALISED").
**How to avoid:** If this phase needs to store anything new client-side, treat BOTH databases as
frozen-at-v1 and additive-only: `engineer-worksheet` (worksheet only, out of scope for 46.6) and
`engineer-capture` (shared partial, survey's real dependency). Never bump `DB_VERSION` on either.
Confirmed: `_engineer-offline-capture.blade.php:69-70` (`DB_NAME = 'engineer-capture'`,
`DB_VERSION = 1`), included by `surveys/show.blade.php:2461`.

### Pitfall 7: SQLite tests vs MySQL/MariaDB live (house-wide, applies if any migration is added)
**What goes wrong:** Feature tests run SQLite `:memory:`; production is MySQL/MariaDB. A migration
can pass every gate and still be impossible on live (e.g. the 64-char identifier cap bit a RAMS
migration on 2026-09-27). MySQL DDL is not transactional, so a failed migration retry can falsely
report "table already exists."
**How to avoid:** If this phase adds any `reviewed_at`/`reviewed_by`-style columns or a review-notes
table, name every composite index explicitly and keep identifiers well under 64 characters.
