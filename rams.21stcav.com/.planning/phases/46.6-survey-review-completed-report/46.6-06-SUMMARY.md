# Phase 46.6 Plan 06: The End-to-End Walk, the Ledger, the Deploy Note, Task 1b Summary

**One real-HTTP walk proves every SRV requirement that can be proven server-side; the three
previously-unreachable report links (completed-report PDF/.xlsx + the orphaned client-report) are
now surfaced on the office edit page; every gate re-run for real; the requirement ledger, deploy
note, and ROADMAP/REQUIREMENTS paperwork are written. Phase 46.6 is NOT complete — 46.6-07's
blocking human checkpoint is outstanding.**

## What was built

**Task 1 — `SurveyEngineerLinkEndToEndTest`.** One feature-test class, two test methods. The main
walk creates a survey with one room, then through real HTTP: `GET /survey/{token}` (asserts the
tab bar, site tab first, all 8 `sv-step-N` sections flattened, no Next/Back); `POST step-save`
then a second `GET` proves the payload persisted; `actingAs` an office user, `GET` the edit page,
`POST report-sections.store` twice (points_raised, items_agreed), re-`GET` proves both render and
the engineer's own `room->notes` is untouched; `GET completed-report` (a real, Browsershot-rendered
55,625-byte PDF, probed live before writing the test rather than assumed); `GET completed-report.xlsx`
(a real `ZipArchive`-openable workbook with `xl/workbook.xml`); both outputs' section headings
checked in order. A second test method documents, in its own docblock rather than faking an
assertion, the two genuinely client-side-only behaviours (tab-reload survival, offline draft
queue) no HTTP request can execute.

**Task 1b — `SurveyReportLinksReachableTest` + the Blade edit.** 46.6-04 created
`site-surveys.completed-report`/`.completed-report.xlsx` with no UI link anywhere — a grep for
`completed-report` across `resources/views/` returned nothing, exactly the condition
`47-CONTEXT.md` records about the pre-existing `site-surveys.client-report`. Proven RED first (2
of 4 tests failed, `To contain: …/completed-report`), then fixed by adding three plain GET anchors
to `resources/views/site-survey/edit.blade.php`, outside `#survey-form`, labelled "— Internal"
(completed-report PDF/.xlsx) and "— Client-facing" (client-report) per D-05.

**Task 2 — the ledger, every gate re-run, the deploy note, ROADMAP/REQUIREMENTS.** All documented
in `46.6-LEDGER.md` / `46.6-DEPLOY-NOTE.md` (see below); `.planning/ROADMAP.md` ticks 46.6-01
through 46.6-06, leaves 46.6-07 and the phase's own top-level checkbox unticked;
`.planning/REQUIREMENTS.md`'s Group SRV section replaces "PROPOSED" with per-requirement
Status/Evidence and folds SRV-01..SRV-06 into the milestone's Total requirements count (67 → 73).

## Deviations from Plan

**None requiring Rule 4 escalation.** One Rule-1-adjacent finding surfaced, not patched:
`SurveyReportXlsxService::build()` never writes a literal "Rooms Summary" heading cell (the PDF
does) — the rooms render as a column-header table instead. This is a genuine, real cross-format
discrepancy the end-to-end walk's own cross-checking surfaced; it was NOT silently fixed in
production code (that would be an uninstructed scope change to a prior plan's shipped service)
and NOT silently asserted around (the walk's xlsx assertions check for room data, not the missing
heading literal, with an explanatory comment). Recorded in the ledger as part of SRV-05's
evidence row, with an explicit open question for 46.6-07.

## Issues Encountered

- Browsershot/Chromium availability on this runner was unknown going into Task 1 — probed directly
  with a throwaway test before committing to a real-HTTP PDF assertion (vs. the Chromium-optional
  `view()->render()` fallback other suites use). Confirmed present (200, `application/pdf`,
  55,625 bytes), so the walk uses the real controller action, proving the actual pipeline rather
  than a stand-in. The throwaway probe test was deleted before this plan's final commit — it never
  shipped.
- `gate-46.ps1 -Baseline` exceeded the Bash tool's default 120s timeout and was moved to the
  background on the first attempt — per the non-negotiable rules, that run's result was discarded
  (never accepted), and the gate was re-run in the foreground with an explicit 300s timeout,
  completing cleanly at 30.10s with exit code 0.
