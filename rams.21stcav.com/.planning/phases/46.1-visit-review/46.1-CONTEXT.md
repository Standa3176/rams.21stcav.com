# Phase 46.1: Visit Review - Context

**Gathered:** 2026-09-21
**Status:** Ready for planning

<domain>
## Phase Boundary

The drawer shows what an engineer sent back, and hands it off. A PM opens a module, sees the
returned photos, room answers, captured serials and client sign-off, downloads the lot as one ZIP
for Bitrix, and acts on it — with the four review controls sitting under the evidence rather than
above it.

**In scope:** a `Returned` tab in the panel; the photo gallery; per-room answers and notes; device
label photos and their serials; the client sign-off; a per-visit photo ZIP; and relocating the four
existing controls (Accept, Send back, Add note, Raise a snag) beneath that evidence.

**Out of scope:** editing anything an engineer captured (that is never allowed — see D-02 in
Phase 46); uploading new files (Phase 48); sending documents to a client (Phase 48); the snag
lifecycle (Phase 47); a data-summary file in the ZIP (deferred — see Deferred Ideas).

</domain>

<decisions>
## Implementation Decisions

Taken with the user on 2026-09-21. Their brief, verbatim:

> "this version should only be used for doc creation for each phase. Please relook at the project
> cockpit and redesign so a user have the same type of page design but if (for example) they click
> site survey they can create the link and manage the returned images/data the same way as a PMV in
> SCC app. They would then download the info and add Bitrix etc. Same for visit worksheets or rams"

### Why this phase exists — the measured gap

Phase 46 built the visit **workflow** (create, issue the link, accept, send back, note, snag) but
not the **review**. Verified 2026-09-21: `grep -c "photo" app/Support/Cockpit/CockpitPanelPresenter.php`
returns **0**. The app captures `SiteSurveyPhoto`, `SiteSurveyRoom`, `SiteSurveyRoomQuestion`,
`WorksheetPhoto`, `WorksheetSignoff` and `DeviceLabelPhoto` — and the cockpit shows none of it.
**A PM can accept a visit today without seeing a single thing the engineer sent back.**

### The reference implementation — SCC's PMV review panel

`resources/views/wizard/v2/partials/_pmv-review-panel.blade.php` in the
`service-contractor-creator` repo. Read it before designing. Its order is the contract:

  review state → **Download all photos (ZIP)** → per-room data → photo gallery →
  client sign-off (name + signature image, read-only) → approve / outcome

The ZIP route is `wizard.pmv.visits.photos-zip` →
`WizardPmvVisitController::downloadPhotosZip` (`routes/web.php:495`), grouping into
`{RoomName}/{before|after|kit}` sub-folders. Its own comment states the point: *"so the admin
doesn't have to click each thumbnail one at a time."*

### Decisions

- **D-01:** A **`Returned` tab** joins the panel, between `Overview` and `Files`. Overview stays the
  summary; Returned is where the work happens. Tab state stays in the query string
  (`?module=…&tab=returned`) — no JavaScript, same as every other tab.

- **D-02:** **The four review controls MOVE out of Overview and sit beneath the evidence.** Accept,
  Send back, Add note and Raise a snag render at the bottom of the Returned tab. The user's reason,
  and the design rule: a PM should not be able to accept a visit without having looked at it. The
  VL-11 cap of **four controls maximum** still binds, and reconstructed visits still offer **zero**.

- **D-03:** **The ZIP is per-visit, photos only, grouped by room** — `{Room}/{before|after|label}/`
  — mirroring SCC. One GET, streams, opens in a new tab. This is the Bitrix hand-off: a folder
  structure survives being dropped into Bitrix; a pile of thumbnails does not.

- **D-04:** **Everything in the Returned tab is READ-ONLY with respect to engineer capture.** It
  reads from `SiteSurveyPhoto` / `WorksheetPhoto` / `DeviceLabelPhoto` / `WorksheetSignoff` live —
  it never copies onto the visit, and it never edits. This is the same rule that Phase 46's D-01
  carry-forward and D-02 office-note both follow, and the reason is the same: a copy goes stale and
  then contradicts its source with no way to tell which is true.

- **D-05:** **Captured serials are first-class.** `DeviceLabelPhoto` holds the label photo and the
  serial with its free-text `captured_by`. Those are the most likely thing to be wanted in Bitrix
  and today the office cannot see them at all. Render them as a list, not buried in the gallery.

- **D-06:** **A reconstructed (backfilled) visit shows its evidence but offers no controls.** Its
  source record has real photos worth seeing. But nobody performed that review, so Accept, Send
  back, Add note and Raise a snag stay hidden — the rule Phase 46 established and proved.

### Claude's Discretion

- Gallery mechanics: thumbnail size, lightbox vs. open-in-new-tab, lazy loading. **No JavaScript
  in the cockpit region** — the fence bans `<script>` and all nine handler attributes, and that ban
  survived Phase 46 deliberately. A plain `<a>` to the full image is acceptable and probably right.
- How the ZIP streams (`ZipArchive` to a temp file vs. `ZipStream`). Note `ZipArchive` already
  appears in `ProjectDrawingController` and `OmManualDocxService`, so there is a house pattern.
- Whether the Returned tab appears at all on a module with no engineer link (Programme, Drawings,
  Programming, Cable schedule). Showing an empty tab on seven of nine modules would be noise.
- Whether a survey's room answers render per-room or as one list.

</decisions>

## Existing Code Insights

- **The fence stands.** `CockpitReadOnlyFenceTest` still bans `<select`, `<script`, all nine
  handler attributes, and the Phase 47/48 affordance strings including **`Download`**. ⚠️ This
  phase ships a download — so the `Download` entry must be lifted **by name, in a commit that says
  why**, exactly as 46-04 lifted `<form`/`<input`/`<button`/`<textarea`. Do NOT delete the entry,
  and do NOT lift `Upload files`, `Mark as sent` or `Issue to client`, which remain Phase 48.
- Both `cockpitRegion()` brackets stay. Both GET row-count invariance tests stay — **the ZIP is a
  GET and must write nothing.**
- `resources/views/layouts/app.blade.php`, `resources/css/app.css` and `tailwind.config.js` must
  stay BYTE-IDENTICAL to `4abd2b24`; asserted by sha256; a mismatch is a STOP.
- All colour is a token on `.cav-brand` in `resources/css/cav-tokens.css` (76 tokens). No hex in
  Blade. Tailwind colour utilities banned. Every class `cav-`-prefixed.
- **Photos are user-uploaded files on a public-token page's sibling data.** Scope every lookup to
  the route-bound `{project}`; never trust a posted or query id; never serve a path derived from
  user input without validating it belongs to this project's visit.
- 24 backfilled visits exist on live. `$isReviewable = ! $isReconstructed && ! $visit->isClosed()`
  is the existing gate — reuse it, do not re-derive it.

</code_context>

<specifics>
## Specific Ideas

- The user's framing: *"they would then download the info and add Bitrix"*. The ZIP is not a
  convenience — it is the integration. Judge it by whether a PM can get a visit's evidence into
  Bitrix without clicking a thumbnail one at a time.
- SCC's own comment on the ZIP button is the acceptance test: *"so the admin doesn't have to click
  each thumbnail one at a time."*

</specifics>

<deferred>
## Deferred Ideas

- **A data summary in the ZIP** (CSV or PDF of room answers, notes and serials). The user chose
  photos-only for now, matching SCC. Worth revisiting once the ZIP is in use.
- **A project-wide download** across all visits — rejected: it mixes trips together and loses the
  "this visit produced this" grouping.
- **Pushing to Bitrix directly** rather than via a download. Not discussed; the download is the
  stated workflow.
- Still open from Phase 46: `D-46-05-01` (the live 500 on roomless worksheet links) and
  `D-46-06-01` (the same-second send-back edge). Neither belongs in this phase.

</deferred>
