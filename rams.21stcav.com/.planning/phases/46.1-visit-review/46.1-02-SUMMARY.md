# Phase 46.1 Plan 02: Photo ZIP + Evidence GETs Summary

**One-liner:** One authenticated GET streams every photo on a visit as a `{Room}/{before|after|label}/`
ZIP for the Bitrix hand-off, a second serves one photo inline for the gallery, and both are proven
inert, traversal-proof, zip-slip-proof and non-enumerable.

## What was built

**`app/Support/Cockpit/VisitPhotoZipBuilder.php`** — `build()` returns the absolute path of a freshly
built temp ZIP; `filename()` returns a `Str::slug()`ged download name; `resolveWithinDisk()` is the
phase's single containment rule, shared with the controller so there is exactly one of them.

- **Shape (D-03):** `{Room}/{before|after|label}/{nnn}-{name}`, with a per-folder sequence so two
  photos sharing an original filename cannot collide. No resolvable room → `Unassigned room/`.
- **Buckets** are membership-resolved against `VisitEvidence::BUCKETS`, never re-derived, so the ZIP's
  folders and 46.1-03's tab headings cannot drift.
- **README.txt** carries the included and skipped counts, the visit reference and the generation time —
  and none of the three capture-audit columns. A short archive explains itself instead of looking like
  data loss. A visit with zero photos still yields a valid archive holding only the README.
- Built **synchronously** to `tempnam()`, then closed — the `ProjectDrawingController` pattern and its
  recorded reason (ZipArchive can emit empty entries when a caller consumes the response mid-build).

**`app/Http/Controllers/ProjectCockpitEvidenceController.php`** — exactly two public actions, `zip()`
and `photo()`. Guards in order: `config('cockpit.enabled')` 404 → `auth()->check()` 403 →
`$visit->project_id === $project->id` 404 → `VisitEvidence::for()` null 404.

**`routes/web.php`** — `projects.cockpit.visits.photos-zip` registered BEFORE
`projects.cockpit.visits.photo` so the literal `photos.zip` segment cannot be shadowed; both inside the
existing `auth` group, both registered unconditionally so `route()` keeps resolving with the flag off.

## The traversal guard

`VisitEvidence` carries RELATIVE paths only and contains no `Storage::` call at all, so this plan is
the one and only place in the phase where a path meets the disk. Both mitigations therefore live at
that call site rather than being assumed of a neighbouring file.

`resolveWithinDisk()`: empty → null; `realpath(Storage::disk('local')->path($relative))` → false or not
a file → null (a missing file is a skipped entry, not a failed download); then
`$candidate !== $root && ! str_starts_with($candidate, $root.DIRECTORY_SEPARATOR)` → **logged at
warning and returned null, never read**. Boundary-safe containment, not a glob prefix that would admit
a sibling directory. The rows were written by an unauthenticated public token page, so
`worksheet_photos.filename` and `device_label_photos.photo_path` are untrusted data even though they
are not in this request.

**The `../../../../.env` proof** is non-vacuous by construction: the test plants a REAL decoy file
carrying `APP_KEY=base64:TRAVERSAL-CANARY-46-1-02` at exactly the location that path resolves to off
the faked disk root, and asserts the file exists and contains the canary BEFORE the request — so
`realpath()` succeeds and `is_file()` is true, and the containment check is the only thing that can
stop the read. Result: `✓ a row whose path escapes the disk root is skipped and its bytes never ship`
— response still **200**, no entry name contains `.env` or `totally-normal`, the canary is absent from
every entry's contents AND from the raw archive bytes, `README.txt` reports the skip, and the
legitimate `Boardroom/after/001-install-01.jpg` is still present. The decoy is removed in `tearDown()`
and is never written over an existing file.

## Zip-slip: every entry name, not the first

`basename()` FIRST (the house rule in `ProjectDrawingController`'s own T-20-02 comment), then
`preg_replace('/[^A-Za-z0-9._-]+/', '-', …)`, a dot-run collapse, `-` trim, leading `.` strip, empty →
`photo-{id}`. Folder segments: separator strip, dot-run collapse, `-` collapse, `.`/`..`/empty →
`Unnamed`.

The test opens the produced archive with a real `ZipArchive` and enumerates **every** `getNameIndex($i)`,
asserting each contains no `..`, no leading `/` or `\`, no backslash at all and no drive letter. A room
named `../../../etc` with an `original_name` of `../../../../etc/passwd` lands at
`etc/after/00N-passwd` — sanitised and still included, not silently dropped. A room named `..` lands
under `Unnamed/`.

## Both GETs write nothing

Eleven tables — `visits`, `install_records`, `install_programmes`, `site_surveys`, `worksheets`,
`snags`, `project_activity_logs`, `site_survey_photos`, `worksheet_photos`, `worksheet_signoffs`,
`device_label_photos` — counted before and after **three** calls to each GET, identical. A separate
test compares the visit row itself, column for column, before and after. `project_activity_logs` is
additionally asserted still at zero: **T-46.1-09 is a ruling, not an oversight**, and it is recorded in
the controller docblock so a later phase that wants the audit must first move that table out of the
fence's invariance list, deliberately and by name.

## No enumeration

`{photo}` is compared against `VisitEvidence::photoIds()` for the route-bound project + visit and is
never passed to `find()`; `{kind}` is membership-resolved against three constants and never echoed.
A photo id from a sibling visit of the SAME project, a photo id from ANOTHER project, and an id that
never existed all 404 with **byte-identical bodies** (asserted by `assertSame()` on the three response
contents). A survey visit asking for a real worksheet photo id is also 404 — a `find()` would have
served it. Hostile `{kind}` values (`<script>alert(1)</script>`, 5,000 chars, `..%2f`, `..`, `SURVEY`)
are 404 and never reflected.

## Response headers

| Route | Headers |
|-------|---------|
| `photos.zip` | `Content-Type: application/zip`, `Content-Disposition: attachment; filename="{slug}.zip"` — the filename goes through `Str::slug()`, so a project named `Acme & Sons / Floor 3` never reaches the header raw |
| `photo/{kind}/{photo}` | `Content-Type: {entry mime or application/octet-stream}`, `Content-Disposition: inline`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox` |

## Deviations from Plan

**1. [Rule 1 - Bug] Dot runs survived the folder sanitiser**

- **Found during:** Task 3, writing the zip-slip assertion
- **Issue:** the planned folder sanitiser replaced separators only, so `../../../etc` became
  `..-..-..-etc`. That cannot traverse — but it still carries `..` into an archive that some other
  tool on the operator's machine unpacks, and it fails the property the plan actually asks for
  ("entry names containing no `..` segment").
- **Fix:** collapse every run of two-or-more dots in the folder sanitiser and in the filename
  sanitiser, then collapse `-` runs and strip a leading `.`. `../../../etc` → `etc`; `..` → `Unnamed`.
- **Files modified:** `app/Support/Cockpit/VisitPhotoZipBuilder.php`
- **Commit:** `47b242b1`

**2. [Scope] RV-04 not marked complete**

absent from the cockpit region; the link that says the word lands in 46.1-04 with the fence lift, so
the fence is edited exactly once and for exactly one reason. Marking RV-04 complete here would be
false.
