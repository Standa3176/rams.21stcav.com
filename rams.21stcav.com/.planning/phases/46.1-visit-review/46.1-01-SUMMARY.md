# Phase 46.1 Plan 01: VisitEvidence + CockpitEvidencePresenter Summary

**One-liner:** A project-scoped, read-live resolver (`VisitEvidence`) and a thin view shape
(`CockpitEvidencePresenter`) that answer "what did the engineer send back on this visit" from the
engineer's own records — writing nothing, copying nothing, and returning none of the three
capture-audit columns.

## What was built

`grep -c "photo" app/Support/Cockpit/CockpitPanelPresenter.php` returned **0** on 2026-09-21. The
app captures six kinds of returned evidence and the cockpit resolved none of it, so a PM could
accept a visit without having seen a single thing that came back. This plan closes that at the
derivation layer; nothing renders yet and no route changed.

**`app/Support/Cockpit/VisitEvidence.php`** — `for(Project, Visit): ?self`, plus `photos()`,
`rooms()`, `serials()`, `signoff()`, `returnedAt()`, `photoIds()` and `sourceMissing()`.

- **Scope (T-46.1-03):** returns null unless `$visit->project_id === $project->id`, and returns
  null when the visit has no source at all. The source is reached through `Visit::source()` —
  never a hand-rolled `find()` on a submitted id.
- **Read live (D-04):** every value is resolved from `SiteSurveyPhoto` / `SiteSurveyRoom` /
  `SiteSurveyRoomQuestion` / `WorksheetPhoto` / `WorksheetSignoff` / `DeviceLabelPhoto` at call
  time. Nothing is copied onto `visits`, denormalised, or memoised between instances.
- **Buckets:** `before` = survey photos, `after` = worksheet photos, `label` = device-label photos.
  D-03 names three buckets; this schema has no before/after column, so the mapping onto the three
  kinds of evidence it does hold IS the meaning — and it is recorded in the class docblock, at the
  definition site, so 46.1-02's ZIP folders and 46.1-03's headings cannot diverge.
- **Paths:** RELATIVE only (`storagePath()` / `photo_path`). No `->absolutePath(` and no
  `Storage::` call exists in the file, so exactly one place in this phase turns a stored path into
  a filesystem path — the ZIP builder and photo route of Plan 46.1-02 (T-46.1-05).
- **Eager loading:** one pass per source kind (`rooms.photos` + `rooms.questions` for a survey;
  `photos` + `signoffs` plus a single device-label query for a worksheet), so Blade stays cheap.

**`app/Support/Cockpit/CockpitEvidencePresenter.php`** — `evidence(Project, Visit): ?array`
returning `has_anything`, `source_missing`, `photos_by_bucket` (fixed before/after/label order,
empty buckets dropped), `photo_count`, `rooms`, `serials`, `signoff`, `returned_at`. It derives
only; it issues no query beyond what `VisitEvidence` already loaded.

## The security rule, and why the proof is not vacuous

`device_label_photos.captured_by` is **not** a person's name. It is an audit field holding a
capture IP plus an actor hash, and it has a leak history:
`2026_07_08_170000_backfill_device_label_photos_captured_by_leak.php` nulled every legacy value
because `PublicWorksheetController::uploadLabelPhoto` had been writing the first 8 hex characters
of the worksheet UUID token into it — a credential fragment in a data column (Audit CR-01). That
migration's own comment records the column "is never read by application code", and this plan
keeps that true. `worksheet_signoffs.ip_address` and `.user_agent` are excluded on the same
grounds: the sign-off surface is the client's **name** and **signature image** only.

The fixture really stores `captured_by = 'ip:203.0.113.9|actor:deadbeef'`, `ip_address =
'198.51.100.77'` and a real `user_agent`, and the test asserts those values are present **in the
database** before asserting they are absent from `json_encode()` of the presenter output. A test
that passed because the fixture left the columns null would prove nothing.

## Tests

`tests/Unit/Cockpit/CockpitEvidencePresenterTest.php` — 16 tests, 87 assertions:

- foreign-project visit → null; sourceless visit → null; force-deleted source → non-null with
  `source_missing` true (the visit still happened)
- survey photos land in `before/`, with the photo array's eight keys pinned as the contract
- unanswered questions omitted but counted (`answered` of `total`); `other_text` only on `other`
- a room that returned nothing is omitted
- worksheet photos + serials + sign-off, with the serial and sign-off key lists pinned so an audit

  room note between two calls
- **write-nothing:** nine row counts identical across three consecutive `evidence()` calls
- **RV-03:** the serialised-output assertion described above
- `photoIds()` returns `[kind, id]` pairs for membership checking in 46.1-02
- every path is relative, and `VisitEvidence` contains no `->absolutePath(` and no `Storage::`

## Deviations from Plan

**1. [Rule 1 - Bug] The absolute-path assertion matched my own docblock**

- **Found during:** Task 2, first gate run (15 passed, 1 failed)
- **Issue:** the test grepped `VisitEvidence.php` for the literal `absolutePath(`, which the class
  docblock legitimately contains where it records the prohibition. A rule you cannot write down is
  a rule that gets undone, so deleting the comment was the wrong fix.
- **Fix:** assert on the CALL form `->absolutePath(` instead, and add a second assertion that no
  `Storage::` facade call exists in the file either — which is a strictly stronger statement of
  T-46.1-05 than the original grep.
- **Files modified:** `tests/Unit/Cockpit/CockpitEvidencePresenterTest.php`
- **Commit:** 09a5b095

**2. [Scope] RV-01/RV-02/RV-03 not marked complete**

## Environment note (not a defect)

The first `-Path tests/Feature/Cockpit` invocation was orphaned when the agent harness moved the
call to the background: three `php.exe` processes sat at ~15s CPU over 50 minutes with the output
file frozen at 982 bytes. A clean re-run of the identical command finished in **246.76s** with
201 passed. The suite is slow (~4 min), not hung. Launch it with `run_in_background: true` from
the start rather than letting a foreground call time out into the background.

**NEVER RUN TWO `artisan test` PROCESSES AT ONCE IN THIS REPO.** The orphaned run eventually
reported — 13.5 hours later — `12 failed, 189 passed`, all twelve in `CockpitVisitActionsTest`
and all of them HTML-render assertions. They are **not** a regression: run solo, that same file
gives `Tests: 35 passed (2759 assertions)`, and the identical full command run solo gives
`201 passed`. The cause is that concurrent runs share `bootstrap/cache` and the compiled-Blade
directory on disk (only the sqlite database is `:memory:` and therefore per-process), so one run
clobbers the compiled views another is asserting against. I triggered this myself by launching
the cockpit suite and the D-06 baseline in parallel to save wall-clock. It cost an hour of
chasing a phantom failure, and it would have been very easy to record those twelve as a real
break. Serialise the gate runs.
