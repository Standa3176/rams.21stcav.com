## The "Electrical is absent entirely" question — resolved by code trace, confirmed by test

`26-VERIFICATION.md`'s round-2 evidence could not establish why no `Electrical`-named row appeared in RAMS 97's rendered register, and explicitly asked this plan to determine which of two causes applied: the tier-2 candidate deduped against the legacy row, or the tier-2 signal simply never fired.

**Traced through every hazard-touching code path in the repo** (`reviewedToRisk()`, `RamsDataBuilderService::assemble()`'s hazard normaliser, `mergeRiskData()`, `DocxBuilderService::buildRiskAssessment()`) — none of them can silently drop a non-empty-named hazard row once it exists in `reviewed_data['hazards']`. There is no code path that removes a row; `tieredRowsNotAlreadyPresent()`'s dedup only ever removes a CANDIDATE that matches an EXISTING name, never an existing row itself.

**The tier-2 "Electrical" candidate (`signal:mains_connection`) requires a narrow, specific phrase set** — `HazardIncludeWhenResolver::TIER2_KEYWORD_SIGNALS['mains_connection']` matches only `mains connection`, `mains disconnection`, `isolate the`, `new circuit`, `electrical connection`, `mains isolation`, `disconnect the existing supply`. A general AV strip-out/install scope narrative is very unlikely to contain any of these — ordinary AV cabling/connection language is covered separately by the ALWAYS-tier `Low voltage AV connections` hazard, not this signal. This is almost certainly correct, INTENDED tier-2 behaviour for 21CQ30960's scope — not a bug, and not this plan's third defect.

**Conclusion:** if the round-2 register genuinely contained no electrical-related row at all (neither an `Electrical Hazards` legacy passthrough nor a new `Electrical` tier-2 addition), the most likely explanation is that `reviewed_data['hazards']` for project 92 simply never carried an electrical entry at the time of that specific regeneration — a fact about that project's review history, not a code defect this plan needs to fix. This cannot be confirmed from this environment: `.env` here is `sqlite`/`local`, disconnected from the live `zoomhardware_21backend_live` replica (same limitation `26-07-SUMMARY.md` documented for the 7->11 delta investigation).

**What this plan proves instead, definitively, by automated test (Task 3):** when an `Electrical Hazards` reviewed row IS present, the fold+rename mechanism this plan adds NEVER drops it — it survives, renamed to `Electrical`, carrying the library's controls and (subject to `score_reviewed`) the library's scores. This settles the code-level half of the question the verification could not: the mechanism is not the cause of any future "Electrical" absence. If live re-verification after deploy still shows no electrical-related row, that is project 92's data history and needs no further Phase 26 code change — record this explicitly in the plan's SUMMARY and `26-VERIFICATION.md` round-3 (if run), do not silently re-open HAZ-02 over it.
</investigation>
