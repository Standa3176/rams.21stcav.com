# Phase 46.5 Plan 06: One Creation, One Outcome Summary

The site survey's wizard now ends with the PM **confirming the spaces, all of them ticked**, and the
final submit produces **the document, the visit and the engineer link in one transaction** — or
**nothing at all**, with the PM told in words which half happened. An install creation produces
**exactly one worksheet**, which is the trap this plan existed to avoid.

## THE ORDERING SHIPPED, PER MODULE — AND WHAT A RETRY DOES

| Module | Ordering | Why | A retry |
|---|---|---|---|
| **site_survey** | **DOCUMENT FIRST** — adopt-or-create the survey, persist its columns, create the visit, `issue()` ADOPTS that same survey | `liveSurveyFor()` uses the same four clauses `activeSurvey()` does, so the row created moments earlier **in this transaction** is the one it finds. There is never a second survey | After a failure: re-enters with no survey (rolled back) and creates one cleanly. After a **partial** success: cannot happen — there is no partial success. On a project that **already had** a live survey: adopts it, count stays 1, token unchanged |
| **worksheet** | **VISIT FIRST**, and the issuer's worksheet **IS** the document | ⚠ `worksheetFor()` has **NO adoption** — every call `Worksheet::create()`s and dispatches a build. Calling `generateFromProject` as well is how ONE click makes TWO worksheets and TWO queued AI builds | After a failure: re-enters with no worksheet and produces exactly one. A **second deliberate** creation produces a second worksheet, unchanged: a first-fix trip and an install trip are different visits |
| **rams / om** | **Document only.** No visit, no link (D-04) | An install's link is the install's. The creator is never called for them; the controller's existing branch is untouched | Unchanged from Plan 05 |

## THE ASSERTION THAT PROVES ONE CREATION YIELDS ONE WORKSHEET AND ONE BUILD

```php
$this->assertSame(
    1,
    Worksheet::where('project_id', $project->id)->count(),
    'ONE creation produced more than one worksheet. `worksheetFor()` has no adoption, '
    .'so the generator must NOT be called as well as the issuer.',
);

Bus::assertDispatchedTimes(BuildWorksheetJob::class, 1);
```

`Bus::fake()` is armed in `setUp()` on **every** path — `phpunit.xml` runs the `sync` connection, so a
real dispatch would run `BuildWorksheetJob` **inline** and make live AI calls from a test. Faking it
is also what lets the guard **count** the dispatches rather than infer them.

## THE DISPATCH IS INSIDE THE TRANSACTION, AND THAT WAS A DECISION

`BuildWorksheetJob::dispatch()` happens inside `VisitLinkIssuer::worksheetFor()`, which **this plan
does not edit** (its adoption rules are load-bearing and already tested, and the scope fence names
it). So the dispatch is **inside** the transaction. That is bounded by two **measured** facts, not by
hope, and both are written in the creator's docblock:

1. **Live runs `QUEUE_CONNECTION=database`** (`.env:39`, `config/queue.php:16`). A dispatch on the
   database connection INSERTs a `jobs` row through the same connection, so it is **inside this
   transaction too and rolls back with everything else**.
2. **Even if it were not**, `BuildWorksheetJob::handle()` resolves the worksheet by id and **returns
   silently when the row is gone** (`app/Jobs/BuildWorksheetJob.php:50-55`). A job that outran a
   rollback finds nothing and does nothing.

The outcome therefore **never claims a file exists**. It says the document was created and its build
is **queued**, which is the truth and is what the existing panel already reports.

## SUCCESS IS STRUCTURALLY IMPOSSIBLE FOR A HALF-RUN

```php
public function successMessage(): ?string
{
    if (! $this->isComplete()) {
```

That is not a convention a caller must remember — it is **the only way** to obtain a success

## WHICH HALF HAPPENED — THE MESSAGE IS NOT ONE GENERIC SENTENCE

| Case | What the PM reads |
|---|---|
| Rolled back cleanly | *"Nothing was created. The document, the visit and the engineer link were all rolled back, so you can safely try again."* |
| The survey existed BEFORE this request and was adopted | *"This project's existing survey was used and left exactly as it was. The visit and the engineer link were NOT created. Nothing else was saved, so you can safely try again."* |

`documentPreExists()` is asked **before the transaction opens**, because afterwards a rollback has
erased the difference between "adopted" and "never existed". No exception text, no stack trace and no
submitted value reaches the screen (T-46.5-06-07); `report($e)` carries the detail to the log.

## THE SPACES STEP — AND THE ASSUMPTION, WRITTEN AT THE CODE

**Default ALL, asserted per space:**

```php
$this->assertMatchesRegularExpression(
    '/<input[^>]*name="visit_rooms\[\]"[^>]*value="'.preg_quote($space, '/').'"[^>]*checked/',
    $form,
    "The space [{$space}] is not offered TICKED on step 3. D-02 says default all.",
);
```

**Where the list comes from, and that it is an inference,** is written at
`CockpitDocumentFormPresenter::PREFILL_PROJECT_SPACES` and again at
`ProjectCockpitController::spaceNames()`, in these words: *"THIS IS A STATED ASSUMPTION, NOT AN
INSTRUCTION FROM THE USER. They were asked TWICE where the confirmable space list should come from
and did not answer, so it was INFERRED."* The source is
`ProjectContextResolver::resolve()['rooms']` — the same source `SurveyService::createFromProject()`
seeds a new survey's rooms from — **falling back to a live survey's own rooms when one is being
adopted**, because those are the spaces that actually exist on the record the engineer opens. The
retired `roomNames()` read the live survey only, and at creation time there is no survey, so it would
have offered nothing at all. **Changing the inference is one method.**

**Default-all is a RENDER decision, never a stored one** — a stored default would persist something
before the final step, which GCW-03 forbids. **Ticking none is an answer**, asserted:
`assertSame([], $visit->rooms_in_scope, 'An empty scope is a stored answer, not a refusal.')`.

**The cost is stated in the Blade:** an all-unticked answer submits no key at all, so a Back-then-Next
or a validation bounce re-ticks everything. Step 3 is the **last** step, so the only way back through
is deliberate, and re-confirming was judged a smaller harm than a hidden companion input that would
put a second control name on the form.

## Deviations from Plan

Four, all mechanical or forced by a measured fact. **Not one relaxes an assertion to make a red test
fit.**

1. **[Rule 3 — blocking] `VisitLinkIssuer` is `final`, so the plan's "bind a double that throws from
   `issue()`" is impossible** — it can be neither subclassed nor Mockery-mocked, and the scope fence
   forbids editing it. The throw is forced instead from `ProjectService::log()`, the **last**
   collaborator inside the transaction, which is **strictly stronger**: by the time it fires, the
   document, the visit **and** the engineer link have all already succeeded. The link-issuance
   failure itself is *also* forced literally, on the install path, through
   `WorkerMonitorService::ensureRunning()` — a collaborator `worksheetFor()` calls **after** creating
   the worksheet, so the rollback has to remove a record the **issuer** created.

2. **[Rule 1 — my own mechanism was wrong] A container rebind could not be undone mid-test.**
   `forgetInstance()` left the earlier resolution in place, so the "retry" half silently re-failed and
   asserted 0 instead of 1. The doubles now read a **static flag**, which `releaseTheFailure()` flips.
   Found by the red test, not by reasoning.

3. **[Rule 3 — blocking] `ProjectCockpitController` had to be edited**, though the plan lists only the
   presenter and the Blade. Its `documentValues()` `match` has **no default arm** by design, so the
   new `visit.` prefix would have thrown `UnhandledMatchError` on every disclosure of the form; and
   the spaces need a resolver. Both are reads. `persist()` in the document controller needed the same
   named arm.

4. **[Rule 2 — the threat register's rule did not fit the control] `visit_engineers.*` is validated
   `string|max:150`, not `exists:labour_resources,id`.** The page renders **names** (LR-04), so an
   `exists` rule on an id would reject every real submission. The creator instead resolves the ticked
   names against **active** labour resources and **drops anything matching none**, so an unknown name
   **cannot become an id at all** — structurally stronger than the rule T-46.5-06-03 named. Asserted
   by `test_an_engineer_name_that_matches_nobody_is_dropped()`.
