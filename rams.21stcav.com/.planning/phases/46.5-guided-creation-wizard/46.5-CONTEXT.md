# Phase 46.5: Guided Creation Wizard - Context

**Gathered:** 2026-09-27
**Status:** Ready for planning

<domain>
## Phase Boundary

The cockpit's one long panel form becomes a **guided, multi-step creation flow**, and a creation ends
with everything that deliverable needs — the document, and where relevant the visit and the engineer
link — in **one pass** rather than three separate acts.

**In scope:** the company name on the cockpit header; the stepped wizard for **Site survey**,
**Install (Worksheet)** and **RAMS**; RAMS generated standalone **or** attached to an install, driven
by the deliverable tick that already exists; a **job summary** entry for RAMS; the **third photo
bucket** so an install records start / during / end; and one creation flow producing document +
visit + engineer link together.

**Out of scope:** the **Review report tab and the new completed-survey report PDF** — those are
**Phase 46.6**, which follows this one; a new RAMS renderer (*"RAMs will use existing RAM process"*);
an O&M wizard; snags (Phase 47); sending anything to a client (Phase 48).

</domain>

## Implementation Decisions

Taken with the user on 2026-09-27, from the live cockpit. Their words, verbatim:

> "on site survey , when I click create , it shows a long form that needs completed can this be
> smaller sections it , dates ,site contact and engineer then next button Then notes (dont need comms
> room) . then next and confirm space being surveys (default all) .Then generate visit ,engineer link
> , pdf/word version all under a signl creation version."

and on RAMS:

> "RAMs is doc creation only ie office user should be able to either gen independant of a visit or as
> part of an install ie are RAMS req ? if ticked yes it follow a similar flow to site survey ie gather
> info NEXT gather more info etc then create rams based on project info , user entered visit info and
> userer enter job summary (if engered or project data) ... created link , pdf/word etc is for install
> rather than survey ie have serial capture , room images start , during/ end etc etc and signoff"

### Decisions

- **D-01:** **The cockpit header carries the client company name.** Small, asked for directly, and
  the header presenter already assembles the masthead.

- **D-02:** **Creation becomes a stepped wizard, and the steps are the user's own.** For **Site
  survey**: (1) dates, site contact, engineer → **Next**; (2) notes — **comms room is NOT on this
  step**; (3) confirm the spaces being surveyed, **defaulting to all**. Then one action produces the
  document, the visit and the engineer link together.

  **No JavaScript.** Step state is query-string (`?module=…&step=2`), exactly as the panel and tabs
  already are, so the back button and a bookmark keep working and the read-only fence is untouched.

  ⚠️ **A half-finished wizard must not create a half-finished record.** Decide and state where a
  part-completed wizard lives — nothing persisted until the final step, or a draft that can be
  resumed. Do **not** leave an engineer link issued against a survey whose rooms were never confirmed.

- **D-03:** **Comms room leaves the office creation form ONLY.** *"dont need comms room"* is about
  this form. It is still captured **by the surveyor on site** via the engineer link, still renders in
  the site-survey Word document (quick task `260926-s7k`), and still rides the **survey→install
  carry-forward**, where an installing engineer reads the surveyor's comms-room access notes.
  **Removing it from those is out of scope and would be a safety regression.**

- **D-04:** **RAMS is document creation only, and may be standalone OR attached to an install.**
  *"office user should be able to either gen independant of a visit or as part of an install."*
  It gets the same stepped flow, but **issues no engineer link of its own** — an install's link is
  the install's.

  Its content comes from three places: **project info** (exists), **user-entered visit info** (the
  wizard), and a **user-entered job summary**, which may be typed or taken from project data.
  ⚠️ **"RAMs will use existing RAM process"** — do **not** write a new RAMS renderer.

- **D-05:** **The "are RAMS required?" tick ALREADY EXISTS — wire it, do not rebuild it.**
  `ProjectDeliverable` / `ProjectDeliverableAudit` came out of phase `260822-esf`, with per-key state
  including `STATE_NOT_YET_DECIDED`. A module whose deliverable is ticked required is what drives the
  flow. **Read `Project::deliverableState()`; it is the safe reader and it is deliberately guarded.**

- **D-06:** **An install records THREE photo stages: start · during · end.**
  Today `WorksheetPhoto::BUCKETS` holds **two** — `start` and `completion`, shipped 2026-09-26 in
  Phase 46.4 (D-03). Add a third.

  ⚠️ **Do NOT rename `completion` to `end`.** Every pre-existing photo was explicitly backfilled to
  `completion` by `2026_09_26_100000`, whose docblock justifies that ruling by quoting the tray's own
  title. A rename is a data migration that falsifies it for no gain. **Add `during`; change the
  LABEL if "End" reads better than "Completion", and say which you chose.**

- **D-07:** **One creation, one outcome.** *"generate visit , engineer link , pdf/word version all
  under a signl creation version."* Finishing the wizard produces all of it. Both the visit model and
  `VisitLinkIssuer` already exist (Phase 46) — **this is wiring, not new machinery.**

  ⚠️ **Partial failure is the thing to design for.** If the document generates and the link does not,
  the PM must be told which half happened. Decide the ordering and what a retry does. **Do not leave
  it to chance and do not report success for a half-run.**

### Claude's Discretion

- Whether a step validates on leaving it or only at the end (prefer per-step — a PM should not reach
  step 3 to learn step 1 was wrong).
- Progress indication across steps.
- Whether Install and RAMS share the wizard component or each carry their own step set. **Prefer
  shared and data-driven** — the panel's contents have changed five times in six weeks; a sixth
  should be a map entry.
- Where the company name sits in the masthead.

</decisions>

<code_context>
## Existing Code Insights

- **No JavaScript and no Alpine in the cockpit region**, by ruling. The fence bans `<script` and nine
  handler attributes; counts stand at **2 / 21 / 9 / 13**, moved only by name. `<select` is banned and
  has survived every form so far — a wizard may finally need one; **lift it by name in the commit
  that ships it, never by deletion.**
- ⚠️ **The stretched-link trap.** `.cav-module` has `position: relative`; `.cav-module__open::after`
  has `inset: 0`. Giving the anchor a `position` **or a `transform`** collapses the whole-row click
  target onto the 28px glyph **with nothing failing**. `CockpitVisualTest` measures the pairing and
  has been proven to bite — run it after every CSS edit.
- ⚠️ **Guard tests match COMMENTS.** Pinned counts (` x-data` 1, ` x-show` 1, ` x-model` 2,
  ` x-cloak` 1, `{!!` 1, `Local blob unreadable` 1) have nearly been broken six times by an agent
  writing a directive name or a pinned string in prose.
- ⚠️ **The suite runs sqlite `:memory:`; live is MySQL.** A migration can pass every gate and be
  impossible on live — the 64-char identifier cap did exactly that on 2026-09-27
  (`SQLSTATE[42000] 1059`), and because MySQL DDL is not transactional the retry then lied with
  "table already exists". **Name every composite index explicitly.**
- **The three protected files** (`layouts/app.blade.php`, `resources/css/app.css`,
  `tailwind.config.js`) stay **BYTE-IDENTICAL to `4abd2b24`**, sha256 via working-tree
  `Get-FileHash`. **A mismatch is a STOP.**
- **`resources/css/cockpit.css` is a Vite entry** — touching it means `npm run build` on deploy.
- `@php` inside a Blade `{{-- --}}` comment **still compiles** — it has cost this milestone twice.

</code_context>

<specifics>
## Specific Ideas

- The acceptance test is the user's standing one, in their words on every version of this page:
  **"simple to use"**, and an earlier design was rejected as **"scary"**. A 13-field wall became
  three short steps because they asked — judge it by whether a PM can finish a survey creation
  without scrolling back.
- **The user found the last defect by clicking, not by reading a test.** The open row would not close
  because the assertion that should have caught it only ever rendered the closed page. Build the
  wizard's tests to render **every** step, and count what they measured.

</specifics>
