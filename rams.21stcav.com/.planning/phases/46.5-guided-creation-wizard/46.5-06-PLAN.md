<ordering_ruling>
## THE ORDERING, DECIDED PER MODULE, AND WHAT A RETRY DOES

**ONE TRANSACTION.** Document row + field persistence + visit + link issuance all sit inside a single
`DB::transaction`, exactly as `storeVisit` already does. A throw anywhere rolls back all of it, so
the answer to *"which half happened?"* is, for everything transactional, **neither — and the PM is
told so in those words.** This is chosen over a compensating-action design because there is nothing
to compensate.

**site_survey** — adopt-or-create the survey, persist its columns, then create the visit and let
`VisitLinkIssuer::surveyFor()` ADOPT THAT SAME SURVEY. It will: `liveSurveyFor()` uses the same four
clauses `activeSurvey()` does, so the survey created moments earlier in this transaction is the one
it finds. **There is never a second survey.** A RETRY after a failure re-enters with no survey
(rolled back) and creates one cleanly. A retry after a PARTIAL SUCCESS cannot happen — there is no
partial success. A retry on a project that ALREADY had a live survey adopts it, which is the
existing, tested behaviour.

**worksheet** — ⚠️ **THE TRAP. `VisitLinkIssuer::worksheetFor()` HAS NO ADOPTION: every call creates
a worksheet and dispatches a build.** So the combined action for an install must **create the visit
FIRST and let the issuer produce the worksheet.** It must **NOT** also call
`WorksheetController::generateFromProject` — doing both is how a single click produces TWO worksheets
and two queued builds. The worksheet module has zero PM-enterable fields (a finding, not an
omission), so there is nothing to persist before the visit. **Assert `worksheets` count === 1 after
one creation.**

**rams** — document only. No visit, no link (D-04). Unchanged from plan 05.

**THE ONE THING A TRANSACTION CANNOT HOLD.** `BuildWorksheetJob::dispatch()` and
`BuildRamsDocumentJob` are QUEUED — the document BUILD happens after commit and can fail later. The
outcome must therefore never claim a file exists. It says the document was **created and its build
queued**, which is the truth, and it is the same thing the existing panel already reports. Say it in
the outcome's own words; do not promise bytes.
</ordering_ruling>
