<the_ruling_to_extend>
From `46.4-06-SUMMARY.md`, shipped and in production:

| Action | Offline | On screen |
|---|---|---|
| ADD a kit row | **Queues** — blobless IndexedDB row | `Queued on this device — uploads by itself when you are online` |
| CORRECT a row already on the SERVER | **Refused** | `Needs a connection`, `aria-disabled="true"`, dimmed, explains on tap |
| MARK a server row deleted | **Refused** | same |
| EDIT a row still IN THE QUEUE | **Works** — device-only write | `Edit` |
| DISCARD a row still IN THE QUEUE | **Works** | `Discard`, no reason asked |

The rule in one line: **no affordance may appear to work offline and silently lose the change, and
the engineer is always told which case they are in.** Whatever this plan chooses must satisfy it.
</the_ruling_to_extend>

  <action>
Add a new, final `<script>` IIFE to the page (after the existing offline-queue IIFE, so nothing
above it moves) headed by a block comment titled exactly
`46.7-01 — WHAT AUTOSAVE DOES WHEN THERE IS NO SIGNAL`. Follow the 46.4-06 precedent: the ruling
lives **at the code**, not as a pointer to a planning file, because that file will not be open when
somebody next wonders.

The ruling, and the four headings the comment must carry verbatim:

**`AUTOSAVE USES localStorage, NEVER THE PHOTO QUEUE`** — the photo queue is schema-frozen at
version 1 and holds real unsent work on real phones; a migration branch does not exist. Autosave
needs none of it: an autosave payload is the **whole** value of one field, so only the latest
matters and a single overwritten key is a complete record. Adding a kind to the frozen store to get
that would risk every pending photo for nothing. This is the same separation the sibling app made
for the same reason.

**`A DRAFT HELD ON THE DEVICE IS A DRAFT THE ENGINEER CAN SEE`** — text that has not reached the
office is shown as not-yet-sent, in words, and it is shown again after a reload. The engineer is
never looking at a field that appears saved and is not.

**`LAST WRITE WINS, AND THAT IS SAFE HERE BECAUSE THE PAYLOAD IS WHOLE`** — a notes field is
replaced, not merged. There is no queued-add-with-no-server-id problem (46.4-06's first reason) and
no two-writers merge to get wrong. That is why this extends the shipped ruling rather than
contradicting it: 46.4-06 refused a MODIFY because a queued row has no identity to modify; a room's
notes are keyed by the room name and always have one.

**`A DRAFT THE SERVER REFUSES IS NEVER DISCARDED`** — if the client signs while a draft is still on
the device, the capture lock refuses it (correctly: the client signed a record). The draft **stays
on the device**, the engineer is shown the server's own sentence, and the text remains selectable so
it can be handed to the office. Silently dropping it would be the exact data loss D-04 exists to
prevent.

End the comment with **the cost stated, not hidden** (the same closing move as 46.4-06): an
undrained draft lives only on that phone and in that browser profile — a wiped phone, a cleared
site-data, or a different device loses it; and a draft refused by the sign-off lock will never
reach the office by itself.

⚠️ The comment must not name any Alpine directive and must not contain the unescaped-echo
delimiter — both are pinned by count and the guards match comments (standing constraint 1).

Then build `DraftStore` in that IIFE — vanilla, no framework, module-private, exposed on `window`
the way `OfflineQueue` is so plan 03 can call it:
- key `'wsDraft_' + {{ (int) $worksheet->id }}` — per worksheet, like the existing `wsState_` key
- `DraftStore.put(fieldKey, value)` → writes `{ value, queuedAt, sent: false }` into one JSON object
  under that key, last-write-wins per `fieldKey`
- `DraftStore.get(fieldKey)` / `DraftStore.all()` / `DraftStore.markSent(fieldKey, sentValue)` /
  `DraftStore.clear(fieldKey)`
- `markSent` clears the entry **only if** the value it is acknowledging still equals the stored
  value; a newer keystroke must not be acknowledged by an older round trip
- every `localStorage` access wrapped in try/catch (Safari private mode throws) and a failure to
  store is **surfaced**, not swallowed — a page that cannot hold a draft must say so before the
  engineer types 200 words into it
- `DraftStore` fires a `worksheet-draft-change` event, mirroring the existing
  `offline-queue-change` idiom, so the indicator in plan 03 subscribes rather than polls

**Do not wire it to any field and do not add any endpoint in this plan.** There is nothing to save
to yet; that is deliberate.

This is the one thing in the phase that cannot be discovered safely. The page is currently honest by
accident: every action is a full-page POST, so a failure is visible. Autosave that fails quietly is
**worse than what exists today** — an engineer types notes in a plant room, sees nothing wrong,
walks out, and the words are gone.

The recommendation is already built and tested (tasks 1 and 2) but **wired to nothing**. Nothing is

    <option id="option-a">
      <name>A — Keep typing offline; the words are held on the phone and clearly marked (RECOMMENDED)</name>
      <pros>
An engineer in a plant room with no signal can still write down what they found — which is exactly
where and when notes get written. Nothing is ever lost quietly: the field shows
`Held on this phone — not sent yet`, it still says that after a reload, and it sends itself when

      </pros>
      <cons>
The words live only on **that phone, in that browser**, until signal returns. A wiped phone, cleared
browsing data, or picking up a different phone loses a note that never got out. And if the client
signs off before the note reaches the office, the office will not get it — the engineer is shown
why and the text stays on screen to read out or copy, but it will not arrive by itself.
      </cons>
    </option>
    <option id="option-b">
      <name>B — Notes need a connection, and say so</name>
      <pros>
Identical to how correcting a kit row already behaves, so engineers have met the idiom. The field
greys out and reads `Needs a connection`. Nothing can ever be held anywhere and then lost, because
nothing is ever held. Cheapest to build and the least to go wrong.
      </pros>
      <cons>
An engineer standing in a basement comms cupboard **cannot write anything down** — in the one place
notes are most worth having. It also gives up the whole point of autosave, which is never having to
think about saving.
      </cons>
    </option>
    <option id="option-c">
      <name>C — Hybrid: keep typing offline, and warn before leaving the page with an unsent draft</name>
      <pros>Option A, plus a browser "you have unsent notes" prompt on navigate-away.</pros>
      <cons>

read past. It narrows the loss window but does not close it, for a noticeably worse feel.
      </cons>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| engineer's browser → `/worksheet/{token}/*` | The token is the ONLY credential. No login, no identity. Everything crossing is untrusted. |
| browser `localStorage` → the page's own DOM | Draft text written by this page, read back and rendered by this page. Attacker-controllable if the device is shared or another script on the origin writes the key. |
| IndexedDB `pending_uploads` → `drain()` | Pre-existing, holds real unsent work. This plan's threat is **disturbing** it, not attacking it. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-46.7-01-01 | Tampering | `localStorage` draft → rendered back into the page | mitigate | The draft is restored into a `textarea` via `.value` and into the indicator via `textContent` — never `innerHTML`. Asserted as a source pattern in task 2. |
| T-46.7-01-02 | Denial of Service | The frozen `pending_uploads` store | mitigate | This plan adds no store, no kind, no index and does not bump `DB_VERSION`. Pinned by four occurrence-count assertions plus the `isBinary` ordering assertion. |
| T-46.7-01-03 | Information Disclosure | A draft left on a shared/lost device | accept | Same exposure class as the photo queue, which already holds site photos on the device by design and shipped on that basis. The token in the URL is a strictly larger exposure on the same device. No new class of secret is stored. |
| T-46.7-01-04 | Repudiation | `markSent` acknowledging a value the engineer has since changed | mitigate | `markSent` clears only when the acknowledged value still equals the stored value; otherwise the newer keystroke stays pending. Asserted in task 2. |
| T-46.7-01-SC | Tampering | npm/pip/cargo installs | mitigate | **No package is installed by this plan** — the page is standalone vanilla JS with no bundler. Nothing to audit; a plan that needs a package here has drifted. |
</threat_model>
