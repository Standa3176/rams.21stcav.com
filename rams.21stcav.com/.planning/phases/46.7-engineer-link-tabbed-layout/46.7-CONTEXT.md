# Phase 46.7: Engineer Link — Tabbed Layout + Autosave - Context

**Gathered:** 2026-09-29
**Status:** Ready for planning

<domain>
## Phase Boundary

The worksheet engineer link stops being a long scroll of `<details>` accordions and becomes a
**tabbed page** in the shape of SCC's PMV engineer link: a **site header**, **one tab per room**, and
a **sticky tab bar** — with **autosave** replacing the full-page POST-and-reload cycle.

**In scope:** the tab structure and the sticky bar; a site/header tab carrying client, reference and
address; autosave of the fields an engineer types; tab state surviving a reload; and the offline
behaviour of autosave.

**Out of scope:** the capture FIELDS themselves — photo stages, labels, additional-kit rows, serial
capture and sign-off all work and are **not** being redesigned; the cockpit; the site-survey link;
the Review report (Phase 46.6); anything in the RAMS pipeline.

</domain>

<decisions>
## Implementation Decisions

Taken with the user on 2026-09-29. Their words:

> "i thought the engineer link was changed to be more like the scc call out/pm it rooms as tabs at
> the bottom with header page with address and contract etc."

and, when offered the phase:

> "proceed with build and autosave"

⚠️ **This is a gap in what was delivered, not a change of mind.** Phase 46.4 was asked to make the
engineer link *"follow the same design as the scc pmv engineer links"*. It delivered the **capture
fields** and never touched the **layout** — 46.4's own boundary names photo buckets and kit rows and
is silent on page structure. The research commissioned at the time described SCC's tabbed layout
accurately and it was not carried into the phase. Recorded so this reads as a correction.

### Decisions

- **D-01:** **Rooms become TABS, not accordions.** Today: **seven `<details>` blocks, zero tab
  markup** (measured). SCC's shape is the model — `data-tab="site"` first, one `data-tab="room-N"`
  per room, then `documents` and `wrap` — with a **sticky tab bar** carrying one button per room and
  a **status class per room** so an engineer sees at a glance which rooms are done.

- **D-02:** **A site header carrying client, reference and address.** These already render, but as a
  single inline strip (`public-show.blade.php:475-477`). They become the header/site tab.

- **D-03:** **Autosave replaces the POST-and-reload cycle** for the fields an engineer types. SCC's
  model: no form submit, a debounced save posting one JSON blob to its own endpoint.

- **D-04:** ⚠️ **AUTOSAVE MUST NOT LOSE AN ENGINEER'S TYPING WHEN THERE IS NO SIGNAL. THIS IS THE
  CENTRAL DESIGN PROBLEM OF THE PHASE AND MUST BE DECIDED, NOT DISCOVERED.**

  Today the page is honest by accident: everything is a full-page POST, so a failure is **visible**.
  Autosave that silently fails offline is **strictly worse than what exists** — an engineer types
  notes in a plant room, sees nothing wrong, navigates, and the words are gone.

  ⚠️ **SCC's autosave has NO offline path** — its IndexedDB queue is photos-only, exactly like ours.
  **So this half cannot be copied; it must be designed.**

  The existing, shipped ruling to extend (Phase 46.4, plan 46.4-06) is: a row already **on the
  server** needs a connection to change; a row still **in the queue** can be corrected on the device;
  and the controls say **`Needs a connection`** rather than appearing to work. **Whatever is chosen
  must satisfy the same rule: no affordance may appear to work offline and silently lose the change.**

- **D-05:** **Tab state must survive a reload.** The page still does full-page reloads for photo
  upload and sign-off, and it already restores `<details>` open-state and scroll position
  (`public-show.blade.php` ~`:2011-2079`). **A tab that resets to room 1 after every photo would be a
  regression against the accordions it replaces.**

### Claude's Discretion

- Tab mechanics: query-string, hash, or JS state — but it must survive a reload (D-05) and work on a
  phone held one-handed.
- Whether the sticky bar scrolls horizontally or wraps on a narrow screen.
- Debounce interval, and what the save indicator says.
- Whether `documents` and `wrap` tabs are worth having here, or are SCC concepts that do not transfer.

</decisions>

<code_context>
## Existing Code Insights

- ⚠️ **THE OFFLINE QUEUE IS SCHEMA-FROZEN AT VERSION 1 AND HOLDS REAL UNSENT WORK.** DB
  `engineer-worksheet`, store `pending_uploads`, keyPath `id`, index `capturedAt`, three kinds
  (`completed`, `label`, `kit`). **`onupgradeneeded` only ever CREATES — it never migrates**, so
  **bumping `DB_VERSION`, changing `keyPath` or touching the index STRANDS EVERY PENDING PHOTO on
  every engineer's phone.** If autosave needs storage, it must be **additive** the way `kind:'kit'`
  was, and the `isBinary` branch must stay **above** the blob append in `drain()`.
- **The capture surface LOCKS at sign-off** (Phase 46.4 D-07), enforced **server-side on eight
  endpoints** before validation. **Any new autosave endpoint must carry the same lock**, or the
  client can change a signed record. Wave 3's reflection test lists every guarded method and **will
  fail if a new write endpoint is not on it** — that is deliberate.
- **Sign-off already refuses to work offline** by explicit design, with a clear message. Room-complete
  and survey-reviewed have no offline path. **Only binaries queue today.**
- **`{!! !!}` is pinned at exactly ONE occurrence**; Alpine occurrence counts are pinned at
  ` x-data` 1, ` x-show` 1, ` x-model` 2, ` x-cloak` 1 — **all five are dead directives on a page
  that loads no Alpine**, kept as pins. ⚠️ **These guards match COMMENTS** — seven near-misses so far.
- **Two pre-existing defects on this page, unfixed:** `uploadPhoto` has **no room-name inclusion
  guard** (its two siblings do), and **re-signing is UI-unreachable since May** because a blanket
  `<fieldset disabled>` wraps the sign-off card on a signed page.
- Engineer-typed text is **unauthenticated input on a page a CLIENT signs** — every echo escaped,
  including JS-built markup.

</code_context>

<specifics>
## Specific Ideas

- **Judge it on a phone, one-handed, in a plant room with bad signal.** That is the only place this
  page is used. A tab bar that needs two hands, or a save that fails quietly, is worse than the
  accordion it replaced.
- The user's own framing for the whole milestone has been **"simple to use"**, and they rejected an
  earlier design as **"scary"**.
- **The accordions are not bad — they are just long.** The win is the sticky bar showing which rooms
  are done, not tabs for their own sake. If a room's status is not visible in the bar, the phase has
  missed its point.

</specifics>
