# Phase 46.7 Plan 02: Tabs, the Sticky Status Bar and Reload Survival Summary

The engineer link's rooms stop being a long scroll of accordions and become tab panels, with a bar
fixed to the bottom of the screen carrying one button per room and **that room's status, written by
the server**. The tab an engineer is on now survives the full-page reload that photo upload and
sign-off still perform.

## The bar shows status, and the status is the server's

This is the thing the phase was for. `46.7-CONTEXT.md`, the user's framing: *"the accordions are not
bad — they are just long. The win is the sticky bar showing which rooms are done, not tabs for their
own sake. If a room's status is not visible in the bar, the phase has missed its point."*

Four statuses, in this precedence, and the precedence is the load-bearing part:

| Status | When | Why it sits where it does |
|---|---|---|
| `unreviewed` | a survey applies to the room and it has not been reviewed | **Outranks everything**, because this is the state that BLOCKS the client's signature. A room reading green while still holding up sign-off would send an engineer off site with an unsignable job. |
| `complete` | `roomCompletedAt` is set | |
| `in-progress` | at least one photo, not complete | |
| `todo` | reviewed-or-no-survey, zero photos | |

Each bar button carries `data-room-status="{status}"` **and** a `tab--status-{status}` class, both
emitted by PHP, plus a text glyph (`⚠ ✓ ◐ ○`) so the status reads without relying on colour — in
sunlight, on a cheap screen, or by an engineer who does not see the hue at all.

**Why server-emitted is a reliability argument and not a style preference:** this page is read in
plant rooms and comms cupboards on a dying signal. A bar whose colours are painted by JavaScript
shows an engineer *nothing* on the one device-and-day where it matters. Asserted against the raw
response body, before any parser and before any script could have run — and asserted in the negative
too, that nothing in the page assigns `data-room-status` from script:

```php
$this->assertStringNotContainsString(
    "setAttribute('data-room-status'",
    $this->source(),
    'A script assigns data-room-status. The status must be the server\'s, so that the bar '
    . 'is correct on a phone with no working JavaScript.',
);
```

## One derivation, consumed twice — and the assertion that the two AGREE

The bar renders after the room panels close, so it cannot read the loop's locals. The obvious move is
to derive status a second time down there, and that is exactly how a bar and a panel come to
disagree. So `$roomTabs` is built **once**, in the page-level `@php` block, and the loop body reads
its own row out of it (`$tab = $roomTabs[$idx];`). There is no second derivation to drift.

**It adds no query.** `$photoCounts` comes from the controller; `$roomsRequiringReview` was already
built out of the one survey query this page makes; `surveyReviewedAt()` / `roomCompletedAt()` read
already-loaded columns. `git diff` adds no `->get(`, no `->first(`, no `::where(` to the view.

`$firstIncompleteIdx` was **moved** from the in-rooms block to page level rather than copied, for the
same reason: the bar has to mark selected the same tab the panel marks active.

The assertion that proves the single derivation is still single — per room, both directions per
status, in `EngineerLinkTabbedLayoutTest::test_each_bar_button_agrees_with_its_own_rooms_panel_head`:

```php
case 'unreviewed':
    $this->assertTrue(
        $unreviewedPill,
        "The bar calls {$target} unreviewed but its panel head shows no "
        . '"Survey not reviewed" pill. One of the two is lying to the engineer.',
    );
    $this->assertFalse(
        $reviewedPill,
        "The panel head for {$target} claims the survey IS reviewed while the bar "
        . 'says it is not — sign-off will block for a reason the engineer cannot see.',
    );
    break;
```

and the loop is itself counted, so a selector that finds nothing cannot pass by checking nothing:

```php
$this->assertSame(
    count(self::ROOMS),
    $checked,
    'The agreement loop ran a different number of times than there are rooms — a selector '
    . 'that finds nothing would otherwise pass this test by checking nothing.',
);
```

The photo count is also asserted equal on both surfaces, because the Mark Room Complete soft gate
reads that number.

## The three landmines planning found, and what happened to each

### 1. `{!! $skipRestoreAttr !!}` — moved verbatim, count still 1

It is the page's one unescaped echo, pinned at exactly **1** in three test files with the literal
string also asserted present in all three. It now sits on the tab panel:

```blade
<section class="ws-tab-panel card{{ $idx === $firstIncompleteIdx ? ' is-active' : '' }}"
         data-tab="{{ $tab['tabKey'] }}"
         data-room-name="{{ $tab['name'] }}"
         id="room-{{ $roomIdSlug }}" {!! $skipRestoreAttr !!}
         role="tabpanel"
```

Its meaning became "do not auto-**activate** this tab" instead of "do not auto-**open** this drawer"
— same intent, same restore handler, so a room the engineer has just marked complete still does not
pull them back into it on reload. Measured after the rewrite: `{!!` **1**, and the literal present.
A new assertion also pins it **to the panel element** by regex, so it cannot drift onto something
else and still satisfy a bare count.

### 3. The `#room-{slug}` anchor — now activates a tab, on load AND on hashchange

The sign-off-blocked banner's "Jump to first unreviewed room →" is an engineer's only way out of a
blocked sign-off. The hash resolver matches `data-tab` first, then falls back to an `id`-to-panel
lookup (which is what `#room-{slug}` is), then gives up silently. `hashchange` is handled as well as
load — tapping that link on an already-loaded page fires `hashchange` and nothing else, so a
load-only handler would have left the link dead.

The contract is asserted here; the browser behaviour belongs to plan 04's checkpoint:

```php
$panel = $xpath->query("//*[@id='room-{$slug}'][@data-tab]");
$this->assertSame(
    1,
    $panel->length,
    'The banner anchor names #room-' . $slug . ' but no tab panel carries that id. The '
    . 'link would silently do nothing and the engineer is stranded at a sign-off they '
    . 'cannot complete.',
);
```

plus `assertStringContainsString("addEventListener('hashchange'", …)` with the message *"Tapping the
jump link on a page that is already loaded would do nothing at all."*

## D-05 — how the tab survives a reload

Folded into the **existing** `wsState_` restore IIFE (one storage key, one five-minute stale guard,
one restore ordering, and the `data-skip-restore` check that handler already performs). **No sixth
script tag was added** — asserted by `substr_count($source, "var KEY = 'wsState_'") === 1`.

Two carriers, because each covers the other's gap:

| Carrier | Survives | Does not survive |
|---|---|---|
| `location.hash`, written with **`history.replaceState`** | a manual refresh; makes a room shareable | the server redirect, which drops the fragment |
| `wsState_.activeTab` in `sessionStorage` | **the server redirect** — this is the carrier that does the D-05 work | a fresh tab (by design, 5-minute stale guard) |

**`replaceState`, never `pushState`** — on a phone the back button must leave the page, not walk back
through nine rooms one tap at a time. Pinned both ways:

```php
$this->assertStringContainsString('history.replaceState', $source, …);
$this->assertStringNotContainsString(
    'history.pushState',
    $source,
    'pushState makes the phone back button WALK the tabs instead of leaving the page — an '
    . 'engineer trying to go back taps nine times and never escapes.',
);
```

Restore precedence, first match wins: **(1)** a hash naming a real panel, **(2)** `activeTab` from a
non-stale record whose panel is not `data-skip-restore="1"`, **(3)** the server-rendered `is-active`
panel. Step 3 is not code — it is the *absence* of code, which is why the page is correct before the
script runs and stays correct if it never runs at all.

The existing scroll restore was **kept** and deliberately not replaced by a scroll-to-top: an
engineer who uploaded a photo half way down a room wants to be back where they were, which is the
whole reason that code exists. Only a deliberate tab tap scrolls to the top.

## Rulings taken, so nobody re-litigates them

**NO `documents` tab and NO `wrap` tab.** 46.7-CONTEXT.md leaves this to discretion; the ruling is
**no**. Reference files are per-project downloads that already live in a drawer inside the rooms, and
the sign-off card **is** the wrap-up — it renders below the panels and is always visible. Two empty
tabs on a phone are two mis-taps.

**The bar SCROLLS horizontally; it does not wrap.** A wrapping bar changes height with the room
count, so the same button sits in a different place on a 3-room job and a 9-room job — and this page
is used one-handed by a thumb that learns one position. `overflow-x: auto` with momentum scrolling
keeps the bar exactly one row tall on every worksheet, and the activated button is scrolled into view
(`block: 'nearest', inline: 'center'`) so room 7 of 9 is never off-screen after a reload.

**The bar renders for a signed worksheet, outside the lock's fieldset.** A signed worksheet is a
record and whoever reads it back still has to navigate it. The bar emits no write (T-46.7-02-03), so
it does not belong inside a fieldset that disables controls — and the tray `data-capture-control`
count is re-asserted at **0** in the signed state so a layout rewrite cannot resurrect a control the
lock removed.

## Deviations from Plan

### Auto-fixed / adjusted

**1. [Rule 3 — blocking] There is no `<main>` element on this page**

- **Found during:** Task 1(c)/(d)
- **Issue:** The plan says to render the bar "after `</main>`" and to give `<main>` bottom padding.
  This view has no `<main>` — the content lives in `<div class="wrap">` and the page-level box is
  `<body>`.
- **Fix:** The bar renders immediately after the `.wrap` closing `</div>` (outside the capture-lock
  fieldset and outside the `empty($rooms)` branch, both deliberately), and the padding reservation
  went on `body`: `body { padding-bottom: calc(4.75rem + env(safe-area-inset-bottom, 0px)); }`. Same
  effect, same reason — without it the client's Sign & Submit button sits under the fixed bar and
  cannot be tapped. Pinned by a regex assertion so it cannot be dropped.
- **Commit:** `8b17dfcf`

**2. [Rule 2 — correctness] `$roomTabs` carries EVERY room, not only the named ones**

- **Found during:** Task 1(a)
- **Issue:** The plan specifies one entry per room **with a non-empty name**. But the room loop
  iterates every room, so an unnamed room would render a panel with no button in the bar — an
  orphan panel, a room an engineer cannot reach — and it would break the bijection the plan's own
  task 3 requires.
- **Fix:** Every room gets a row, carrying a `hasName` flag. The name falls back to
  `'Unknown Room'`, matching what the panel head already rendered. `$firstIncompleteIdx` still skips
  unnamed rooms, exactly as the code it replaced did. `$roomsTotal` is the row count.
- **Commit:** `8b17dfcf`

**3. [scope] Tasks 1 and 2 landed in one commit**

- Both tasks edit interleaved regions of the same single file, and the task-1 half alone would have
  left `EngineerLinkInstallCaptureEndToEndTest` red (landmine 2 is repaired in the same commit).
  Splitting would have produced a knowingly-red commit rather than a smaller one. Task 3 is its own
  commit. Recorded rather than glossed.
