### ⚠️ CORRECTION TO THE "WAVE 2 ONLY" FRAMING — verified, not assumed

The split is usually described as *"wave 2 is deployed, waves 1 and 3 are not."* **That is not
what is on live, and it could not be.** Wave 1 and wave 2 edit **the same file**
(`resources/views/worksheets/public-show.blade.php`) and wave 1's commits are **ancestors** of
wave 2's. Any git-based deploy of wave 2 necessarily carried wave 1 with it. Verified
first-hand at wave 2's tip:

```
$ git show 840c163d:…/public-show.blade.php | grep -c "window.DraftStore"
1        ← wave 1 IS there
$ git show 840c163d:…/public-show.blade.php | grep -c "data-room-notes"
0        ← wave 3 is NOT
```

**So live today = waves 1 + 2.** That is harmless — `DraftStore` on live is dead code with no
caller, no listener, no `fetch` and no storage write until something calls it. But a deployer
reasoning about "what changed" from the wrong baseline will misread the diff.

**Therefore what THIS deploy actually adds is wave 3 and nothing else:** the per-room notes
box, the `POST /worksheet/{token}/rooms/{roomName}/notes` endpoint, the
`worksheet-notes-write` limiter, and the first caller `DraftStore` has ever had.

**What an engineer will SEE that they cannot see today:** a `📝 What you found in this room`
textarea in every room tab, above the additional-kit list, that saves itself and reports
`Held on this phone — not sent yet` / `Saved HH:MM` / the sign-off lock's sentence. Nothing

## 3. THE DEPLOY

### Push — from Windows, and to the RIGHT remote

```bash
git push live feat/worksheet-classifier-universal
```

⚠️ **`origin` IS A DIFFERENT REPOSITORY.** Verified on this machine:

```
live        https://github.com/Standa3176/rams.21stcav.com.git
rams-live   https://github.com/Standa3176/rams.21stcav.com.git
origin      https://github.com/Standa3176/21st-Opps-Doc-Tool.git   ← THE WRONG REPO
```

A bare `git push` sends RAMS code to `21st-Opps-Doc-Tool`. It also means **"ahead of origin"
counts lie** — they are measured against a repository this application is not deployed from.
Always name the remote and the branch.

### On the VPS

```bash
# 1. AS stcav. NEVER AS root. See the warning below.
sudo -u stcav -H bash -lc '
  cd /path/to/rams.21stcav.com &&
  git fetch live &&
  git checkout feat/worksheet-classifier-universal &&
  git pull live feat/worksheet-classifier-universal
'

# 2. MANDATORY — the engineer-link view changed heavily (tabs, bar, site tab, notes box).
sudo -u stcav -H php artisan view:clear

# 3. The route table and a rate limiter changed (a new named route + a new limiter).
sudo -u stcav -H php artisan route:clear
sudo -u stcav -H php artisan config:clear

# 4. NOT NEEDED — do not run:
#    php artisan migrate      (no migrations — §2)
#    npm ci && npm run build  (no Vite input changed, page has no @vite — §2)
```

`route:clear` and `config:clear` are in the list because a cached route table will **404 the
new notes endpoint** and a cached config will not know the `worksheet-notes-write` limiter —
in both cases the notes box would appear on the page, accept typing, and then fail every save.
That failure mode is *visible* (the field would sit on `Held on this phone — not sent yet`
forever), but it would look like the offline bug the phase exists to prevent.

### ⚠️ RUN IT AS `stcav`, AND WHY "it worked as root last time" IS THE WARNING

**Deploy as `stcav`. Never as root.**

The last deploy was run **as root and the pull SUCCEEDED**, where an earlier one had been
refused with git's *"detected dubious ownership in repository"*. **Something changed between
those two deploys, and the one that succeeded is the one to be suspicious of** — a refusal is
loud and harmless; a success that should have been refused means the ownership guard is no
longer protecting the checkout.

The failure mode to look for is **root-owned objects left inside the repository or
`storage/`** by that root run. They do not break anything immediately; they break the *next*
`stcav` deploy, or worse, they make `php-fpm` (running as `stcav`) unable to write a cache or
a log — which surfaces as a 500 on a page that was fine a minute ago.

Check, and fix if needed:

```bash
# Anything in the repo not owned by stcav?
find /path/to/rams.21stcav.com -not -user stcav -printf '%u %p\n' 2>/dev/null | head -50

# Most likely places, if the above finds anything:
sudo chown -R stcav:stcav /path/to/rams.21stcav.com/storage
sudo chown -R stcav:stcav /path/to/rams.21stcav.com/bootstrap/cache
sudo chown -R stcav:stcav /path/to/rams.21stcav.com/.git

# Only if you are confident nothing else lives under that path:
sudo chown -R stcav:stcav /path/to/rams.21stcav.com
```

Do **not** "fix" a dubious-ownership refusal with `git config --global safe.directory` — that
silences the guard instead of correcting the ownership that tripped it.

## 4. POST-DEPLOY CHECKS — ON A PHONE, NOT A DESK

The first four are the ones a laptop cannot judge, and they are the checkpoint's own steps.

1. **Open a real engineer link on a phone.** The bottom bar shows one button per room with
   `⚠ / ✓ / ◐ / ○` and a photo count. Every room has a button.
2. **⚠️ Airplane mode → type two sentences in a room's notes box.** It must say
   *"Held on this phone — not sent yet"*. **Reload.** The words must still be in the box and
   it must still say held. **Airplane mode off.** It must send itself and flip to
   *"Saved HH:MM"*.
3. **Photo upload does not dump you in room 1.** Go to the **last** room, take a photo, and
   confirm the page comes back on that room.
4. **The bar does not cover the buttons.** Scroll to the very bottom of the longest room and
   of the sign-off card. `Mark Room Complete` and `Sign & Submit` must both be tappable.
5. **A signed worksheet still reads back.** Notes render as static text, tabs still switch,
   and there is no editable control anywhere.
6. **Watch the log for the new endpoint.** `tail -f storage/logs/laravel.log` while saving a
   note; a 419/404/500 here means step 3 of the VPS commands was skipped.

## 5. ROLLBACK

Nothing to undo at the schema level (§2), so a revert is sufficient and complete.

**To pull the whole phase back** (returns the engineer link to the `<details>` accordions):

```bash
git revert --no-commit 80ea7aff 6b17488e 40306b2d 7f1b31ea 739936de 915d5569 8b17dfcf ef07a73f 2145646b
git commit -m "revert: phase 46.7 engineer link tabbed layout"
```

**To pull back ONLY the notes box** — which is what happens if the checkpoint's question 8
comes back *"I wanted the tabs and the bar, not a new field"*. This is the more likely
rollback and it is clean:

```bash
git revert --no-commit 6b17488e 40306b2d 7f1b31ea 739936de
git commit -m "revert: the 46.7 per-room notes box and its endpoint"
```

That leaves the tabs and the sticky bar in place and returns `DraftStore` to being unwired —
exactly the state live is in today. **No existing capture field was changed to make room for
the notes box**, so nothing else has to be put back: the photo trays, the tray caption, the
kit rows, serial capture, Mark Reviewed, Mark Room Complete and sign-off are all untouched by
wave 3.

Rows already written to `pre_install_confirmations['room_notes']` are **left in place** by
either revert. They are inert — nothing reads that key once the view is reverted — and they
are the only record of what an engineer typed, so they must not be deleted to tidy up.

After any revert: `php artisan view:clear && php artisan route:clear && php artisan config:clear`.
