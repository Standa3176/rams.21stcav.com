# Phase 22.1: RAMS Scope/Room-Data Consolidation — Context

**Gathered:** 2026-05-13
**Status:** Ready for planning

<domain>
## Phase Boundary

Eliminate the field-duplication across the 3-stage RAMS pipeline (`form_data` → `reviewed_data` → `generated_data`). The 2026-05-13 audit identified 5 overlapping "scope/works/space narrative" fields at 3 granularities, all storing similar text in different JSON paths with inconsistent fallback chains.

**In scope (audit Clusters 1, 2, 5):**
- Cluster 1: Project-wide narrative consolidation — `works_description` writer rule, `method_statement_notes` merge, `works_bullets` deprecation
- Cluster 2: Per-room narrative consolidation — drop `description` / `summary` / `scope` fields, backfill `summary → works_summary`
- Cluster 5: Dead-path removal — `RamsGeneratorService`, `RamsPrompt`, `reviewed_data.project.overview` round-trip, related test scaffolding
- One-time backfill: `summary → works_summary` on existing `reviewed_data` rows
- Regression: byte-equivalence golden-file test ensuring existing data renders unchanged

**NOT in scope (defers to Phase 22.2):**
- Cluster 3: cross-document `Project.works_description` propagation rules (RAMS + Worksheet + Mini-OM + Survey)
- Cluster 4: Survey ↔ RAMS one-way sync direction (requires feature flag, in-flight workflow caution)

**Backward-compat invariant:** `generated_data` JSON shape stays identical. Already-rendered RAMS docs render byte-identical. The cleanup is on INPUT-side duplication only.

</domain>

<decisions>
## Implementation Decisions

### Locked decisions (discussed)

- **D-01 — Drop `room_overviews[*].description` field entirely.** Stop generating it via `RoomOverviewSummaryPrompt`. Use the engineer-typed `overview` field as the prose source for `MethodStatementPrompt` input. Rationale:
  - CLAUDE.md locks the principle "AI output must be reviewable" — `description` is invisible to engineers (no edit UI exists at `project-packages/review.blade.php`).
  - The engineer-typed `overview` is already a human-authored prose paragraph; using it as method-statement input maintains AI input quality without an extra AI call.
  - Net effect: -1 AI call per room (cost + speed win), -1 invisible AI output, simpler `room_overviews[]` shape.
  - `RoomOverviewSummaryPrompt` now produces ONLY `summary`/`works_summary` bullets — its single remaining output.

### Carry-forward from earlier phases (locked, not re-discussed)

- **D-LOCK from Phase 22:** Backfill commands ship as artisan with `--apply` flag, dry-run-default, with 4 outcome categories (matched / skipped / already-set / no-match). This phase's `summary → works_summary` backfill follows the same pattern.
- **D-LOCK D-10 invariant (Phases 21+22):** v1.3 surfaces must continue rendering legacy data unchanged. Phase 22.1 extends this: existing `reviewed_data` records render byte-identical PDFs before and after the cleanup. Golden-file regression test in `tests/Feature/RamsRenderRegressionTest.php`.
- **CLAUDE.md:** "AI is ONLY allowed for formatting and method statement structuring — never for inventing scope/equipment/design." Phase 22.1 confirms this by removing AI prompts that toe the line (`WorksBulletsPrompt` per D-08 below). `RamsPrompt` (the legacy whole-document AI prompt) is removed per D-07 because its schema would VIOLATE this constraint if ever called (it AI-generates hazards.controls + regulations).
- **PSR-12, ASCII art comment dividers in services, named log prefixes ("RamsBuilderService: ..."), no emojis in code.**

### Claude's Discretion — sensible defaults the audit prescribes

These were not selected by the user as gray areas to discuss; downstream agents follow the audit's recommendation.

#### Cluster 1 defaults (project-wide narrative)

- **D-02 — Stop auto-seeding `Project.works_description` from QuoteWerks PDF.** `ExtractQuoteJob:124,133` removes the `works_description => $extracted['overview']` assignments. The raw QuoteWerks overview text still appears in the review form as a starting-value suggestion in the `scope_of_works` (formerly `method_statement_notes`) textarea, but is NOT persisted to `Project.works_description` until the PM approves the review form. Eliminates the path where sales-style prose from years-old quotes leaks into the manual RAMS create form default.
- **D-03 — `method_statement_notes` MERGES into `reviewed_data.scope_of_works`.** Two names for the same thing. The "PM INSTRUCTIONS" separator-suffix in `MethodStatementService:144` reads from `scope_of_works` directly. `ProjectPackageReviewController:348` mapping (`method_statement_notes` → `Project.works_description`) is removed; `scope_of_works` becomes the canonical project-wide scope paragraph.
- **D-04 — Deprecate the project-wide `works_bullets` textarea.** No RAMS consumer reads it. The Survey's "Planned AV Works" drawer rewires to derive from `reviewed_data.scope_of_works_bullets` (the equipment-keyword-derived computed field) or from the union of `room_overviews[*].works_summary`. Remove the textarea from `project-packages/review.blade.php:449-469`.
- **D-05 — `works_overview` (2-3 sentence executive summary) stays but is explicitly DERIVED from `scope_of_works` in one AI call.** `ScopeOfWorksPrompt:63` already returns both fields in one JSON; just stop fetching them independently.
- **D-06 — `scope_of_works_bullets` computed once at approve-time and persisted on `reviewed_data`.** Currently recomputed on every PDF render via `RamsComplianceUpgradeService::upgradeScopeOfWorks()` which can drift if the equipment list changes between approve and regenerate. Approve-time persistence locks the bullets, removes the per-render heuristic, and protects the byte-equivalence invariant.

#### Cluster 2 defaults (per-room narrative)

- **D-07 — Drop `room_overviews[*].summary` (legacy duplicate of `works_summary`).** One-off backfill artisan command `php artisan rams:backfill-room-overview-summary` follows the Phase 22 pattern: dry-run-default + `--apply`, 4 outcome categories (`backfilled` / `already-set` / `both-set-no-action` / `neither-set`). Idempotent.
- **D-08 — Drop `room_overviews[*].scope` from the fallback chain.** Nothing writes it (verified by audit grep). Remove from `pdf/rams.blade.php:834` and `RamsComplianceUpgradeService:71`.

#### Cluster 5 defaults (dead-path removal)

- **D-09 — Drop `reviewed_data.project.overview`.** Round-tripped but no consumer reads it. Remove from `RamsReviewDataService::normaliseProject():113`.
- **D-10 — Delete `RamsGeneratorService` and `RamsPrompt`.** Legacy alternate generator + whole-document AI prompt. `RamsPrompt`'s schema AI-generates hazards.controls + regulations which would violate the CLAUDE.md constraint if ever called. Verified by grep: `RamsPrompt::class` only referenced in `RamsGeneratorService:252`. Both files delete cleanly. Final verification: confirm no test or out-of-tree script invokes them before deletion (`app/scripts/generate_rams_docx.js` mentioned as possibly dead — check).
- **D-11 — Drop `WorksBulletsPrompt`.** Its consumer (`works_bullets` textarea) is deprecated per D-04. No remaining caller.

#### Regression strategy (audit recommendation)

- **D-12 — Golden-file PDF byte-identity test.** Same pattern as Phase 22's `CableScheduleXlsxRegressionTest`. Pick 3-5 existing `reviewed_data` fixtures (covering manual-form RAMS, quote-import RAMS, and survey-derived RAMS) → render PDF before changes → render PDF after changes → assert `hash_file('sha256', $a) === hash_file('sha256', $b)`. Skip cleanly when PDF runtime deps absent (puppeteer / D2 binary) following the `is_file($binary) || is_executable($binary)` pattern locked in Phase 22 PdfRenderService.
- **D-13 — Structural JSON diff for `reviewed_data` shape.** Complementary to the byte test: a unit test asserts the legacy → migrated `reviewed_data` JSON has the expected keys removed (`project.overview`, `room_overviews[*].summary`, `room_overviews[*].scope`, `room_overviews[*].description`) and no unexpected drift on retained keys.

<specifics>
## Specific Ideas

- **Backfill command name:** `php artisan rams:backfill-room-overview-summary` (mirrors `cables:backfill-port-fks` naming from Phase 22).
- **Backfill outcome categories:** `backfilled` (had `summary`, was empty, copied to `works_summary`) / `already-set` (`works_summary` was non-empty, no overwrite) / `both-set-no-action` (both keys non-empty — log a warning so a human can pick which truth to keep) / `neither-set` (no source data, skip).
- **Golden-file regression fixtures:** pick at least one of each — (1) manual-form RAMS pre-Phase-22.1, (2) quote-import RAMS pre-Phase-22.1 with all 4 per-room narrative fields populated, (3) survey-derived RAMS. Snapshot the PDF byte hash before and after. Test SKIPS cleanly when puppeteer/D2 not installed (same skip pattern as Phase 22).
- **`scope_of_works_bullets` persist trigger:** `ProjectPackageReviewController::approve()` writes the bullets into `reviewed_data.scope_of_works_bullets`. `RamsComplianceUpgradeService::upgradeScopeOfWorks()` becomes a no-op when the field is already persisted (read-through cache pattern: only compute when missing).
- **Method-statement prompt input change (D-01):** `MethodStatementService:267` currently passes `room_overviews[*].description` as the prose input. Switch to `room_overviews[*].overview`. If `overview` is empty, fall back to `room_overviews[*].works_summary` joined as a paragraph (bullets → prose at prompt-input time only, not persisted).
- **Verification ratchet — confirm `RamsPrompt` is truly dead before delete (D-10):** `grep -r "RamsPrompt" app/ tests/ database/seeders/` should return zero hits AFTER removing `RamsGeneratorService.php` (because that's the only reference). Also `grep -r "RamsGeneratorService" app/ tests/` — must be zero hits before deleting `RamsPrompt`.
