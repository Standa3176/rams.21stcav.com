# Phase 22.1: Code Review Report

**Reviewed:** 2026-05-13T10:00:00Z
**Depth:** standard
**Files Reviewed:** 32
**Status:** issues_found

## Summary

Phase 22.1 (RAMS Scope/Room-Data Consolidation) ships a well-structured refactor: per-room narrative collapses to exactly 4 canonical keys (`room` / `overview` / `works_summary` / `solution_type_id`), the project-wide scope flows through a single canonical store (`reviewed_data.scope_of_works` + `scope_of_works_bullets`), three dead-path classes (`RamsGeneratorService`, `RamsPrompt`, `WorksBulletsPrompt`) are deleted and CI-guarded, and a dry-run-by-default backfill artisan command migrates legacy `summary` → `works_summary` with documented idempotency.

The CI guard suite is strong: `Phase22_1InvariantGuardTest`, `ScopeConsolidationGuardTest`, `DeadPathRemovalGuardTest`, `ReviewedDataStructuralDiffTest`, and three byte-equivalence regression fixtures (manual-form, quote-import, survey-derived) collectively pin every Phase 22.1 invariant. The T-22.1-05 SQL-injection mitigation is correctly implemented (PHP `(int)` cast on the `rams_id` arg) and end-to-end tested (`test_t22_1_05_sql_injection_via_rams_id_arg_neutralised_by_int_cast` asserts `Schema::hasTable` survives the payload). The Plan 06 read-through cache pattern (approve-time persist → render-time short-circuit) is clean and covered by both unit and structural tests.

The findings below are concentrated in one area: **the read side of the canonical 4-key schema is enforced (`RamsReviewDataService::normaliseRoomOverviews` strips legacy keys), but several write sites still emit the legacy `summary` and `description` keys**. The normaliser hides this on read, but the persisted JSON in `extracted_data` continues to accumulate dead keys on every save. After Plan 03's backfill artisan runs in production, these write sites will silently re-introduce the very keys the backfill cleaned up — creating a stable contradiction that future maintainers may misread.

## Warnings

### WR-01: review.blade.php reads `$ro['summary']` without null guard — undefined array key warning after normalise()

**File:** `resources/views/project-packages/review.blade.php:497`
**Issue:** The blade renders:
```blade
<input type="hidden" name="room_overviews[{{ $ri }}][summary]"
       value="{{ old("room_overviews.{$ri}.summary", $ro['summary']) }}">
```
After Phase 22.1 D-07, `RamsReviewDataService::normaliseRoomOverviews()` (line 198-207) emits exactly 4 keys — `room`, `overview`, `works_summary`, `solution_type_id`. The controller calls `$this->reviewDataService->normalise($raw)` at `ProjectPackageReviewController.php:293` and the normalised payload is what the blade receives. Therefore `$ro['summary']` is an undefined array key on every render.

Under PHP 8.2 this raises `Warning: Undefined array key "summary"` per row. Other reads on the same row (line 512 `$ro['solution_type_id'] ?? ''` and line 540 `$ro['description'] ?? ''`) correctly use the null-coalesce guard, so the inconsistency is a clear oversight.

**Fix:**
```blade
<input type="hidden" name="room_overviews[{{ $ri }}][summary]"
       value="{{ old("room_overviews.{$ri}.summary", $ro['summary'] ?? '') }}">
```
Even better — if the hidden `summary` input is dead per D-07 (the field is no longer round-tripped through the canonical schema), remove the hidden input entirely along with the dead `description` textarea (see IN-01).

## Info

### IN-01: review.blade.php still posts dead `summary` + `description` form fields — saves re-introduce legacy keys

**File:** `resources/views/project-packages/review.blade.php:496-497, 536-540`
**Issue:** The form still emits two dead fields per row:
- A hidden `<input name="room_overviews[{i}][summary]">` (line 496-497)
- A textarea `<textarea name="room_overviews[{i}][description]">` (line 536-540) — "Room Description (O&M prose paragraph)"

`ProjectPackageReviewController::parseReviewPayload()` (line 1020-1037) writes BOTH keys back into the request payload, which is then merged into `extracted_data` via `array_merge($package->extracted_data ?? [], $payload)` at line 312. While `RamsReviewDataService::normaliseRoomOverviews()` strips both keys on read, the persisted JSON in `project_packages.extracted_data.room_overviews[]` continues to accumulate `summary` and `description` keys on every save.

This is exactly the data shape the Plan 03 backfill artisan (`rams:backfill-room-overview-summary`) is designed to clean up. After production migration, the next save through the review form will re-introduce the legacy keys — undoing the migration's "schema is now 4 canonical keys" guarantee for any record the PM touches. The structural-diff test (`ReviewedDataStructuralDiffTest`) only exercises the read path through `RamsReviewDataService::normalise()` and therefore does not detect this.

A second symptom: the AJAX endpoint `ProjectPackageReviewController::generateRoomSummary()` (line 558-562) still returns `description` in its JSON response (with the comment "for any existing front-end consumer"), and the blade JS at line 1814-1818 still consumes it. Both ends of the dead round-trip are still wired.

**Fix:**
1. Remove the hidden `summary` input (line 496-497).
2. Remove the `description` textarea block (line 535-540).
3. Drop `summary` and `description` from `parseReviewPayload()`'s `roomOverviews[]` build (line 1028-1037).
4. Drop the `description` JSON response field from `generateRoomSummary()` (line 547-561).
5. Add a guard test in `ReviewedDataStructuralDiffTest` asserting that after `$package->update(['extracted_data' => ...])` from a real form POST, the stored `room_overviews[N]` has exactly the 4 canonical keys.

### IN-02: ExtractQuoteJob scaffolds dead `summary`/`description` keys into newly-extracted room_overviews

**File:** `app/Jobs/ExtractQuoteJob.php:302-314`
**Issue:** When the AI hasn't produced `room_overviews`, the scaffold writes:
```php
$ai['room_overviews'] = array_values(array_map(
    static fn (string $roomName): array => [
        'room'             => $roomName,
        'overview'         => '',
        'works_summary'    => '',
        'solution_type_id' => '',
        'summary'          => '',
        'description'      => '',
    ],
    (array) $ai['rooms']
));
```
Per Phase 22.1 invariant DATA-02 (exactly 4 canonical keys per room), newly-extracted records should write the canonical 4-key shape from the start. These dead keys propagate into `project_packages.extracted_data` until a PM save round-trips them through the (also-leaky) review form (IN-01). New imports done after the backfill artisan has run still ship with the legacy shape baked in.

A minor consistency issue: `solution_type_id` is set to `''` (empty string) here, but `RamsReviewDataService::normaliseRoomOverviews()` at line 203 coerces via `(int) (...) ?: null` — both `''` and `0` collapse to `null`. The shape mismatch is harmless but indicates the scaffold was not updated when the canonical contract tightened in Plan 03.

**Fix:** Drop `summary` and `description` from the array literal; coerce `solution_type_id` to `null`:
```php
static fn (string $roomName): array => [
    'room'             => $roomName,
    'overview'         => '',
    'works_summary'    => '',
    'solution_type_id' => null,
],
```

### IN-03: generateSurveyRooms writes legacy `summary` + `description` into expanded room_overviews

**File:** `app/Http/Controllers/ProjectPackageReviewController.php:781-790`
**Issue:** When the PM clicks "Generate Rooms" to expand `Small Room` → `Small Room 1` … `Small Room 9`, each new `room_overviews[]` entry is built as:
```php
$roomOverviews[] = [
    'room'             => $resolveName($i),
    'overview'         => $sourceOverview,
    'works_summary'    => $sourceWorksSummary,
    'summary'          => '',
    'description'      => $sourceDescription,
    'solution_type_id' => $sourceSolutionId,
];
```
Same data-shape regression as IN-02. Worse: `description` is populated from `$sourceDescription` (lines 733, 748), so the expanded rooms each carry a legacy AI prose paragraph that nothing downstream reads after Phase 22.1. The PM's manually-edited room (the source) doesn't have `description` set in the canonical store, but the auto-generated copies do — asymmetric data within the same record. The structural-diff guard does not fire because `normaliseRoomOverviews()` strips the keys on read.

**Fix:**
1. Drop `summary` and `description` from the literal at lines 786-787.
2. Remove the `$sourceDescription` source-trace logic at lines 733, 748 (it has no downstream consumer once the write is gone).

### IN-04: RoomOverviewSummaryService::summarize() writes to legacy `summary` key, not canonical `works_summary`

**File:** `app/Services/RoomOverviewSummaryService.php:67-72, 81-84`
**Issue:** The service's own docblock (lines 16-21) states the single AI output is `summary`, but Phase 22.1 D-07 makes `works_summary` the single canonical persistence key. The service writes:
```php
return array_map(function ($r) use ($summaries) {
    // ...
    if ($room !== '' && isset($summaries[$room])) {
        $r['summary'] = $summaries[$room]['summary'] !== ''
            ? $summaries[$room]['summary']
            : $this->fallbackSummary($overview);
    }
    // ...
}, $roomOverviews);
```
Callers then write the returned rows back into `extracted_data['room_overviews']`:
- `ExtractQuoteJob::generateContentPack()` at `app/Jobs/ExtractQuoteJob.php:197, 230` — every newly-imported quote now writes `summary` (legacy) instead of `works_summary` (canonical).
- `RamsComplianceUpgradeService::ensurePerRoomBullets()` at line 144-170 calls `summarize()` and correctly pairs results into `$rooms[$roomIdx]['works_summary']` from `$result['summary']` — but only at PDF-render time, not at extraction time.
- `ProjectPackageReviewController::generateRoomSummary()` at line 546 reads `$results[0]['summary']` directly.

Net effect: the migration's "after the backfill, every record has `works_summary` populated" guarantee is invalidated by every new quote import, because the extraction-time write path uses the legacy key. The backfill artisan would need to be re-run periodically — exactly the situation Phase 22.1 was designed to eliminate.

**Fix:** Treat `works_summary` as the canonical key throughout. Two equivalent options:

Option A (rename the output key in the service):
1. Change `$r['summary'] = ...` to `$r['works_summary'] = ...` in `summarize()` (lines 67, 71, 82).
2. Update `RamsComplianceUpgradeService::ensurePerRoomBullets()` line 168 from `(string) ($result['summary'] ?? '')` to `(string) ($result['works_summary'] ?? '')`.
3. Update `ProjectPackageReviewController::generateRoomSummary()` line 546 from `$results[0]['summary']` to `$results[0]['works_summary']`.

Option B (have callers translate):
- Keep the service's internal `summary` key (it mirrors the AI's JSON output) but have each caller pair it explicitly to `works_summary` before persistence — exactly what `ensurePerRoomBullets` already does. Apply the same pattern to `ExtractQuoteJob::generateContentPack` and `ProjectPackageReviewController::generateRoomSummary`.

Option A is cleaner; Option B is less disruptive. Either way, lock with a test fixture in `BackfillRoomOverviewSummaryCommandTest` asserting that re-running `ExtractQuoteJob` after a backfill does not re-introduce the legacy `summary` key.
