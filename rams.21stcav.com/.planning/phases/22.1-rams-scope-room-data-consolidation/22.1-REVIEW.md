# Phase 22.1 (Plan 07): Code Review Report

**Reviewed:** 2026-05-13
**Depth:** standard
**Files Reviewed:** 5
**Status:** issues_found

## Summary

Plan 07 was a focused gap-closure plan that did three correct things:

1. **Stripped the dead `summary` hidden input + `description` textarea** from `resources/views/project-packages/review.blade.php` (both the static row and the JS row-template) and removed the orphan `data.description` consumer branch in `generateRoomSummary()`.
2. **Converged four `ProjectPackageReviewController` methods** on the canonical 4-key per-room shape (`room`, `overview`, `works_summary`, `solution_type_id`), removing legacy `summary` / `description` keys from `editPayload()` derivation, `generateRoomSummary()` response, `generateSurveyRooms()` validation + scaffold, and `parseReviewPayload()` persistence.
3. **Renamed the `RoomOverviewSummaryService::summarize()` output key** from `summary` to `works_summary`, plus updated the `ExtractQuoteJob` scaffold to emit the canonical 4-key shape and added two write-side guard tests to `ReviewedDataStructuralDiffTest`.

The narrow scope of these five files is correct. The new tests (`parseReviewPayload` reflection + `$package->update` round-trip) are well-formed and exercise meaningful invariants.

**However, the service-key rename in `RoomOverviewSummaryService` was not propagated to all of its callers.** Two production code paths (`RamsComplianceUpgradeService` and `WorksheetGeneratorService`) still read the old `summary` key from the service's return value and will now silently no-op. These are critical regressions because they fail-open: no exception, no log warning, just empty bullet output across RAMS and Worksheet generation. The blast radius is "every render that hits the per-room bullet conversion path after Plan 07 deploys."

A secondary regression sits in `RamsReviewController` (different controller, RAMS-document path), where `parseReviewPayload()` still emits the legacy `summary` key — partly mitigated by the read-side normaliser, but inconsistent with the principle Plan 07 is asserting for the project-package path. This was out of Plan 07's stated scope, but worth flagging because the same rename will eventually need to land there.

The two new write-side tests look correct, with one nitpick on test naming/coverage clarity. The reflection approach (`ReflectionMethod` + `Request::create()`) is sound and won't false-positive.

## Critical Issues

### CR-01: RoomOverviewSummaryService rename breaks RamsComplianceUpgradeService bullet conversion

**File:** `app/Services/Rams/RamsComplianceUpgradeService.php:168`
**Issue:** `RoomOverviewSummaryService::summarize()` now writes `works_summary` (not `summary`) into each returned row. `RamsComplianceUpgradeService::ensurePerRoomBullets()` still reads the OLD key:

```php
$bullets = trim((string) ($result['summary'] ?? ''));
if ($bullets === '') continue;
$rooms[$roomIdx]['works_summary'] = $bullets;
```

Because the rename was not propagated, `$result['summary']` is always `''`, the `continue` short-circuits every iteration, and `$rooms[$roomIdx]['works_summary']` is never backfilled. The per-room bullet conversion silently no-ops on every call — failing open with no log line. This is the exact `summarize()` invocation the docblock at line 100-101 describes as the compliance-upgrade fast path. It's directly in the RAMS PDF render hot path (`upgradeScopeOfWorks`).

**Fix:**
```php
// Phase 22.1 Plan 07: RoomOverviewSummaryService now writes `works_summary`
// not `summary` (see RoomOverviewSummaryService docblock).
$bullets = trim((string) ($result['works_summary'] ?? ''));
if ($bullets === '') continue;
$rooms[$roomIdx]['works_summary'] = $bullets;
```

### CR-02: RoomOverviewSummaryService rename breaks WorksheetGeneratorService bullet backfill

**File:** `app/Services/WorksheetGeneratorService.php:139`
**Issue:** Same regression as CR-01 in a second caller. The worksheet-generation backfill that converts overview prose into bullets does:

```php
$results = $summariser->summarize($payload);
foreach ((array) $results as $r) {
    if (! is_array($r)) continue;
    $rname = strtolower(trim((string) ($r['room'] ?? '')));
    $bull  = trim((string) ($r['summary'] ?? ''));   // ← reads dead key
    if ($rname === '' || $bull === '') continue;
    ...
    $store['room_overviews'][$roomOverviewIdx[$rname]]['works_summary'] = $bull;
```

Post-Plan-07, `$r['summary']` is always `''`, the inner `continue` short-circuits every row, and the worksheet's bullet backfill silently fails. The persisted `works_summary` on `room_overviews[i]` is never updated. Like CR-01, this is fail-open with no log warning.

**Fix:**
```php
// Phase 22.1 Plan 07: RoomOverviewSummaryService now writes `works_summary`
// not `summary` (see RoomOverviewSummaryService docblock).
$bull  = trim((string) ($r['works_summary'] ?? ''));
```

## Warnings

### WR-01: ProjectPackageReviewController::generateScopeOfWorks still reads legacy `$ro['summary']` fallback

**File:** `app/Http/Controllers/ProjectPackageReviewController.php:463`
**Issue:** The `generateScopeOfWorks()` method (unchanged by Plan 07) reads room overview data with a fallback to the legacy key:

```php
$summary = trim((string) ($ro['works_summary'] ?? $ro['summary'] ?? ''));
```

After Plan 07, `parseReviewPayload()` drops the `summary` key on every save, so this fallback is dead code for any record that has been re-saved via the new code. The risk: it would mask a real regression where `works_summary` is missing — silently substituting whatever stale `summary` happens to be in storage from pre-backfill records. The defense-in-depth read should match the new canonical shape.

**Fix:** Drop the legacy-key fallback. If a record predates the backfill artisan command, the read-side normaliser (`RamsReviewDataService::normaliseRoomOverviews`) already projects to the canonical 4-key shape, so `$ro['summary']` will never reach this code anyway in practice.

```php
$summary = trim((string) ($ro['works_summary'] ?? ''));
```

### WR-02: ProjectPackageReviewController::generateRoomSummary still passes legacy `'summary' => ''` into summarize() input

**File:** `app/Http/Controllers/ProjectPackageReviewController.php:543`
**Issue:** The AJAX `generateRoomSummary()` method passes the input row to `RoomOverviewSummaryService::summarize()` with a dead `'summary' => ''` key:

```php
$results = $this->roomSummaryService->summarize([
    [
        'room'                => $room,
        'overview'            => $overview,
        'summary'             => '',           // ← dead key
        'solution_type'       => $solutionTypeName,
        'solution_method'     => $solutionTypeMethod,
    ],
]);
```

The service only reads `room` and `overview` from each input row — the extra `summary` field is harmless input bloat — but it contradicts the principle of "the canonical row is exactly 4 keys" that the rest of Plan 07 asserts. Equivalent dead input lives in `WorksheetGeneratorService.php:133` (`['room' => …, 'overview' => …, 'summary' => '']`). Both should be cleaned up so future readers of the codebase see one consistent shape.

**Fix:** Drop the dead `'summary' => ''` line in both call sites — the service does not consume it.

### IN-01: RamsReviewController parseReviewPayload still persists legacy `summary` (out-of-scope but related)

**File:** `app/Http/Controllers/RamsReviewController.php:298`
**Issue:** A separate controller (`RamsReviewController`, RAMS-document path — different from `ProjectPackageReviewController`) still emits the legacy `summary` key in its own `parseReviewPayload()`:

```php
$roomOverviews[] = [
    'room'     => $room,
    'overview' => trim((string) ($row['overview'] ?? '')),
    'summary'  => trim((string) ($row['summary']  ?? '')),

```

Combined with `RamsReviewController::summarize()` at line 328-329 (which calls `RoomOverviewSummaryService::summarize()` and assigns the result whole back into `$payload['room_overviews']`), this creates a hybrid persisted row that contains BOTH `summary` (empty, from `parseReviewPayload`) AND `works_summary` (populated, from the renamed service). The read-side normaliser (`RamsReviewDataService::normaliseRoomOverviews`) strips the legacy key at read time, so byte-equivalence holds — but every save now writes data the reader actively ignores.

Plan 07 explicitly scoped to the `ProjectPackageReviewController` path. Flagging here so a future closure plan (or follow-up issue) can converge `RamsReviewController` on the same canonical shape.

**Fix:** Out of Plan 07's scope. Track as a follow-up — rename the `summary` field in `RamsReviewController::parseReviewPayload()` to `works_summary` to match the project-package path and the new service contract.

### IN-02: RoomOverviewSummaryService no-op early-return path does NOT inject works_summary

**File:** `app/Services/RoomOverviewSummaryService.php:35-37`
**Issue:** The check-list in the plan asks "do the 3 renamed writes consistently land for every code path." There are actually FOUR return paths in `summarize()`:

1. Line 36 — `if (empty($rows))` → returns `$roomOverviews` UNCHANGED, no `works_summary` injected.
2. Line 47-51 — empty `$roomsForAi` (all rooms have empty overview) → injects empty `$r['works_summary'] = ''`.
3. Line 69-80 — AI success → injects `$r['works_summary'] = …` (either AI bullets or fallback prose).
4. Line 87-90 — AI failure → injects `$r['works_summary'] = $this->fallbackSummary(...)`.

Path 1 (line 36) returns input untouched. Practically this only fires when no row has a non-empty `room` field — a degenerate input case where callers would also have nothing to consume. No functional regression today, but it's an asymmetry against paths 2/3/4. Worth a one-line guard or a docblock note that "input rows with no valid `room` field are returned verbatim and may not contain `works_summary`."

**Fix (minor):** Either inject the key consistently on path 1 (cheap defensive `array_map`), or add a docblock note. Not a bug — flagging for future maintainability.

### IN-03: ReviewedDataStructuralDiffTest write-side round-trip test exercises Eloquent cast, not the merge logic

**File:** `tests/Feature/Rams/ReviewedDataStructuralDiffTest.php:280`
**Issue:** The test name (`test_write_side_package_update_round_trips_canonical_shape_unchanged`) implies it verifies the WHOLE write-path round-trip. In practice it calls `$package->update(['extracted_data' => $canonicalPayload])` with a wholesale payload replacement — not through `parseReviewPayload()` + `array_merge($package->extracted_data ?? [], $payload)` (the actual `update()` / `approve()` controller-method body). So it exercises:

- The `protected $casts = ['extracted_data' => 'array']` JSON cast.
- The MySQL JSON column round-trip.

It does NOT exercise the merge that could re-introduce legacy keys via stale `$package->extracted_data` carrying old fields not overwritten by the payload key paths. The first test (`parseReviewPayload reflection`) covers the parsing layer; an additional small test that uses the full controller `update()` action on a package whose `extracted_data` already contains legacy keys would catch the case where `array_merge` accidentally preserves legacy `summary` / `description` because Plan 07's parseReviewPayload only writes its 4-key array (the merge then overlays it on top of legacy keys at the same path).

Looking at `update()` (line 314 — `$merged = array_merge($package->extracted_data ?? [], $payload);`), the merge replaces `room_overviews` wholesale because PHP `array_merge` overwrites keys with later values for non-numeric keys. So in practice this is safe. But a test that explicitly verifies legacy keys are gone after a controller `update()` call would be a stronger invariant.

**Fix:** Either rename the test to make scope clear (e.g. `test_extracted_data_json_cast_preserves_canonical_shape_unchanged`) or add a follow-up controller-level integration test. Not a bug.
