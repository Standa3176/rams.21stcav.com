## Summary — the four findings that change the plan

1. **The bag trap in CONTEXT.md cannot fire.** `project_packages` has **no `reviewed_data`
   column** — not in the migration, not in `$fillable`, not in `$casts`. `ProjectPackage` is not
   `RamsDocument`. Every `?: extracted_data` fallback that reads `$package->reviewed_data` therefore
   always falls through. **Write to `extracted_data`. Nothing else is needed.** (Q1)
2. **`importFromData()` is NOT the common funnel.** It has exactly one production caller —
   `QuoteWerksImportService:72`. The PDF path goes through `import()` / `reimport()` /
   `completePendingReimport()` / `ExtractQuoteJob`. CONTEXT.md's canonical reference is wrong. (Q2)
3. **The PDF path already has this feature.** `ExtractQuoteJob::generateContentPack()`
   (`app/Jobs/ExtractQuoteJob.php:217-270`) already calls `RoomOverviewSummaryService::summarize()`
   and writes `works_summary` into `extracted_data['room_overviews']`, best-effort, after the
   transaction. **The real gap is the QuoteWerks path only.** The phase is materially smaller than
   the roadmap assumes. (Q2, Q4)
4. **The worksheet already does the lazy variant.** `WorksheetGeneratorService:118-188` back-fills
   bullets at worksheet-generation time via the same service and persists them back.
   **The worksheet needs zero new work** — but it imposes a hard output constraint: bullets that do
   not start with `- ` are silently discarded (`:111`, `:174`). (Q6)

**Primary recommendation:** one new job, `GenerateRoomWorksSummariesJob(int $packageId)`, modelled on
`GenerateSurveyQuestionsJob`, dispatched from `QuoteImportService::importFromData()` with
`->afterCommit()`, filtering to rows whose `works_summary` is empty, writing back to
`$package->fresh()->extracted_data`. Optionally also dispatch from `reimport()` /
`completePendingReimport()` to close the re-import hole. No migration. No new prompt. No new service.

**Write to `extracted_data['room_overviews'][n]['works_summary']`. Single bag. No double-write. No
per-key merge in the reader.**

### Q2.3 — transactions and `afterCommit`: **yes, this footgun is live**

Every relevant creator is wrapped:

- `importFromData()` — `return DB::transaction(function () … )` at **`:348`**, package created at `:371`, returned at `:381` from *inside* the closure.
- `import()` — `DB::transaction` at `:72`.
- `reimport()` — `:212`. `completePendingReimport()` — `:302`.

Queue config: `config/queue.php:16` default `env('QUEUE_CONNECTION', 'database')`; `.env:39`
`QUEUE_CONNECTION=database`. **`config/queue.php:44` sets `'after_commit' => false` for the
`database` connection** (and `:71, :80, :91, :100` for the others). So **global
`after_commit` is OFF**.

The codebase is already aware of this and relies on it being handled:
`app/Core/Modules/Survey/SurveyService.php:234-236` comments *"The database queue driver defers
actual dispatch until after the outer transaction commits, so the room record is guaranteed to
exist when the job runs"* — then dispatches bare at `:236`, inside the `DB::transaction` opened at
`:112`.

**That comment is not reliable in general.** With `after_commit => false` the job row is inserted
into the `jobs` table *within the same transaction*, so it is invisible to a worker until commit —
which is why it works in practice **on the `database` driver with a single connection**. It is an
accident of the driver, not a guarantee, and it breaks immediately on `redis`/`sqs`, or if
`DB_QUEUE_CONNECTION` (`config/queue.php:40`) is ever pointed at a second connection.

**Recommendation (HIGH confidence):** dispatch with
`GenerateRoomWorksSummariesJob::dispatch($package->id)->afterCommit()`, wrapped in try/catch
mirroring `SurveyService.php:236-241`. It is one method call, it is correct on every driver, and it
removes the dependency on the driver accident. Do **not** flip the global `after_commit` to `true`
in `config/queue.php` — that would change dispatch semantics for all ten existing job classes and is
far outside this phase's fence.

**Alternative worth noting:** `ExtractQuoteJob` sidesteps the problem entirely by calling
`generateContentPack()` **after** the transaction closes (`:174-177`, with the explicit comment at
`:187-190`: *"Called AFTER the DB::transaction above closes — never inside it"*). Dispatching from
*outside* the `DB::transaction` closure in `importFromData()` would need the closure to return and
the dispatch to happen in the method body — a ~3-line restructure. `afterCommit()` is cheaper and
achieves the same thing.

Also relevant to cost: under `phpunit.xml:40` `QUEUE_CONNECTION=sync`, so in tests the job runs
**inline at dispatch** unless `Queue::fake()` is used. With `afterCommit()` + `sync`, Laravel still
defers to commit. This is a real test-authoring trap: a test that asserts the DB state immediately
after `importFromData()` returns will see the job already run (sync) — which is convenient, but it
means `Queue::fake()` is required to assert *dispatch* separately from *effect*.

### Q4.1 — `summarize()` is a **batch** call, not per-room. D-02's cost model is wrong (in your favour).

`app/Services/RoomOverviewSummaryService.php:28` — `public function summarize(array $roomOverviews): array`.

So the "4-key row in" claim in CONTEXT.md is **half right**: the 4-key shape is accepted, but only
`room` + `overview` are consumed. HIGH confidence.

**Output:** the same array, with `works_summary` (`:76` / `:80` / `:95`) and `_summary_fallback`
(`:77` / `:81` / `:96`) set on **every** row. Verified.

**One AI call for all rooms.** `:59` — `AIManager::run($prompt, ['rooms' => $roomsForAi])` is called
**once**, outside any loop, with every room in the payload. The prompt is built for a JSON *array* of
rooms (`RoomOverviewSummaryPrompt::build():111-118, :143-146`).

> **This contradicts D-02 and the roadmap's "a 12-room quote is 12 calls" (ROADMAP:1042-1044).**
> With the existing service, a 12-room quote is **1 call**. The decision to background it is still
> right — the call is slow (up to 180 s, Q4.3) and `maxTokens()` is 2000 (`RoomOverviewSummaryPrompt:97`),
> which is a real truncation ceiling at 12 rooms × 5-12 bullets. But the planner should not design
> a 12-way fan-out, a per-room retry ledger, or a partial-failure resumption scheme for a cost that
> does not exist. **Surface this at the checkpoint — it is a decision input the user did not have.**
>
> Secondary consequence: `maxTokens() = 2000` means a large quote can trip
> `ClaudeProvider:202-206` *"Claude response was truncated (max_tokens reached)"* → `RuntimeException`
> → after 2 attempts `AIGenerationException` → **every room falls back, not just the overflow ones**
> (`RoomOverviewSummaryService:85-98`). If the planner wants robustness at 12+ rooms, the honest
> options are (a) chunk the rooms into batches inside the job, or (b) raise `maxTokens()`. (a) does
> not touch the live prompt; (b) does. Prefer (a).

### Q4.3 — Failure surface of `AIManager`

`app/Core/AI/AIManager.php:67` — `public static function run(BasePrompt $prompt, array $context = [], ?string $provider = null): array`.

| Property | Value | Line |
|---|---|---|
| Internal retries | `private const MAX_ATTEMPTS = 2;` — loop `while ($attempts < self::MAX_ATTEMPTS)` | `:30`, `:95` |
| Exception on failure | `\App\Exceptions\AIGenerationException` — thrown at `:140-143` (provider threw on last attempt) and `:148-151` (empty result after all attempts) | — |
| What the provider throws | `RuntimeException` only; caught at `:132` | `ClaudeProvider:181, :205, :229` |

| HTTP timeout | `->timeout($options['timeout'] ?? self::DEFAULT_TIMEOUT)` with `private const DEFAULT_TIMEOUT = 180;` | `ClaudeProvider:177`, `:20` |
| Truncation | `stop_reason === 'max_tokens'` → `RuntimeException` | `ClaudeProvider:202-206` |

**Worst-case wall clock for one `summarize()` call: 2 × 180 s = 360 s.** The precedent job's

(matching `ReimportQuoteJob:67`'s precedent of raising it to 180 with the justification *"Generous
ceiling for slow Claude responses on dense quotes"*). The planner must note this deviation from
D-06 **by name with a reason**, not silently.

Also: with `$tries = 2` at the job level *and* `MAX_ATTEMPTS = 2` inside `AIManager`, a hard outage
costs up to **4** provider calls and ~12 minutes. The `catch (\Throwable)` envelope of the
precedent (`GenerateSurveyQuestionsJob:147`) swallows the error and **returns normally**, which means
the queue sees success and **does not retry** — so in the precedent's shape, `$tries = 2` is
effectively `1`. This is worth stating plainly in the plan: copying the precedent's envelope means
`$tries` is decorative. That is acceptable under D-04 and is actually the safer posture (no retry
