<framework_facts>
**Why this plan does NOT use `->afterCommit()`. Verified in the installed Laravel 12.54.1 — read this
before you write the dispatch, because it inverts what an earlier draft of this plan instructed.**

`->afterCommit()` does not push the job. It makes `Queue::enqueueUsing()` **register a callback**; the
real push happens later, inside
`vendor/laravel/framework/src/Illuminate/Database/DatabaseTransactionRecord.php:83-88`, whose
`executeCallbacks()` is a bare `foreach ($this->callbacks as $callback) { $callback(); }` — **with no
try/catch of its own**.

And that runs outside every try/catch in the transaction method:
`vendor/laravel/framework/src/Illuminate/Database/Concerns/ManagesTransactions.php` wraps the PDO
commit in a try/catch at `:51-64`, but the `$this->transactionsManager?->commit(...)` call at
`:66-70` — the call that executes those callbacks — sits **outside it**.

**Consequence:** with `->afterCommit()`, a queue-driver failure throws out of
`transactionsManager->commit()`, out of `DB::transaction()`, and out of `importFromData()` — **after**
the `project_packages` row has already been committed. A try/catch wrapped around the
`dispatch()->afterCommit()` call wraps only the *registration* of the callback, which cannot fail for
this reason. So that arrangement produces a **half-reported import**: the package exists, the request
fails. That is strictly worse than what AIB-04 and D-04 promise, and a test asserting "a dispatch
failure does not fail the import" against it would be either unfixably RED or made green by throwing
at the registration point — which is asserting the safe half of a condition, the exact 2026-09-30
failure mode CONTEXT bans.

**Therefore: dispatch AFTER `DB::transaction()` returns, with no `afterCommit()`.** D-10's intent —
never let a worker see the package before the commit — is then satisfied **structurally**: the
transaction has already committed by the time the dispatch line is reached. And the real push is now
inside the try/catch, so AIB-04 is actually deliverable.

One test-environment note, confirmed: under `RefreshDatabase` the whole test runs inside an outer
transaction, and `DatabaseTransactionsManager::afterCommitCallbacksShouldBeExecuted()` returns
`$level === 1` (not `=== 0`), which is why a before-vs-after-commit distinction is still testable here.
</framework_facts>
</context>
