<objective>
Add the two house-rule detectors `ControlTextRuleViolations` was explicitly built to receive
(class docblock, `:19-21`): `ffp2` (trivial, no negation) and `confined_space` (negation-aware,
conservative-by-construction). These are the ONE choke point `RamsBuilderService::reviewedToRisk()`
consumes via `detectAll()` — that call site is NOT touched by this plan, per the class's own
extensibility contract and CONTEXT.md's explicit prohibition.

This plan covers the hazard **control-line** text surface only (RULE-01's respiratory-PPE
wording and GATE-07's confined-space mislabel, wherever either appears inside a hazard's
`controls[]` array). It does NOT cover the `ppe`/`ppe_matrix` arrays (Plan 28-03 — a
different, closed-vocabulary surface with no rule-scanning mechanism today) and does NOT add
the throwing gate (Plan 28-06 — GATE-06/07's independent re-check, which calls into these same
detectors rather than re-implementing them).

Purpose: give the tier-1 precedence branch in `reviewedToRisk()` the ability to auto-correct a
reviewed FFP2 or confined-space control line to current library text on every full regeneration
— the same mechanism that fixed 438 rows in Plan 27-08 — and give Plan 28-06's throwing gate a
single place to classify surviving text.
Output: two new detector methods, a two-entry registry addition, and an extended proof corpus in
the existing test file (no new test file — the corpus lives where the existing detectors' corpus
already lives).
</objective>

**1. `DocxBuilderService.php:1903` — §6.11 "Coordination with Other Trades" boilerplate.
EXCLUDED, deliberately.**
The sentence reads: *"Principal Contractor — obtain permits-to-work (ceiling access, hot works,
roof access, confined-space entry) from the Principal Contractor…"*, and its own docblock says
*"Always renders — this is a boilerplate coordination policy applicable to every install."*

It is excluded on the same reasoning as CONTEXT.md D-02: it **names a permit category the
Principal Contractor may operate on their site**; it does not assert that a ceiling void, comms
room or riser IS a confined space. RULE-06 and GATE-07 govern how 21CAV labels **its own**
spaces. Removing the item would misrepresent the PC's permit regime rather than correct a 21CAV
claim.

Two things make this safe rather than merely convenient:
- It is rendered as direct DOCX boilerplate and never enters `$data['hazards']`, `$data['ppe']`
  or `$data['ppe_matrix']`, so Plan 28-06's gate never scans it. There is no live risk of it
  tripping generation.
- Task 2 adds a test recording its classification explicitly, so the behaviour is documented
  rather than discovered later.

Note the boundary this draws: D-02 exempted a Blade **picker** (engineer UI). This is
unconditional **generated document text**, which ROADMAP criterion 2 names as in scope — so the
exemption does **not** carry over automatically and is being granted here on its own merits.
If a reviewer disagrees, the fix is a one-word edit to that bullet, not a redesign.

**2. `resources/views/rams/review.blade.php:264` — the permit-type picker. EXCLUDED per
CONTEXT.md D-02, already locked.** No plan touches it. Listed again here only because it is the
nearest neighbour to decision 1 above and the two are easily confused.
