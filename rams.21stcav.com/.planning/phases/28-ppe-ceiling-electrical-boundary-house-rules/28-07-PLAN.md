<objective>
**Orchestrator decision (2026-09-05, overriding CONTEXT.md D-08's earlier "measure before
deciding" framing): a backfill migration IS in scope, unconditionally.** Two surfaces do not
self-heal on their own: `reviewed_data['ppe']` (a stored FFP2 string survives every future
regeneration forever — `RamsBuilderService::reviewedToRisk()`'s ppe assembly and
`RamsDataBuilderService::mergePpe()` only ever merge/dedupe, they never rescan already-persisted
values without Plan 28-03's wrap, and even with that wrap a document that is never regenerated
again keeps the stale string in `generated_data['ppe']` forever) and `reviewed_data['exclusions']`
(Plan 28-05's default-seed bullet only fires when the key has never been set; any document that
has been through even one no-op Save Review is permanently excluded from that default). Both
surfaces are named in the ROADMAP success criteria ("No respiratory-PPE mention anywhere in
generated output"; "A generated RAMS states the electrical scope boundary"), so fix-forward alone
does not satisfy them — this migration is required, not optional, regardless of what the
measurement below finds.

**What the measurement is FOR:** research could not reach the production database this session
(local dev DB has 0 `RamsDocument` rows). The measurement is not a go/no-go gate on whether to
build the migration — it is (a) the evidence the migration's own commit/SUMMARY records instead
of an invented number, and (b) the count against which the migration's own reported
"documents touched" output is sanity-checked after it runs. Do not hardcode an assumed row count
anywhere in the migration or its documentation before Task 1 reports the real one.

**Scope, stated explicitly:** this migration touches ONLY `reviewed_data` (both keys), mirroring
Plan 27-08's precedent exactly. It does NOT touch `generated_data` or any already-rendered
on-disk `.docx`/`.pdf` file — retroactively rewriting a document a client may already hold a copy
of is a materially different, larger, and riskier action than this milestone's source artifacts
decided on; the risk posture explicitly asks for a minimal diff. Any hazard-controls FFP2/
confined-space text still baked into an old document's `generated_data` is instead caught by
Plan 28-06's throwing gate the next time that document goes through ANY generation path
(Save Review, regenerate, or PDF/DOCX rebuild) — forcing remediation at that point rather than
silently rewriting a historical document out from under an engineer. `RamsRefreshComplianceCommand`
(considered as an alternative/complementary path, per research's Open Question 3) is NOT used
here: tracing its pipeline confirms it re-runs `RamsComplianceUpgradeService::upgrade()` over
`generated_data` but never calls `reviewedToRisk()`'s tier-1 detector — it cannot substitute for
either this migration's direct `reviewed_data` patch or the detector's self-heal-on-full-
regeneration behaviour.

Purpose: guarantee RULE-01 and RULE-09 hold for already-persisted `reviewed_data`, not just
future writes.
Output: one measurement (recorded in the SUMMARY, human-run against production) and one migration
file.
</objective>
