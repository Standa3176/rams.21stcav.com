requirement.** `house-rules.md` §"Ceiling work" and both `REQUIREMENTS.md` RULE-06 and
`ROADMAP.md` Phase 28 success criterion 2 already state the target title verbatim: "Restricted
access and ceiling void working". Phase 26 shipped "Restricted access and ceiling voids"
(missing "working"). Renaming means editing three code surfaces in one commit and needs ZERO
edits to `ROADMAP.md`/`REQUIREMENTS.md` (they already state the correct target); amending the
requirement instead would mean editing two planning documents AND recording a permanent,
deliberate app-vs-skill divergence for no functional gain — the milestone's own stated
arbitration rule is "where the app and the skill disagree, the skill wins unless the user says
otherwise for a specific job" (`REQUIREMENTS.md` preamble), and no such override exists for
RULE-06. Rename is both the smaller diff and the one that needs no divergence record.

`LegacyHazardNameFoldMap` is the exact mechanism Phase 26 built for this: the seeder is the
version-controlled source, the map is the single choke point every caller resolves a legacy name
through. This plan uses it as designed, plus closes a reachability gap this rename would
otherwise create: `LegacyHazardNameFoldMap`'s existing two entries only fold PRE-Phase-26 names
forward. Any document reviewed between Phase 26 and Phase 28 — carrying the Phase-26-shipped
title "Restricted access and ceiling voids" (not a pre-Phase-26 legacy name) — would silently
keep the OLD title forever on regeneration unless a new fold-map entry is added for THAT string
too. This plan adds that entry explicitly; it is not optional.

Purpose: make the app's hazard title match the skill's settled wording, on all four surfaces
CONTEXT.md's D-05 names (fold-map target, seeder, drift-guard test, requirement/roadmap text —
the last of which already agrees and needs no edit), with no unreachable "renamed but no path
forward" gap for already-reviewed documents.
Output: one renamed seeder hazard, two repointed fold-map values, one new fold-map entry, and an
updated/extended drift-guard test.

**Added in revision 1, after plan-checker review (Warning 4). Stated so it is a decision, not an
omission.**

The rename is **not** backfilled onto already-persisted documents. Plan 28-07's migration touches
`reviewed_data['ppe']` and `reviewed_data['exclusions']` only; a document generated between
Phase 26 and Phase 28 keeps the stored title "Restricted access and ceiling voids" in its
`reviewed_data` / `generated_data` until it is next fully regenerated, at which point the new
fold-map entry this plan adds resolves it forward.

**Why that is acceptable here, when the PPE and exclusions surfaces DID warrant a migration:**
- The old title is a **wording-consistency** gap, not a safety defect. "Restricted access and
  ceiling voids" was never a confined-space mislabel — it is the correct position, just not the
  skill's exact phrasing. A stale `Dust Mask (FFP2)` PPE entry, by contrast, is a live safety
  contradiction, which is why that one is migrated.
- It self-heals on the next full regeneration, which is the same philosophy already applied to
  stale hazard-control text (Plan 27-08's tier-1 mechanism) and accepted there.
- D-05's "all surfaces must agree, never a third spelling" constraint is about the surfaces the
  app **generates from** — fold map, seeder, requirement text, roadmap. It is satisfied. Documents
  already issued to clients are historical records; Phase 26 established
  (`26-CONTEXT.md`, denormalised hazard storage) that reseeding deliberately cannot retro-change
  an already-issued RAMS.

**If this is later judged wrong**, the fix is to extend Plan 28-07's migration with a third
JSON-patch pass over stored hazard names using the same chunking and idempotency, not a new
mechanism.
</scope_decision_no_title_backfill>
