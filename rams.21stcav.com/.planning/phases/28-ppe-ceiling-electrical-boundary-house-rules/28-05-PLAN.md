<objective>
Ship RULE-09 (electrical scope boundary) and RULE-10 (ceiling-load statement) — both are "make an
existing statement reach output" problems, not "invent new logic" problems.

**RULE-10 needs no new trigger.** Research empirically proved (this session's `artisan tinker`
run against the real seeded `hazard_templates` table) that `signal:ceiling_void_access` already
fires for a ceiling-MOUNTED job via the broad `ceiling_works` activity keyword match — a job
never has to enter the void. The ceiling-load sentence already exists verbatim at
`HazardTemplateSeeder.php:223` inside that hazard's controls. This plan's job is to lock that
finding in with a real, end-to-end regression test (Wave-0 gap identified in `28-VALIDATION.md`)
so it stops being a point-in-time observation, not to write new derivation logic.

**RULE-09 has no home today.** D-06's constraint is that no scope signal may be trusted without
first verifying it is non-empty on live data (the DATA-01 trap that made Phase 27's RULE-03
correct-but-unreachable) — and D-06 explicitly licenses the unconditional route
(`house-rules.md` §"Scope boundaries to state explicitly": "these recur on almost every job and
are worth stating even when obvious"). `RamsDisplayPatchService`'s existing 5-item unconditional
default exclusions array is exactly that unconditional home, already reaching both DOCX render
paths. This plan adds a 6th bullet there — no new mechanism, no AI decision, per `CLAUDE.md:12`.

**D-07 scope decision, stated explicitly:** this plan ships ONLY the electrical-boundary
sentence itself. It deliberately DEFERS the four further `house-rules.md` §"Electrical scope
boundary" positions D-07 names (no BS 7671/lock-off/test-dead language for plugging into a
socket; never a live-working PPE row; "first-fix power" -> "first-fix AV signal/data/ELV
cabling" terminology; hardwired-supply isolation by the client's authorised person). Reason: (1)
`RULE-09` as written in `REQUIREMENTS.md` is exactly one sentence and this plan satisfies it in
full; (2) there is an open, unresolved user decision on BS 7671 wording carried in project memory
— settling it is a checkpoint question, not a planner call, and this plan's minimum route does
not require settling it; (3) the other three positions are checks against text that does not
currently exist anywhere in the app (no live-working PPE row exists; "first-fix power" does not
appear in any file this phase touches) — adding them now would be scope invention against no
named defect. This mirrors the Phase 27 RULE-12 precedent of shipping a minimum and saying so
explicitly rather than silently narrowing.

Purpose: satisfy ROADMAP success criterion 3 in full for RULE-10 (self-heal proof) and in its
stated minimum for RULE-09 (unconditional statement).
Output: one new exclusions bullet, one feature test per requirement.
</objective>
