<objective>
Add the throwing half of D-03's auto-correct-then-throw pair: an independent re-check inside
`RamsComplianceUpgradeService::upgrade()`, mirroring GATE-09's `enforceDisplayLiftGate()` shape
exactly (same file, same config-gated call-site pattern, same `RamsGenerationException` +
`RamsController.php:597-604` catch-and-redirect surface). This is the mechanism that catches
anything Plan 28-01's tier-1 auto-correction did NOT reach — most importantly the Save Review
path (`RamsController::updateAndDownload()`), which never calls `RamsBuilderService::reviewedToRisk()`
at all and therefore never runs tier-1 correction; a pre-Phase-28 document's stale
`generated_data['hazards'][*]['controls']` can still carry FFP2/confined-space text when an
engineer does an otherwise-unrelated Save Review, and this gate is the only thing that will catch
it on that specific path.

**Scope decision, stated explicitly:** the gate scans THREE surfaces, not just hazard controls —
`$data['hazards'][*]['controls']` (via `ControlTextRuleViolations::detect()`, both `ffp2` and
`confined_space` keys), `$data['ppe']` (a flat array, raw case-insensitive substring check for the
literal token `FFP2` — NOT routed through `ControlTextRuleViolations`, since PPE is closed
vocabulary, not free text needing classification, per Plan 28-03's own reasoning), and
`$data['ppe_matrix'][*]['ppe']` (same raw check, defense-in-depth even though `addPpeMatrix()`
already rebuilds this array fresh from corrected source strings at the very start of the same
`upgrade()` call). This is required for GATE-06's literal wording — "errors on any FFP2
occurrence" — to be true rather than true-only-for-the-hazard-controls-subset.

**The 5-call-site decision, stated explicitly (per the pattern map's flagged gap):**
`RamsComplianceUpgradeService::upgrade()` has 5 call sites. Verified this session:
1. `RamsBuilderService.php:296` (`runFromReview()`) and 2. `RamsBuilderService.php:941`
(`buildFromForm()`'s pipeline) are both reached ONLY via `BuildRamsDocumentJob::handle()`, which
already wraps its entire body in `catch (\Throwable $e)` and persists `status = STATUS_FAILED` +
`error_message` on the record — ADEQUATE, no change needed; a thrown `RamsGenerationException`
here already surfaces to the user via the document's status/error message.
3. `RamsController.php:603` (`updateAndDownload()` / Save Review) already has a clean
`catch (RamsGenerationException) { return back()->withInput()->with('error', ...); }` —
ADEQUATE, the established GATE-09 precedent, unchanged.
4. `RamsController.php:701` (DOCX-rebuild-on-download fallback) catches `\Throwable`, logs, and
sets `$rebuildError`, which the method later surfaces via `back()->with('error', "DOCX download
failed: {$rebuildError} — ...")` — ADEQUATE (confirmed by reading the full method to line ~726;
it does not silently swallow the message), though structurally different from the Save Review
catch. No change needed.
5. `RamsController.php:852` (`downloadPdf()`) has **NO try/catch around the `upgrade()` call at
all** — a thrown `RamsGenerationException` here propagates as an unhandled exception (Laravel's
default 500 page). This is the one genuine gap. **Fix: wrap this specific call in the same
try/catch shape as `updateAndDownload()`**, placed before the existing `pdfService->buildRams()`
try/catch (which remains unchanged, for actual PDF-rendering failures).

Purpose: complete D-03's pair and close the one real reachability gap in the existing `upgrade()`
call-site surface, rather than assuming GATE-09's precedent already solved it everywhere.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP request (Save Review / DOCX-rebuild-on-download / PDF-download) -> `RamsComplianceUpgradeService::upgrade()` -> thrown exception -> `back()->with('error', $e->getMessage())` | The exception message is returned to the requesting user's own browser session (never to a third party) — it names a safety-content rule violation, not internal system state. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28-06-01 | Denial of Service | An overly aggressive gate blocks all document generation | mitigate | `RAMS_PPE_CEILING_ELECTRICAL_GATE` env flag is a single-.env-edit, instant kill-switch, independent of `RAMS_DISPLAY_LIFT_GATE` — GATE-09 cannot be accidentally disarmed by a GATE-06/07 rollback and vice versa (D-08). |
| T-28-06-02 | Information Disclosure | Exception message surfaced via `back()->with('error', $e->getMessage())` | accept | The message is a canned, developer-authored safety-rule string built from the offending hazard/PPE text already visible to the same authenticated, authorized user in the review form — no stack trace, no internal path, no cross-user leakage. |
| T-28-06-03 | Elevation of Privilege | none — this plan adds no new route, no new auth check surface | accept | The gate runs inside an already-authorized document-generation pipeline; it narrows what content can be generated, it does not change who can generate. |
