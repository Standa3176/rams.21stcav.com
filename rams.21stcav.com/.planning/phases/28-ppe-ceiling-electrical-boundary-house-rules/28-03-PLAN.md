<objective>
Close research Q4's genuinely-new gap: `reviewed_data['ppe']` is a closed pick-list array
(checkboxes, not free text) that round-trips through `array_unique(array_merge(...))` with ZERO
rule-scanning anywhere in the pipeline. `ControlTextRuleViolations` (Plan 28-01) cannot help here
— its docblock and D-01's own analysis are explicit that it exists for free-text hazard control
lines, not closed-vocabulary picklist items. A stored `Dust Mask (FFP2)` string survives forever
regardless of every other fix in this phase unless this array gets its own, much simpler,
mechanism.

This plan ships that mechanism: `PpeVocabularyFoldMap`, a `LegacyHazardNameFoldMap`-shaped
all-static string-replace map, wired into the two places research identified as touching
ALREADY-PERSISTED `reviewed_data['ppe']` data (`RamsBuilderService::reviewedToRisk()` and
`RamsDataBuilderService::mergePpe()`). `RiskTemplateResolverService.php:44/106` are edited
directly at the source string instead of routed through the map — they are code constants that
generate fresh PPE lists, not stored data being carried forward, so a direct string fix is
sufficient and avoids adding an unnecessary indirection to fresh-generation code.

Purpose: guarantee RULE-01 ("FFP3 replaces FFP2 wherever respiratory PPE is specified") holds for
the PPE array specifically, closing Pitfall 1 from research (a plan that only fixes
`ControlTextRuleViolations` and assumes GATE-06 is satisfied "for any FFP2 occurrence" while this
array is never touched).
Output: one new map class + drift-guard test, two call sites wrapped, one direct source fix, one
end-to-end feature test proving the persisted-data case.
</objective>
