<objective>
Implement GATE-14 (missing risk references) as a WARN-tier gate behind `RAMS_MISSING_RISK_REF_GATE`,
using the config-resident implication map from Plan 30-01, and prove by static source guard that it
does not re-derive the thing it is checking.

Purpose: the canonical defect is Step 4 "Display & Mount Installation" citing RA11/12/13/21 but
omitting RA01 Working at Height and RA02 Manual Handling, on a step entirely about lifting displays
onto wall mounts.

Research Finding 7 reframes this gate completely, and the reframing is the whole plan.
`crossReferenceMethodStatementRisks()` (`:991-1092`) **strips** the model's own "Associated Risks:"
line (`:1043-1046`) and **recomputes** `associated_risks` deterministically from a hard-coded
`$keywordRiskMap` (`:1015-1027`). So in this application a step's risk references are the app's own
output, not the AI's. Two consequences, both binding:

1. GATE-14 must be an INDEPENDENT re-check. Reusing `$keywordRiskMap` would be the "gate re-derives
   the thing it is checking" anti-pattern that `enforceDisplayLiftGate()`'s docblock (`:1268-1276`)
   exists to warn against. The canonical Step-4 defect is a *predictable output* of the map's
   intersection rule at `:1057-1063` — it requires the literal token on BOTH sides, so a step saying
   "lift the display onto the wall mount" never satisfies "manual handling". The map is
   intersection-based; the defect needs implication-based inference.
2. GATE-14 is WARN tier, not error tier (decided by the user after research). A violation is a defect
   in the app's own derivation, not in anything the engineer can edit on the review screen. A
   blocking error there would be unactionable.

Output: one warn-tier gate method, its own dispatch block, a unit test file, and a source guard.
</objective>

<interfaces>
What `crossReferenceMethodStatementRisks()` does, in order (`:991-1092`):
  1. strips any model-authored `Associated Risks: …` bullet via `isAssociatedRisksLine()`
     (`:1043-1046`, `:1100-1103`)
  2. recomputes matches with the hard-coded `$keywordRiskMap` (`:1015-1027`), requiring the keyword
     in BOTH the combined phase text AND the hazard name (`:1057-1063`), with a >4-char
     word-fragment fallback (`:1067-1077`)
  3. writes `$phase['associated_risks']` (int row indices) and
     `$phase['associated_risks_label']` (`'Associated Risks: RA01, RA02'`) — the label is the only
     thing rendered (`pdf/rams.blade.php:1635-1636`)

`RA##` is row index + 1, NOT `$h['id']` (`:1000-1013`, mirrored `DocxBuilderService.php:1221`).

From Plan 30-01 config: `rams_tier1.missing_risk_implications`, rows of
`['phrase' => string, 'signal' => string, 'label' => string]` — step-action vocabulary
(wall mount, onto the bracket, lift the display, above 2m, stepladder, podium, ceiling void).
Hazard-side resolution goes through `StructuralGateVocabulary`, so D-07's one-vocabulary property
holds across GATE-01 and GATE-14.

Warn entry shape (Plan 30-01's contract; render surface built in Plan 30-04):
  ['gate' => 'GATE-14', 'hazard_index' => null, 'step_title' => string, 'hazard' => string,
   'message' => string]

UI-SPEC copy, adapted to warn tier:
  `GATE-14 — method step "{step title}" does not cite {RA##} ({hazard name}), which its own text
   implies.` Because `associated_risks` is app-generated, the message must NOT tell the engineer to
  "add the reference to the step's risks line" — the app overwrites that line on the next run. Say
  instead that the app's own cross-reference derivation missed it and the step should be reviewed
  before issuing.

Source-guard analog — `tests/Feature/Rams/DisplayLiftPolicySourceGuardTest.php:1-80`:
  docblock states the guard's purpose and names the grep the allow-list was DERIVED from, and says
  the list was re-derived live at execution time, not hand-copied;
  `private const ALLOWED_FILES = [...]` with a per-entry justification comment;
  `private const MARKER = 'DisplayLiftPolicy::';`
  scans `base_path('app')` only; `tests/` excluded with a stated reason.
  Caution: GATE-14's marker `keywordRiskMap` is a LOCAL VARIABLE, a weaker grep target than a
  `Class::` marker. Pick the marker deliberately and state the weakness in the docblock.
